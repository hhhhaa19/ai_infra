模块 7

PyTorch 接入、torch.compile 与端到端

这一模块讲什么：前面解释了单个算子为什么快，这里回答下一个问题：把它用进真实工程以后，完整模型有没有变快？顺序是：先搭出 decoder layer，理解 prefill 和 decode，再看测量结果；然后解释融合和 compile，最后把算子正式注册进 PyTorch，并排查 graph break。

文件位置：rmsnorm_ext.cu → src/rmsnorm/torch/ext.cu，rmsNormWarp.cu → src/rmsnorm/kernels.cu。下面保留的旧名字是当时的记录。

1PyTorch 与模型

PyTorch 基础

写 decoder layer 之前，先要会用几个基础语法。nn.Parameter 把张量登记成模型参数，这样 .cuda() 和 state_dict() 才会带上它。nn.Linear 会自动创建 weight，形状是 [输出, 输入]。

RMSNorm 里要用到广播。两个张量右对齐逐维比较，相等或有一边是 1 就能运算，是 1 的那一边沿该维重复使用，不会真的复制（stride=0）。scale 每行一个，形状是 [rows,1]，所以 mean 要写 keepdim=True；w 每列一个，形状是 [n]。两者都能广播到 [rows,n]。这里的乘法用 *，表示逐元素；@ 才是矩阵乘法。

Attention 要把一个维度拆成多个头：[b,s,2048] → reshape 成 [b,s,16,128] → transpose 成 [b,16,s,128] → SDPA → 再换回来。reshape 只是换一种切法，内存顺序不变；transpose 交换两个维度后，张量在内存里不再连续，这时再 reshape 就要拷贝。写 b, s, h = x.shape 解包时，还能顺便检查维数。

搭建 decoder layer

有了这些基础，就能写一层 LLaMA 风格的 decoder。输入先经过 norm1 和 attention，再和原来的 x 相加；结果经过 norm2 和 mlp，再相加一次，这就是 pre-norm 加残差。

x ─┬─ norm1 ─ attn ─┐                         attn：q/k/v/o 四个投影 + SDPA(is_causal=True)
   └────────────────+─▶ x ─┬─ norm2 ─ mlp ─┐   mlp ：down( silu(gate(x)) * up(x) )，SwiGLU
                           └───────────────+─▶ 输出
norm1 / norm2 是两个位置不同的 RMSNorm（各有 weight），impl 对两者相同
hidden 2048、16 头 × 128、intermediate 5632，一层约 5138 万参数（FP32 约 205 MB）

impl 决定两个 RMSNorm 用 eager 写法，还是用我们的算子。

prefill 与 decode

先分清两个名字：decoder layer 是模型结构，decode 是运行阶段。一次生成分两段：prefill 把整段 prompt 一次送入，decode 之后每一步给每个请求送入 1 个新 token。两个阶段穿过同样的层、用同样的权重，只是输入形状不同。

再说权重。同一层在两个阶段用同一套权重；不同层结构相同，但权重各有一套。所以参数量 = 每层 × 层数 + embedding / 输出层。开源模型主要发布的是权重、config.json 和分词器。

这也解释了为什么可以放心替换算子：训练只改权重，不改公式。只要数学等价（eps 位置一致）、权重形状和含义一致、误差在容差内，就能换一种实现。测速时还可以用随机权重，因为计算量和读写量只看形状（MoE 路由除外）。但结论不能直接套到别的模型：hidden 变大时 RMSNorm 占比下降，走的分档也不同。数值验证（尤其 FP16）仍需要真实权重，这一点待验证。

batch 是同时处理几个请求。decode 的主要成本是读一遍权重，b8 共用这一遍读取，所以只比 b1 慢约 24%，均摊到每个请求快很多。这就是批处理的意义。

真实请求长度不同怎么办？hidden 由模型决定，大家都一样；会变的是 prompt 长度和历史长度。主流做法是把所有请求的 token 拼成一长条（packing），配一张 cu_seqlens 边界表。RMSNorm、投影、MLP 这些按行处理的算子不用知道边界，只有 Attention 要用 varlen 接口。

在此之上还有连续批处理（prefill 与 decode 混排）、chunked prefill（长 prompt 切块、每步有 token 预算），更大规模时会把 prefill 和 decode 分开部署。

2调用链与整层收益

从 Python 到 GPU 的调用链

现在看调用 layer(x) 时发生了什么。Python 一层层走到 RMSNorm.forward，再进入我们的算子，由 dispatcher 按张量类型选择实现，最后启动 kernel。

【现在（TORCH_LIBRARY）】
DecoderLayer(impl="ours") → RMSNorm.__init__ → rms_norm_op() → load_rmsnorm()   # 建模型时就加载
layer(x)
 → DecoderLayer.forward → self.norm1(x)
   → RMSNorm.forward(x)                         # nn.Module 规定必须叫 forward，按 impl 选实现
     → rms_norm_op()(x, w, eps)                 # 已加载过，直接返回 torch.ops.ai_infra.rms_norm
       → dispatcher：x 是 CUDA 张量 → forward    # Meta/Fake 张量 → forward_meta；CPU 张量 → 报"没有 CPU 实现"
         → C++ forward(x, w, eps, impl=0)       # TORCH_CHECK → empty_like → data_ptr → 当前 stream
           → launchRMSNorm → 按 n（和行数）分档；对齐且 n % 4 == 0 时用 float4 版→ 启动 kernel

【最早（PYBIND11，已删除）】
ext().forward(x, w, eps) → C++ forward → …
PYBIND11_MODULE 只把 C++ 函数交给 Python，PyTorch 本身不知道它存在，torch.compile 只能切断图。

有三点要注意。第一，张量本来就在 GPU 上，所以不需要 H2D / D2H；但必须用 getCurrentCUDAStream()，这样才能和前后的 PyTorch 运算保持顺序。第二，这个算子只有前向，训练时梯度会断在这里，要支持训练就得另写反向 kernel，并用 autograd.Function 配对，所以它是推理加速。

第三，已知限制：没有同设备检查和 device guard；rows / n 转 int 缺大尺寸检查；只支持 FP32、连续存储。

整层收益

prefill（1 × 512 token）是矩阵 × 矩阵，GPU 一直在忙。RMSNorm 只占约 2%，算子本身快 3.5 倍，整层也只快约 1.5%。这符合 Amdahl 定律：整体加速 = 1 / ((1−p) + p/s)，p 是占比，s 是该部分的加速倍数。占比太小，算子再快也没用。

decode（每次 1 个 token）不一样：它是向量 × 矩阵，每个 kernel 只要几 μs，但 CPU 发射一个 kernel 要几十 μs，所以 GPU 常常在等 CPU。eager 每层比 kernel 合计多约 170 μs，GPU 约 12% 的时间在等。

我们把每层 kernel 从 34 个减到 24 个，不开 nsys 实测 b1 整层快约 10%、b8 约 2%。收益来自少发射，不是 kernel 变快。batch 越大，kernel 越大，GPU 越不空闲，这部分收益就越小。nsys 会放大发射开销，在它下面测得的 −23% / −20% 不能作为结论。

由此可以判断瓶颈：wall 约等于 kernel 合计时，是 GPU 受限；wall 远大于 kernel 合计时，是 CPU 受限。

decode 的 kernel 时间主要花在读权重：205 MB ÷ 约 190 GB/s ≈ 1.08 ms，实测 1.26 ms。cuBLAS 的名字也能看出来：GEMM 是矩阵 × 矩阵，GEMV 是矩阵 × 向量，前缀 s 表示 FP32。

prefill 走 sgemm（计算受限）；decode b1 走 gemv（读权重受限，和 RMSNorm 一样受带宽限制）；b8 走扁矩阵的 sliced sgemm + splitK。这些 kernel 占整层 95% 以上，决定了换 RMSNorm 的收益上限。

减少开销的方法

上面的问题可以分成两类：kernel 之间搬数据太多，以及 CPU 发射太多。"搬运"指的是 GPU 内部显存（DRAM）和 SM 寄存器之间，不是 CPU 和 GPU 之间。kernel 结束时寄存器就清空，下一个 kernel 只能再从显存读。融合把多个运算合成一个 kernel，中间结果留在寄存器里；CUDA Graphs 录下一串 kernel，之后一次重放，省掉 CPU 发射。torch.compile 负责自动做融合。

技术解决什么怎么做
算子融合显存 ↔ 寄存器搬运太多（主要）、kernel 太多多个运算合成一个 kernel，中间结果留在寄存器
CUDA GraphsCPU 发射开销录制一串 kernel，一次 cudaGraphLaunch 重放；地址、形状固定，无 CPU 分支
torch.compile自动融合Dynamo 记录图（带 guard）→ Inductor 融合 → 生成 Triton；不认识的东西会切断图
reduce-overheadcompile 后剩下的发射开销compile + CUDA Graphs

Triton 是比 CUDA 更容易写 kernel 的语言和编译器。Orin（ARM + CUDA 11.4 + Jetson torch）没有可用的 Triton，所以 torch.compile 跑不了，eager 和我们的扩展不受影响。dynamic=False 时形状写成常量，这和我们用模板参数是同一思路，只是我们提前编译好各个档位，它在运行时为每个形状编译一份。

3注册自定义算子

注册进 PyTorch

最早我们用 PYBIND11，它只是把 C++ 函数交给 Python，PyTorch 本身不知道这个算子，torch.compile 只能切断图。后来改成 TORCH_LIBRARY，把它注册进 PyTorch 的算子系统，也就是 dispatcher。

dispatcher 像一个前台：每个张量带着设备标签（CPU / CUDA / Meta），同一个算子可以为每种标签各注册一份实现，调用时按输入的标签选。a + a 在 CPU 和 GPU 上调用的就是两份代码。

PYBIND11_MODULE（最早）TORCH_LIBRARY
注册给谁PythonPyTorch 算子系统（dispatcher）
调用方式ext().forward(x, w, eps)torch.ops.ai_infra.rms_norm(x, w, eps)
本质直接调用一个 C++ 函数先经过 dispatcher，再分派到 CUDA 或 Meta 实现
torch.compile看不懂，切断图图里的正常节点（ONNX 导出也要靠这个注册名）
CPU 张量传进来我们自己的 TORCH_CHECK 报错dispatcher 直接报"没有 CPU 实现"（已测到）
Meta 张量传进来报错调用 forward_meta，返回形状正确的空张量
生产中谁在用练习、小工具vLLM（torch.ops._C.rms_norm）等

注册分三步：① schema 声明名字、参数和返回值；② CUDA 实现，也就是现有的 forward；③ Meta 实现。torch.compile 会用只有形状的假张量走一遍模型，Meta 实现只需要返回形状正确的空张量。

// rmsnorm_ext.cu 末尾
torch::Tensor forward_meta(torch::Tensor x, torch::Tensor weight, double eps, int64_t impl) {
    TORCH_CHECK(weight.dim() == 1 && weight.size(0) == x.size(-1),
                "weight must have shape [n], where n = x.size(-1)");
    return torch::empty_like(x);          // 新张量，不能 return x
}
TORCH_LIBRARY(ai_infra, m) {             // ① 声明：命名空间只能有一个这样的块
    m.def("rms_norm(Tensor x, Tensor weight, float eps, int impl=0) -> Tensor");
    m.def("fused_add_rms_norm(Tensor x, Tensor residual, Tensor weight, float eps) -> (Tensor, Tensor)");
}
TORCH_LIBRARY_IMPL(ai_infra, CUDA, m) {  // ② 输入在 GPU 上：真正启动 kernel
    m.impl("rms_norm", &forward);
    m.impl("fused_add_rms_norm", &fused_forward);
}
TORCH_LIBRARY_IMPL(ai_infra, Meta, m) {  // ③ 输入是 Meta / Fake 张量：只推形状
    m.impl("rms_norm", &forward_meta);
    m.impl("fused_add_rms_norm", &fused_forward_meta);
}

schema 和 C++ 类型有对应关系：float 对应 double，int 对应 int64_t，所以 forward 的参数是 double eps, int64_t impl。int impl=0 是默认值。-> (Tensor, Tensor) 在 C++ 里返回 std::tuple，用 return {h, y}; 构造，Python 拿到 (h, y)。m.impl 的名字必须和 m.def 完全一致。

Meta 实现要和真实实现行为一致。schema 写 -> Tensor 表示返回新张量，所以要 return torch::empty_like(x)。如果直接返回 x，compile 会以为这是原地修改，图和实际运行就不一致了，可能出现隐蔽错误。

Meta 张量的 empty_like 不分配显存。真正原地修改的算子要在 schema 里写 Tensor(a!)，vLLM 的 fused_add_rms_norm 就是这样，我们先做的是返回新张量的版本。

只注册 CUDA 和 Meta 时，CPU 张量在 dispatcher 处就会报错。所以把模型放在 GPU 上导出：torch 2.1 老导出器追踪时真的运行 CUDA 实现；新版 dynamo=True 用 FakeTensor，只需要 Meta。我们也没注册 Autograd，所以不能训练，要支持的话得写反向 kernel，用 torch.library.register_autograd 或 autograd.Function 配对。

torch.ops 是 dispatcher 里所有算子的总目录，aten 是 PyTorch 自带算子的分区（名字来自 C++ 核心库 ATen），ai_infra 是 TORCH_LIBRARY(ai_infra, m) 开的分区。torch.rsqrt(x) 只是 torch.ops.aten.rsqrt(x) 的短名字。C++ 里写 aten::rsqrt、ai_infra::rms_norm，Python 里写点号，指的是同一个东西。

迁移时不是一步切换：先两种接口并存，确认 torch.ops 和原 forward 结果完全一致、Meta 能推形状；再把脚本全部改调 torch.ops；最后删除 PYBIND11，改用 load(..., is_python_module=False)。torch.ops 在 Orin CPU 上每次调用比 pybind 多约 10 μs，整层里 CPU 跑在 GPU 前面时被藏住了。

注册本身和 torch.compile 无关：它用的是核心 dispatcher，Orin 的 torch 2.1 完全支持。Orin 缺的是 Triton。Dynamo 在 Orin 上能用，backend="aot_eager" 或 torch._dynamo.explain 可以检查图有没有被切断。

源码哈希与重编

要解决的问题是：改了 kernel，程序却还在用旧版本，而且不报错。编译 .so 在 Orin 上约 40 秒，所以 load() 不会每次都编译，它只看两样东西有没有变：sources 里列出的文件和编译选项。我们的代码分在三个文件里，load() 不会跟着 #include 往里看：

ext.cu（列在 sources 里）
 └─ #include "../launch.cuh"（没列出）
     └─ #include "kernels.cu"（没列出）

改 ext.cu      → load() 发现变化 → 重编
改 kernels.cu  → load() 没发现   → 继续用旧 .so

load() 看不到 kernels.cu，但看得到编译选项，所以我们自己读这三个文件，算出一个指纹放进选项。哈希把任意内容变成固定长度的字符串：内容相同结果相同，改一点结果几乎一定不同。

_DEPS = [_DIR / "ext.cu", _DIR.parent / "launch.cuh", _DIR.parent / "kernels.cu"]
digest = hashlib.sha1(b"".join(p.read_bytes() for p in _DEPS)).hexdigest()[:12]
load(..., extra_cuda_cflags=["-O2", "-lineinfo", f"-DRMSNORM_SRC_HASH={digest}"])

第一次：哈希 a1b2c3d4e5f6，没有 .so → 编译
第二次：文件没改，哈希不变 → 直接加载
改一行 kernels.cu：哈希变成 9f8e7d6c5b4a → 选项变了 → 重新编译

-D名字=值 相当于 #define，但代码里并不用这个宏，定义它只是为了让编译选项变化。以后新增被 include 的文件时要加进 _DEPS，否则又回到用旧 .so 的问题。CMake 会自动追踪 #include 依赖，所以 plugin 不用这样做。上面表格里的 _DEPS 是改名前的写法，现在是这三个文件。

测试与 NVTX

23 形状 + 160 强制路径 + 5 输入检查是 src/rmsnorm/torch/test.py 的三组测试，都和 float64 的参考结果比。23 个形状测自动分档，让 launchRMSNorm 自己选，覆盖小 n、大 n、边界值、三维张量和空张量。

160 个强制路径是因为自动分档时某个实现可能根本选不到，所以用 impl 强制指定：rows ∈ {1,3,4,5,64} × 10 种 n × 3 种实现 = 150 个，再加 5 种大 n × 2 种实现 = 10 个。

5 个输入检查确保错误输入会报错，而不是算出错的结果：x 在 CPU 上、x 是 float16、weight 长度不对、非连续张量、强制 warp 版但 n > 1024。

NVTX 是 NVIDIA 的打标签工具，在代码里标记"这段时间在做什么"，标签会显示在 nsys 时间线上。nsys 只能看到一堆 kernel，不知道它们属于模型哪一部分，所以 profile_layer.py 打上 norm1、attn 这样的标签，analyze_nsys.py 再归类：kernel → 用 correlationId 找到启动它的 CUDA 调用 → 看这个调用落在哪个 NVTX 范围里 → 算到对应模块。Orin 的 profiler 抓不到 GPU kernel，RMSNorm 占整层约 2% 就是这样统计出来的。

nn.Parameter 与两条编译路径

先看模块怎么定义。下面四行定义了一个 PyTorch 模块，并给它一个能被模型管理的权重：

class RMSNorm(nn.Module):                            # ① 继承 PyTorch 的模块基类，才有 .cuda()、.eval()、state_dict()
    def __init__(self, n):                           # ② RMSNorm(2048) 时运行，相当于 C++ 的构造函数
        super().__init__()                           # ③ 先让基类准备好内部的参数表，不写这行下一行会报错
        self.weight = nn.Parameter(torch.ones(n))    # ④ 创建全 1 的权重并登记成参数

执行 self.weight = ... 时，nn.Module 检查右边的类型，发现是 Parameter，就记进自己的参数表。后面这些功能都会遍历这张表：

操作nn.Parameter普通张量
model.cuda()一起搬到 GPU留在 CPU，运算时可能报设备不一致
model.state_dict()保存和加载不保存
model.parameters()会列出来，优化器能更新不列出
求导默认 requires_grad=True默认不求导

export_onnx.py 里的 layer.load_state_dict(base.state_dict()) 就靠这张表把 eager 模型的权重拷进 ours 模型，两边才完全一致。nn.Linear 内部也用 nn.Parameter。

它计算 y = W @ x，W 的列数要等于输入长度，行数决定输出长度，所以 nn.Linear(2048, 5632) 的 weight 形状是 [5632, 2048]，和参数的顺序相反。这也和 AWQ 笔记对应：W 的一列对应一个输入通道，一行对应一个输出通道。

接着看 rms_norm_op。它不是 aten 算子，而是 decoder_layer.py 里的一个 Python 小函数，作用是确保扩展已加载，然后返回算子：

_op = None
def rms_norm_op():
    global _op
    if _op is None:            # 第一次调用：还没加载
        _op = load_rmsnorm()   # 编译或加载 .so，返回 torch.ops.ai_infra.rms_norm
    return _op                 # 之后直接返回，不再加载

rms_norm_op()(x, self.weight, self.eps)   # 第一个括号拿到算子，第二个括号才运行（走 dispatcher，启动 kernel）
名字是什么
rms_norm_op()我们写的 Python 函数，负责加载并返回算子
torch.ops.ai_infra.rms_norm我们注册的算子，ai_infra 分区
torch.ops.aten.rsqrtPyTorch 自带算子，aten 分区

不直接写 torch.ops.ai_infra.rms_norm，是因为算子要等 .so 加载后才存在，而只用 eager 的人不该为此等编译。__init__ 里也调用一次，就是第九步修的 graph break：加载扩展要读文件、算哈希、调用编译器，Dynamo 看不懂，所以建模型时先加载好，forward 里只是直接返回 _op。

这里还有一个容易想反的顺序：PyTorch 扩展不是"CMake 编译完再调用 Python"，而是先运行 Python，load() 自动完成编译和加载，所以第八步的阶段 A、B 都发生在 Python 进程里。编译结果存在磁盘上，源码和选项没变时下次直接加载（不到 1 秒），变了才重编（Orin 上约 40 秒）。CMake 是另一条路，只负责 plugin。

两条路共用 kernels.cu 和 launch.cuh 的源码，但各自编译出不同的 .so。load() 用 ninja，是因为 .so 必须和当前 PyTorch 的编译参数一致，这些参数由 PyTorch 自己生成，不用我们写 CMakeLists.txt。

排查 graph break

注册之后，graph_breaks.txt 里还是显示 ours 被切成两段。这次排查的思路是：先确定问题在哪一层，再提出假设、验证，最后看实际影响。

  1. 现象：Quest 的 graph_breaks.txt 里 impl=eager: graphs=1 graph_breaks=0 ops=20，impl=ours: graphs=2 graph_breaks=1 ops=14，没有写原因。
  2. 先定层次：graph_breaks.txt 是 torch._dynamo.explain 输出的，explain 只做抓图，不涉及 CUDA Graph；不带 CUDA Graph 的 compile+ours 也是 2 段。所以是 Dynamo 层的问题。
  3. 假设：rms_norm_op() 第一次调用才执行 load_rmsnorm()，里面读文件、算哈希、调 ninja、加载 .so，都不是张量运算，Dynamo 画不进图，只能切断（前面算图 1，这段交给普通 Python，后面重开图 2）。不是"失败"：程序照样跑、结果照样对；真找不到算子会直接报错。
  4. 验证：在 Orin 上（Dynamo 可用，不占 Quest）同一进程里 explain 跑两次：第 1 次（扩展未加载）graphs=2，第 2 次（已加载）graphs=1。Orin torch 2.1 用旧版 explain 调用方式。
  5. 影响范围：compile_layer.py 里第一次用到 ours 的是 explain，它顺带把扩展加载好了；之后计时的 compile+ours 抓图时已经加载，不会切断。所以之前"切断让 compile+ours 更慢、cg 要录两段"的说法不成立，已更正。
  6. 修法：在 RMSNorm.__init__ 里 if impl == "ours": rms_norm_op()，先注册、再 compile、最后调用。新进程第 1 次 explain 就是 graphs=1；Quest 重跑耗时不变。

4生产接入

生产中的接入方式

回到工程上，同一个算子有三条接入路线，取决于上层系统：vLLM、SGLang 这类推理引擎走 eager 加自定义算子；PyTorch 程序走 torch.compile；边缘部署走 ONNX → TensorRT。

路线场景需要做什么
eager + 自定义算子 + CUDA GraphsvLLM、SGLangTORCH_LIBRARY 注册成 torch.ops.xxx
torch.compilePyTorch 训练和推理注册 + 假实现（只推形状），否则 graph break
ONNX → TensorRT边缘部署导出成自定义节点 + TensorRT plugin（已在 Orin 上跑通，见模块 9）

训练和推理一般分开：离线训练、整体替换模型；推荐系统通过参数服务器在线更新；大模型 RL 训练里，推理引擎和训练引擎交替运行并同步权重。
