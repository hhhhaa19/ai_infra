模块 6

性能测量：基线、对照与轮次波动

这一模块讲什么：结果正确后，怎样测量性能、定位瓶颈。先定义测的是什么，再排除干扰，然后看实验结果，最后总结成规则。

1测量方法

确定计时区间

性能数字要先说清楚测的是什么。enqueueV3 只是把任务提交给 GPU，CPU 很快就返回，所以不能只计 CPU 调用耗时。我们用 CUDA event：在 stream 上放两个事件，测它们之间的区间，也就是 GPU 这一段。这段时间可能包含提交不足造成的空隙。

测 kernel 时有两种方式。single 用事件包住一次 kernel 并等待；batch 包住连续 N 次同流 launch，再除以 N。batch 是均摊值，它的 P95 不是单次的 P95，所以两者不能直接比。nearest-rank P95 的取法是：200 个样本排序后取第 190 个（索引 189）。

排除干扰

只测一次的数字不可靠，所以要多层重复，每一层防一种干扰：每个样本连续 N 次前向再除以 N，减少计时点误差；30 个样本取中位数，防止偶发打断；3 轮交替顺序，防止先测的吃亏；3 个独立进程，防止整次运行偏快或偏慢。保留全部轮次，报告稳定区间和异常，不只挑最快值。

还要分清几种状态。重复用同一份输入会享受硬件缓存，构建、启动、稳态耗时要分开报告。Timing Cache 是构建 engine 时的实现计时信息，不是推理结果缓存。

工具读数的误区

GPU-Util 和 occupancy 都不等于有效算力效率。时间线上 cudaStreamSynchronize 的长条表示 CPU 在等 GPU；GPU 上的空档也可能是 GPU 在等 CPU。

nsys 的数据要分开看：kernel 执行时间由 GPU 记录，可信，可以用来算占比；整层墙钟时间被每次发射的拦截开销拉长，不能用来报加速比。所以 nsys 用来找瓶颈，计时用 CUDA event。

下面按时间顺序看实际结果：先是 ResNet-50 部署基线，再到 CUDA benchmark、shared / warp 归约和 RMSNorm。

3工具与规则

四层工具的配合

前面实验用到的工具分别回答不同的问题。一般顺序是：先用 CUDA event 确认差距有多大，再用 nsys 找瓶颈在哪；问题在 kernel 内部时用 ncu 看原因，最后看 SASS 确认编译器到底生成了什么，改完再用 CUDA event 验证。

工具回答什么典型用法不能用来做什么
CUDA event这一段实际要多久比较快慢，算优化百分比解释为什么慢
nsys时间花在哪，CPU 和 GPU 谁在等谁看时间线、每个 kernel 的时间、算占比报整层加速比
ncukernel 内部为什么慢看带宽、stall、cache、活跃线程测实际耗时（默认冷缓存、基础频率，kernel replay 还会打乱 L2）
SASS（机器码）编译器到底生成了什么数 LDG，确认 LDG.E.128、循环有没有展开知道运行时发生了什么

为什么 nsys 不能报整层时间？它要记录每次 CUDA 调用，CPU 每发一个 kernel 都多了拦截开销。kernel 的执行时间由 GPU 记录，不受影响；但 decode 时 GPU 本来就在等 CPU，CPU 一变慢，整层时间就被拉长。

所以 nsys 下 decode b1 / b8 是 −23% / −20%，CUDA event 下是 −10% / −2%：kernel 少了 10 个，每个 kernel 在 nsys 下省得更多，收益就被放大了。

CUDA event 在 stream 上放两个时间点，测的是中间这一整段，不只是 kernel 的执行时间。GPU 在等 CPU 发下一个 kernel 时，空等也算进去。这正是整层测速要的，因为用户感受到的就是这段时间；只想要单个 kernel 自身的时间，就看 nsys 的 kernel 时间。

两类算子的衡量标准

先分类：算子分两类，衡量方法不同。GEMM、卷积受计算限制，看 GFLOPS；RMSNorm、reduction、transpose、softmax、scan 受带宽限制，看 GB/s。分类靠运算强度（arithmetic intensity），单位是 FLOP / Byte：总运算量 ÷ 最少必须搬的字节数。

拿它和硬件自己的比值比。Orin 的算力 5.3 TFLOPS（2048 核 × 每次 FMA 2 FLOP × 1.3 GHz），显存带宽 204.8 GB/s，相除约 26 FLOP/B。比 26 大很多就受计算限制，小很多就受带宽限制，接近 26 两边都要顾。这就是 roofline 的判断方法，详细推导见模块 16。

算子（FP32）运算量最少搬多少字节FLOP / B看什么
GEMM 4096³2·4096³ ≈ 1374 亿读 A、B + 写 C = 3·4096²·4 ≈ 2 亿≈ 683GFLOPS
softmax每个数约 5 次每个数读 4 B + 写 4 B≈ 0.6GB/s
transpose0每个数读 4 B + 写 4 B0GB/s

GFLOPS 是换了单位的速度：总运算量由问题决定，和实现无关；用时才随实现变。4096³ 的 GEMM，naive 约 0.34 s（408 GFLOPS），double buffering 约 0.047 s（2895 GFLOPS）。

用 GFLOPS 而不是秒，好处是能和两个参照比：硬件峰值 5.3 TFLOPS（naive 8%，double buffering 55%），以及 cuBLAS（double buffering 是 cuBLAS 的 85%）。

GB/s 的分子只算一遍：GB/s = 算子最少必须搬的字节数 ÷ 用时。softmax 是读 4n + 写 4n 字节，哪怕 kernel 实际读了三遍，分子也只算一遍，所以多读的浪费会直接体现成 GB/s 变低。参照也有两个：理论带宽 204.8 GB/s 是物理上限；copy kernel（只读一遍、写一遍、什么都不算）是实际能跑到的上限。

超过 copy 的 100% 是什么意思：softmax warp 版 190 GB/s，是理论带宽的 93%、当时 copy 的 108%。这不是突破了物理上限，而是那个 copy 本身没写到最好；copy 加 __restrict__ 以后到了 188 GB/s（见模块 12 ⑤）。所以 copy 也要先写到最快，才能当天花板。

单位：G 是 10⁹，T 是 10¹²，2895 GFLOPS = 2.895 TFLOPS。反过来可以求时间：1.374 × 10¹¹ ÷ 2.895 × 10¹² ≈ 47 ms。内存大小常按 1024 算（GiB = 2³⁰ ≈ 1.074 × 10⁹），带宽一般按 10⁹ 算，两者差约 7%；bench 里的 GB/s 都按 10⁹ 算。

从整体到单个 kernel

实际工作里先看整体：先找到最慢的地方，再优化单个算子。按 Amdahl 定律，一个算子只占总时间的 5%，把它优化到 0，整体也最多快 5%。工具按层次分三层：

第 ② 层看两样东西。一是哪几个 kernel 占的时间最多，只优化前几名。二是 kernel 之间的空隙：GPU 在等 CPU 发下一个 kernel、等同步、等拷贝。空隙多时改 kernel 没用，要减少发射次数：融合（RMSNorm 那次 torch.compile 把 6 个 kernel 融成 1 个），或 CUDA Graph（把一串 kernel 录下来一次发出去）。

profiler 表里的几列：新版 PyTorch 叫 Device time，旧版叫 CUDA time，意思一样。

列意思
Self CPU / CPU totalCPU 花在这个算子上的时间：Python 调用、检查参数、发射 kernel
Self CUDA / CUDA total这个算子发出去的 kernel 在 GPU 上实际运行的时间
Self 与 totalSelf 只算算子自己；total 还包括它内部调用的子算子（如 aten::linear 里的 aten::addmm）

为什么分 CPU 和 CUDA 两列：GPU 是异步执行的，CPU 调 torch.matmul 只是把 kernel 放进队列就返回。用这两列判断瓶颈（下面的数字是示意）：CUDA 时间远大于 CPU 时间（如大 GEMM：CPU 10 µs、CUDA 2 ms），GPU 一直在忙，瓶颈在 kernel 本身，去第 ③ 层看 ncu。

CPU 时间大于等于 CUDA 时间（如小 batch 的 RMSNorm：CPU 20 µs、CUDA 5 µs），GPU 算完就空着等 CPU 发下一个，是 launch 瓶颈；改 kernel 没用，要用 CUDA Graph 或 torch.compile 融合。RMSNorm eager 的 6 个小 kernel 属于这种；SmolVLA 去噪 10 步、每步很多小 kernel，所以考虑用 CUDA Graph。

易错：用 Python 的 time.time() 计时又不先 torch.cuda.synchronize()，测到的只是"发出去"花的时间，会严重偏小。bench 用 cudaEventRecord 在 stream 上打点，测的是 GPU 上的实际时间。

为什么有了 profiler 还要自己计时：计时器负责"测有多快"，profiler 负责"解释为什么"。原因有四个。① profiler 会改变它要测的东西：ncu 把 kernel 重放多遍、默认清 cache、锁频，测的是冷 cache 下单独跑的时间；torch.profiler 和 nsys 的记录开销对几微秒的小 kernel 比例不小。

② 要测的范围不一定是一个 kernel：im2col 版每张图先跑 im2col 再跑 GEMM，关心的是这一整段，包括中间的空隙；event 正好包住一整段，profiler 给的是各个 kernel，相加还会漏掉空隙。③ 可以自动、批量地比：bench 一次跑完多组形状和版本，取中位数、打印 PASS / FAIL，改一行就能重跑。④ 不需要特殊权限：Orin 上的 ncu 要 sudo，计时代码在哪都能跑。

两者要能对得上：ncu 测 conv_igemm_reg 是 531 µs，bench 是 0.530 ms，说明 bench 没测错。对不上时（比如 RMSNorm 的 L2 冷热差别）本身就是一个值得查的信号。

完整流程：端到端计时 → nsys 或 torch.profiler 找出最慢的几个 kernel、看有没有空隙 → 用运算强度判断受计算还是受带宽限制 → ncu 看具体原因 → 决定怎么改：自己写、融合、换库（cuBLAS、cuDNN、TensorRT），或写 TensorRT plugin。面试里"你怎么优化一个模型"答的就是这个流程，手写单个算子只是最后一步里的一种手段。

测量规则总结

每次实验都按这个顺序做。先保证正确，再测性能：用 float64 做参考，输出先写 NaN，再逐元素比对，这样漏写和算错都能发现。测量时 Orin 要锁频，并记录开始和结束频率；比较要在同一次运行内进行，关键结论再用 3 个独立进程确认。

结果出来后算有效带宽和峰值比。超过峰值说明数据还在 L2（Orin 约 3.5 MiB），这类形状要单独列出来。解释时要记住工具条件不同：bench 是热缓存、最高频率；ncu 默认冷缓存、基础频率，kernel replay 还会打乱 L2；nsys 会放大发射开销。最后，静态指令条数不是动态执行次数，加载指令少也不代表读的字节少。

4复习

面试要求

这是区分"做过"和"跑过"的关键模块，面试官很喜欢追问"你怎么测的"。

必须会

  • 先想清楚测的是哪段时间：GPU kernel 时间、含拷贝的请求时间、端到端时间，不能混在一起比。
  • 排除干扰：锁频、预热、多次取中位数、多进程重跑看波动；Jetson 上 jetson_clocks。
  • 四层工具的分工：CUDA event（量多久）→ nsys（时间花在哪）→ ncu（kernel 内部瓶颈）→ SASS（编译器生成了什么）。
  • 至少一次"工具误导"的例子：nsys 会放大 CPU 启动开销（报告的 −20% 实际是 −10%），用不带工具的计时纠正。

应该会

  • ncu 的关键指标：吞吐率（SM / 内存占峰值百分比）、占用率、warp stall 原因（long / short scoreboard、barrier、math pipe throttle）、bank conflict、sector / request。GEMM 里完整用过一遍，见模块 11"为什么变慢"。
  • Roofline：计算强度、拐点，判断访存密集还是计算密集。
  • L2 缓存对测量的影响（数据量小于 L2 时测得偏快；Orin 可用 L2 约 3.5 MiB）。

加分

  • 用 SASS 验证编译器行为（循环有没有展开、有没有生成 LDS.128 / LDG.128）。
  • 统计意义：波动多大时结论才可信、要报几次运行。
