论文

Lina：大模型架构、分布式通信与 MoE

这篇论文讲什么：MoE 模型分布到多张 GPU 后，训练时通信互相抢带宽，推理时部分专家过热。Lina（USENIX ATC 2023）分别解决这两个问题。笔记先补基础，再看论文的方案。已核对关键机制和数字，未复现。

1. 基础：Attention、FFN 和 MoE

Transformer 层里，Attention 负责 token 之间的上下文交互，KV Cache 保存历史的 K / V。FFN 对每个位置做共享参数的变换，不维护这类缓存。残差 x + SubLayer(x) 把增量加回去，也给梯度提供通路。

MoE（专家混合）用多个专家 FFN 替换部分 FFN，由 router 为每个 token 选 Top-k 个专家。专家变多时总参数量增大，但每个 token 只经过少数专家，计算量增长不大。代价是 router、通信、显存和负载不均。

2. 基础：批处理和 KV Cache

单请求 decode 每步 token 很少，专家的矩阵运算规模也小。KV 容量随 batch 和上下文长度近似按 O(B×L) 增长。PagedAttention 用逻辑块到物理块的映射减少浪费。

3. 基础：两种分布式通信

AllReduce：各 rank 做归约，每个 rank 都拿到结果。它常用于数据并行的梯度同步，可以和反向计算重叠，但没被隐藏的部分仍在关键路径上。

All-to-All：每个 rank 向其他 rank 发分片。专家并行用它把 token 发给专家（dispatch），再收回结果（combine）。它通常有直接的数据依赖，下一步计算要等它完成。

4. 训练的问题和 Lina 的办法

分布式 MoE 训练时，AllReduce 和 All-to-All 会抢带宽，而 All-to-All 又卡着下一步计算。Lina 把张量切成 micro-op，在调度边界优先发 All-to-All，再结合流水线和 expert packing。

5. 推理的问题和 Lina 的办法

推理时专家热度不均，少数专家负载很重。Lina 利用跨层的专家选择路径估计热度。阶段一复制热专家、把冷专家装箱到一起；阶段二按真实路由检查偏差，偏差显著时再纠正。复制专家能分担负载，但也要付出额外成本。

分布式 MoE
├─ 训练：AllReduce / All-to-All 带宽竞争
│  └─ 张量分块 → micro-op 优先级调度 + 通信/计算流水线 + expert packing
└─ 推理：专家热度偏斜
   ├─ 阶段一：跨层路径预测 → 热专家复制 / 冷专家装箱
   └─ 阶段二：检查真实路由 → 偏差显著时纠偏

6. 论文结果

实验环境最多 16 张 A100 40GB、100 Gbps IB。训练 step 最多快 1.73×（平均 1.57×）；推理中位延迟改善 1.45×，P95 平均改善 1.63×（新延迟约为旧值的 61%）。这些是论文环境里的结果，不能当作自己项目的加速比。

结论：在 Quest 上 GPU 直连网卡这条路反而比"先拷到 CPU 内存再发"慢，原因还没查清（注意到没有加载 nvidia_peermem，GPUDirect 走的是 DMA-BUF）。对项目的影响：① NCCL 基线改用关掉 GPUDirect 的设置，这是 NCCL 在 Quest 上能跑出的最好成绩，比较才公平；② 服务器内外的实际带宽比从约 22～24 : 1 修正为约 15～17 : 1；③ 作者的 NVSHMEM 版本依赖 GPU 直接发起 RDMA，正好走慢的那条路，在 Quest 上用 NCCL send/recv 按 FAST 的调度一轮一轮发更合适；④ "论文默认 GPUDirect 跑满线速"在实际集群上不一定成立，写进报告的隐含条件。

下一步（已写好、还没结果）：nccl-tests 不能设定流量矩阵，所以写了一个小程序：按模拟器同一套 Zipf 公式生成每对 GPU 之间的数据量（不均衡度 0.5～0.99，另有均匀对照），用两种方式发送——nccl（一次性同时发给所有目标，相当于 alltoallv）和 spreadout（分 7 轮，第 k 轮每张卡只发给"自己编号 + k"），每次都校验收到的数据，并输出最忙那张网卡要发多少数据，用来算理论最优时间。以后加一个 fast 模式就能直接比。

8. 实测：不均衡流量下的 NCCL 基线、PXN 和 FAST 的提升上限

为什么测：nccl-tests 只能测均匀流量，而 FAST 要解决的正是不均匀（热门专家所在 GPU 要收发多得多）。所以自己写测试程序：按 FAST 模拟器同一套 Zipf 公式生成每对 GPU 之间的数据量（不均衡度越高，少数几对 GPU 之间数据越多），用 nccl（所有 send/recv 放在一个 ncclGroup 里一次发完，相当于 alltoallv）和 spreadout（分 7 轮，第 k 轮只发给"自己编号 + k"）两种方式执行，每次都校验收到的数据，并记下"最忙那张卡要跨机发多少"和"每台服务器总共要跨机发多少"，用来算两个时间下限：

  • 最忙网卡下限 = 最忙那张 GPU 的跨机数据量 / 单张网卡带宽：如果每张 GPU 只能用自己的网卡，最少要这么久。
  • FAST 理论最快 = 一台服务器的跨机数据量 / (4 × 20.2 GB/s)：假设服务器内把要发出去的数据完美分给 4 张网卡、每张跑满。没算 NVLink 平衡和调度开销，所以真实 FAST 只会更慢，用它算出的加速比是上限。

第一轮结果（均匀和 Zipf 0.5～0.99 各 3 个矩阵取平均，每卡平均 64 MB / 256 MB，全部校验通过）：

  1. 关掉 GPUDirect 时，NCCL 的用时和"最忙网卡下限"差 0～15%：这时 NCCL 不会把热门 GPU 的数据分给同机其他网卡，正是 FAST 要优化的地方。
  2. spreadout 在所有情况下都比 NCCL 慢约 1.4～2 倍：只分轮发送没有用，FAST 的优势必须来自先在服务器内平衡。
  3. 意外：均匀流量下关 GPUDirect 更快（前一节的结论），但流量不均衡时开着 GPUDirect 的 NCCL 反而更快，而且比"最忙网卡下限"还快。

验证 PXN：猜测原因是 NCCL 的 PXN（PCI × NVLink）——先用 NVLink 把数据转给同机另一张 GPU，再从那张 GPU 的网卡发出去。用 NCCL_DEBUG=INFO 看每条连接的路由，再用 NCCL_PXN_DISABLE=1 关掉对比。日志（GPU 0 发往对面 4 张卡）：

目标默认（GDR + PXN）GDR 开、PXN 关
GPU 4（和 GPU 0 同编号）网卡 0网卡 0
GPU 5NET/IB/1(1)：经 GPU 1 的网卡网卡 0
GPU 6NET/IB/3(2)：经 GPU 2 的网卡网卡 0
GPU 7经 GPU 3 的网卡网卡 0

NET/IB/1(1) 的意思是先经 NVLink 交给 GPU 1、再从它的网卡发。关掉 GPUDirect 时日志里 0 条 PXN：关 GDR 也就关了 PXN。

怎么读这张表：

  1. PXN 有用，且越不均匀越有用：Zipf 0.99 时关掉 PXN 从 24.4 变慢到 28.3 ms（约 14%）。NCCL 默认已经带一个"小号的服务器内平衡"。
  2. 但"低于最忙网卡下限"不全是 PXN 造成的：关 PXN 后 gdr 仍比按 13.7 GB/s 算的下限快（比值约 0.7）。解释：13.7 是均匀流量下所有连接一起抢资源时测的，流量偏斜时最忙那张网卡实际能跑得更快，这个下限定低了——没有单独验证。
  3. FAST 要打败的对手是每种分布下最快的那个 NCCL 设置：均匀时 NCCL 已几乎到理论最快，没有提升空间；越不均匀差距越大，提升上限约 1.5～2 倍。和论文"越不均衡 FAST 越有优势"方向一致。
  4. 写报告要注意：论文里的 NCCL 基线有没有开 PXN，会影响 FAST 的优势有多大，可以放进 critique。

接下来写 FAST：在同一个测试程序里加 fast 模式（作者代码不动，自己按 NCCL send/recv 重写调度）：① 本机所有要跨机发出的数据加起来平均分给 4 张卡，多的卡经 NVLink 交给少的卡，尽量让数据少绕路；② 第 k 张卡只发给对面第 k 张卡，各走各的网卡；③ 到达后如果落在不该收的卡上，再经 NVLink 转交。

正确性检查从每段抽查 3 个字节改成逐字节校验（FAST 会把一段切成几块分开走，抽查可能漏错）；还会记录调度用时和 NVLink 额外搬运量。局限：只有 2 台机器、跨机只有一种配对，所以不需要 BvN 分解（4 台以上要补）；三步依次执行，没有像论文那样切小块流水线重叠，可能比论文的 FAST 慢。结果见第 9 节。

9. 实测：FAST 第一版比 NCCL 慢，问题在实现

设置同第 8 节：每卡平均 256 MB，每种分布 3 个矩阵取平均，单位 ms；每个结果都逐字节校验通过。"最强 NCCL"是每种分布下最快的那个 NCCL 设置（见第 8 节的四种设置）。

流量最强 NCCLFAST 第一版FAST 相对 NCCL 的速度FAST 理论最快
均匀7.612.10.63×7.6
Zipf 0.514.620.60.71×10.1

每卡平均 64 MB 时趋势相同，FAST 是 NCCL 的 0.64～0.81×。

怎么从这张表定位问题：

  1. 先看均匀那一行：均匀流量下每张网卡本来就一样忙，FAST 的"服务器内平衡"什么也不用做，理想情况下应该和 NCCL 一样快（7.6 ms，也等于理论最快）。实测 12.1 ms，多出约 4.5 ms。这部分时间和流量是否均衡无关，只能是实现带来的固定开销，不能说明 FAST 的方法不行。
  2. 再看趋势：越不均衡，FAST 相对 NCCL 越接近（0.63× → 0.82×）。这和"平衡有收益、但被固定开销盖住"一致——这是推测，要等诊断作业把三步拆开计时才能确认。
  3. 已排除的：调度本身平均只算约 5 µs；NVLink 上为平衡多搬的数据也不多。所以开销不在"算调度"和"多搬数据"这两处。
  4. 怀疑的两个原因（待验证）：
    • 跨机那一步切得太碎：一块数据被拆成几小段，分别调用 NCCL 发送，每段都有启动开销；而且一张卡只对一个对端发送时，NCCL 默认只开很少的通道，可能跑不满网卡。
    • 三步完全串行：服务器内平衡 → 跨机 → 到达后转交，前一步做完才开始下一步，NVLink 和网卡不能同时干活。论文里的 FAST 把数据切成小块，让三步流水线重叠。
  5. 诊断方法（结果见第 10 节）：① 三步分别计时，看时间耗在哪一步；② 新加 fastpack 模式，先把要跨机发的数据在 GPU 上打包成一整块、一次发出去，对比"切碎"的影响；③ 给每个对端多开几个通道，看网卡能不能跑满。如果瓶颈是三步串行，下一步就是做流水线。
方法上的要点：新实现比基线慢时，先找一个"新方法理论上不该有任何优势也不该有任何劣势"的输入（这里是均匀流量），在这个输入上的差距就是纯实现开销；把它和方法本身的收益分开，才知道该改实现还是该怀疑方法。

第一步：三步分开计时（256 MB，Zipf 0.99，第一个矩阵，ms）：

第一版 FAST9.522.410.928.3

第一版里，跨机那一步每张卡只对一个对端发送，NCCL 默认只给这对连接开很少几条通道，网卡跑不满；连 NVLink 那两步也慢。改了两处：要跨机发的数据先在 GPU 上打包成一整块再发（fastpack），并设 NCCL_NCHANNELS_PER_NET_PEER=8。第 ② 步快了将近一倍，① ③ 快了 3～4 倍。

第二步：公平比较：FAST 用了"8 条通道"，NCCL 没用，比较不公平。于是让两边都试遍 GPUDirect 开 / 关 × 通道默认 / 8 条，各取自己最快的，216 个结果逐字节正确。256 MB 时 FAST 相对 NCCL：均匀 0.85×、Zipf 0.5 1.15×、0.8 1.35×、0.9 1.44×、0.99 1.58×（64 MB 时 0.83× 和 1.18～1.58×）。

给 NCCL 也开 8 条通道，Zipf 0.99 只从 24.5 降到 24.0 ms，所以 FAST 的优势不是靠这个设置换来的。FAST 离理论最快还差 16～27%：三步一步做完才做下一步，① ③ 的时间（Zipf 0.99 时合计约 5 ms）没有被藏起来。

第三步：流水线。把每段数据切成 C 小块，第 k 块做 ① 的同时，第 k−1 块做 ②、第 k−2 块做 ③，总时间理想情况下接近"跨机传输时间 + 两小块的零头"。正确性先用不整齐的数据量（每卡 3 MB）、切 2 / 4 / 16 块逐字节核对，有错就停。

每种分布 3 个矩阵平均，单位 ms，每个结果逐字节校验。"同一次调用"有 276 个结果、"双队列"有 328 个结果，全部逐字节正确；两个表里 NCCL 和不切块的数字是同一批运行里重测的，和第二步相差不到 1%。流水线两列都取每种分布下最好的切块数。64 MB 时双队列 1.22～1.74×，离理论最快约 14～16%。

  1. 同一次调用为什么只提升一点：三种传输（① ② ③ 的不同小块）放进同一个 ncclGroup 一次发出。判断：NCCL 在一次调用里按固定顺序处理这些传输，NVLink 和网卡并没有真正同时工作；而每多切一块就多一次调用开销，所以切 16 块比 8 块还慢（这个解释没有单独验证，是根据"提升很小、切得越碎越慢"推出来的）。
  2. 双队列怎么做：NVLink 上的工作（机内匀开、到达后分发、本来就在机内的直传）用一个 NCCL communicator，在一个 stream 上跑；跨机传输用另一个 communicator 和另一个 stream。第 k 块用 event 标记先后：第 k 块匀开完才开始传第 k 块，传完才开始分发第 k 块；除此之外两边各跑各的。两个通信组有互相卡死的风险，所以每次运行加了 10 分钟超时，并先用小数据做正确性检查，328 个结果没有卡死。
  3. 结果：256 MB 时双队列只比理论最快慢约 2～3%，基本把网卡跑满；流量越不均匀 FAST 赢得越多（1.33× → 1.96×），和论文的核心结论方向一致。切 4～8 块最好：1 块等于没有流水线，16 块时调用开销又把收益吃掉。
  4. 均匀流量仍慢约 14%：这时没有什么需要平衡，FAST 让每张卡只和对面同位置的卡传，比 NCCL "人人互发"略慢（推测）。论文也承认均匀流量下 FAST 没有优势，可以写进 critique。
  5. 其他：调度计算约 5 µs（论文报告 32 卡约 25 µs），可以忽略。和论文相比提升更小，一部分原因是只有 2 台、8 张卡。4 台 × 2 卡的结果见第 11 节。
这一节的方法：先把总时间拆到每一步，找到真正慢的一步（跨机网卡跑不满）；改完后检查比较是否公平（对手也给同样的设置）；最后才做流水线。流水线要真正重叠，两种硬件上的工作要放在不同的 stream（这里还要不同的 communicator）上，靠 event 只约束必要的先后关系。

11. 实测：4 台 × 每台 2 卡，以及 BvN 到底帮了多少

为什么要做：2 台机器时服务器之间只有一种配对方式，论文最复杂的 BvN 分解没起作用。换成 4 台、每台 2 卡，需要补完整的 BvN：把每台机器之间要传的量汇总成 4×4 矩阵，不够整齐的地方用"空数据"补齐，再拆成若干轮"一对一配对"，每轮每台机器只和另一台传，所有轮的总时间就是理论最短。

对照组是"简单轮流配对"（第 s 轮机器 A 发给 A+s），这样能单独看出 BvN 的贡献。流水线改成支持多轮，NVLink 和网卡仍分两个 communicator / stream。

  3. 实现没问题：离理论最快 2～7%，网卡基本跑满。调度平均约 8 µs，平均拆成 7 轮，最不均匀时 9 轮。

原文也承认开了 PXN 的 NCCL 在轻度不均匀时能接近 FAST，和第 8 节一致。原文 4 台 × 8 张 H200 上是 1.2～1.3×，我们 2 台 × 4 卡是 1.33～1.96×，更高的一个可能原因是 Quest 上 NCCL 默认的 GPUDirect 路径偏慢、对照组更弱，不能说"复现出比原文更大的提升"。

结论（可写进 critique）：FAST 的收益几乎全部来自"机内的卡互相分担"，大小取决于每台有几张卡、各卡流量有多不均；BvN 在我们的流量下只贡献几个百分点；流量均匀时 FAST 比 NCCL 慢，机器越多越明显。拆开机内平衡、分开机器数和每台卡数、小数据三组补充实验见第 12 节。

12. 补充实验：拆开机内平衡、每台卡数、小数据

为什么要做：第 11 节说"收益几乎全来自机内平衡"，但只测了去掉 BvN 那一半；4 台 × 2 卡和 2 台 × 4 卡同时改了机器数和每台卡数，说不清是哪个因素；论文只测 100 MB 以上，推理 decode 每次传的数据小得多。

于是加了一个"不做机内平衡"的版本（每张卡只用自己的网卡发自己的数据，其余照旧：仍用 BvN 分轮、到达后再分发），测了三组：2 台 × 4 卡（去掉机内平衡，外加 1 / 4 / 16 MB 小数据）、4 台 × 2 卡（完整 / 不做机内平衡 / 不做 BvN）、2 台 × 2 卡（完整对比 + 小数据）。每组先用小数据查正确性，结果全部逐字节正确；NCCL 每次都试遍 GDR 开 / 关 × 通道默认 / 8 条取最快。

原文主实验也是 Zipf 模拟流量，所以这一层可以直接对比。按对原文 §5.1.3 / §5.2 的阅读（没有逐句核对）：原文在真实 MoE 预训练中测的不均程度约 0.4～0.8，我们的 0.9、0.99 比真实情况更极端，报告应以 0.5～0.8 的数字为准（2 台 × 4 卡约 1.33～1.6×）；原文接入 Megatron-LM 的端到端训练实验只在 AMD 平台上做，NVIDIA 上没有端到端结果。

我们也没测端到端：通信快了不等于训练整体快同样多。更接近真实的折中是用小 MoE 路由器 + 真实 token 分布生成流量表，目前没做。

要解决的问题：第 12 节的数字来自有 bug 的版本（机内直传被并进第一块的准备步骤，NVLink 和网卡从并行变成先后）。修好这个 bug 后，第 12 节的三组实验（拆开机内平衡、每台卡数 / 机器数、小数据）全部用修复后的版本重跑，结果全部逐字节校验正确。

面试要求

必须会

  • Transformer 的 Attention 和 FFN 各自的计算量和访存特点；MoE 是什么（多个专家 FFN + 路由，每个 token 只激活少数专家）。
  • KV cache：为什么需要、占多少显存（层数 × 2 × 序列长度 × 头数 × 头维度 × 字节数 × batch）。
  • 批处理：静态 batching vs continuous batching。

应该会

  • 两种分布式通信：all-reduce（数据并行 / 张量并行）和 all-to-all（MoE 的专家并行）；为什么 all-to-all 是 MoE 的瓶颈。
  • Lina 在训练和推理上分别解决什么问题（训练时 all-to-all 和 all-reduce 抢带宽 → 调度优先级；推理时专家负载不均 → 动态调度）。

加分

  • 数据并行、张量并行、流水线并行、专家并行的区别和组合。
  • NCCL、NVLink、通信和计算重叠。
  • 多机通信怎么逐层排查带宽（端口速率 → PCIe → 绕开 GPU 测网卡 → GPU 侧设置）；GPUDirect RDMA 是什么、为什么不一定更快（Quest 实测见第 7 节）。
  • 通信流水线怎么真正重叠：同一次 NCCL 调用里放多种传输不一定并行；NVLink 和网卡的工作分到不同 communicator / stream、用 event 衔接（第 10 节）。
  • 复现论文时怎么做消融：把方法拆成几部分分别开关（机内平衡 / BvN），改变论文没改变的条件（每台卡数），并检查对照组是否被削弱（第 11 节）。
