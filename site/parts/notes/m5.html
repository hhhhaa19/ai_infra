模块 5

TensorRT 与 CUDA：构建、执行、数据流

这一模块讲什么：前半部分看 TensorRT 怎么把模型变成执行方案、输入输出怎么进出 GPU；后半部分进入 kernel 内部，从最简单的求和一路讲到 RMSNorm 和硬件映射。TensorRT 负责模型优化和执行，CUDA API 负责显存、拷贝和 stream。

1TensorRT engine

engine 的构建

TensorRT 分两个阶段：先建 engine，之后反复使用。建 engine 时，Builder 创建一个空的 Network，Parser 把 ONNX 的图和权重填进去，Config 提供构建选项。比如 setMemoryPoolLimit(kWORKSPACE, 1ULL<<30) 把临时工作空间上限设为 1 GiB，它只是上限，不会立刻占用 1 GiB。

buildSerializedNetwork 返回的是 IHostMemory，也就是 CPU 内存里的一段字节，还不是能运行的 ICudaEngine。把这段字节写进文件，就是 .engine。

如果输入尺寸会变，还要用 profile 设置 MIN / OPT / MAX：MIN 到 MAX 都能运行，OPT 是重点优化的尺寸，不是唯一允许的尺寸。

engine 的运行

运行时，Runtime 把字节反序列化成 Engine，再由它创建 Context。Engine 是优化好的方案，可以反复使用，所以推理时不用重新解析 ONNX；Context 保存一次运行需要的状态。

接下来数据怎么进去？这里有两个容易混的动作。setTensorAddress 只告诉 Context："这个名字的输入在这个地址"，不搬数据。cudaMemcpyAsync 只负责把字节拷到某个地址，它不知道 Engine 的存在。两者靠同一个地址连起来：拷贝写入地址 A，Context 从地址 A 读。

cudaMalloc 得到地址 A
setTensorAddress("input", A)             // 只登记
同一 stream 上：H2D 写入 A → 推理读取 A → 输出写入 B → D2H 从 B 读回
CPU 最后调用 cudaStreamSynchronize 等待全部完成

同一个 stream 保证这些操作按顺序执行。拷贝如果使用 pageable 内存，驱动可能要先处理；锁页内存（cudaMallocHost / cudaFreeHost）被固定在物理内存里，适合异步传输。它仍然是 CPU 内存，所以还是要拷贝，不是零拷贝。

锁页内存

GPU 读 CPU 内存时靠 DMA：拷贝引擎直接按物理地址读，不经过 CPU 代码。普通 malloc 或 vector 得到的是 pageable 内存，操作系统可以把这些页移走或换出，物理地址不一定稳定，DMA 不能放心地直接读，所以驱动要先处理。典型做法是先拷到自己的 pinned 中转区，具体走中转区还是临时锁页由驱动决定。

pageable：你的 vector → 驱动拷到 pinned 中转区 → DMA 到显存    // 多一步
pinned：  cudaMallocHost 的内存 → DMA 到显存

锁页的目的是让 GPU 能直接、异步地读这块内存，少掉中间这一步。下面是仓库里的两种写法：

【infer_pageable.cpp：普通 vector + 同步拷贝】
float* hostInput = inputHostBuffer.data();
cudaMemcpy(deviceInput.ptr, hostInput, inputBytes, cudaMemcpyHostToDevice);  // CPU 等拷贝完
context->enqueueV3(stream.stream);                                           // 提交推理
cudaStreamSynchronize(stream.stream);                                        // CPU 等推理完
cudaMemcpy(hostOutput, deviceOutput.ptr, outputBytes, cudaMemcpyDeviceToHost);

【infer_async.cpp：pinned + 三步排进同一个 stream】
cudaMallocHost(&inputHostBuffer.ptr, inputBytes);                             // 申请 pinned 内存
cudaMemcpyAsync(deviceInput.ptr, hostInput, inputBytes, cudaMemcpyHostToDevice, stream.stream);
context->enqueueV3(stream.stream);
cudaMemcpyAsync(hostOutput, deviceOutput.ptr, outputBytes, cudaMemcpyDeviceToHost, stream.stream);
cudaStreamSynchronize(stream.stream);                                        // CPU 只在最后等一次

cudaMallocHost 申请的内存要用 cudaFreeHost 释放（HostBuffer 的析构里做），不能用 free。异步拷贝时，cudaStreamSynchronize 返回前 CPU 不能改 hostInput，也不能读 hostOutput，因为 GPU 可能还在用。

A100 ResNet-50、batch=1 的实测：pageable 对 pinned（都同步）中位数约 1.96 对 1.84 ms，低约 6%；pinned 同步对单流异步约 1.84 对 1.83 ms，差异很小。输入只有 602112 字节，所以差距不大。单流异步没有让推理变快，因为 CPU 最后还是要等；它的好处是 CPU 提交后能先做别的事，这个测试里 CPU 没别的事，所以看不出来。

2CUDA 线程模型

线程分工

现在进入 GPU 内部。一次启动写成 kernel<<<blocks, threads, sharedBytes, stream>>>(...)：启动多少个 block、每个 block 多少线程、每个 block 的动态共享内存字节数、提交到哪个 stream。代码里用 extern __shared__ 声明这块共享内存。

线程是编程概念，不是物理核心。线程 32 个一组组成 warp，warp 一起执行指令；block 由 SM 调度。每个线程用下标算出自己负责的元素：

int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) { ... }

例：每个 block 256 线程，blockIdx=1，threadIdx=2 → i = 258

数据量通常不是线程数的整数倍，最后一个 block 的部分线程会超出范围，所以用 if (i < n) 保护。写 threadIdx.x < blockDim.x 没用，因为它永远成立。

线程同步

有时一个线程要读另一个线程写的结果，这就需要同步。__syncthreads() 是 block 内的屏障：所有线程都到达后才一起往下走。所以它不能放在只有部分线程进入的 if 里，否则进入的线程会等不到其他线程。

它只管一个 block。不同 block 要合并结果时，就再启动第二个 kernel，放在同一个 stream 上，它会排在第一个 kernel 后面。

CPU 也可能要等 GPU：cudaStreamSynchronize 等某个 stream，cudaDeviceSynchronize 等当前设备之前提交的工作。写测试时还可以用 cudaMemset(dc, 0xff, bytes) 把输出按字节填成全 1，FP32 下这是 NaN，只要有元素漏写就能发现。

3归约

归约

求和是最基本的例子。最直接的办法是线程把数写进共享内存，再一层层相加，但共享内存读写和屏障都有开销。更好的办法是在 warp 内部用 shuffle：线程之间直接交换寄存器里的值。

下面是 down 版：第 1 轮 lane 0～15 把 lane 16～31 的值加过来；第 2 轮再把范围减半；5 轮后 lane 0 拿到 32 个数的总和。n 不够时，多余的线程用 0 补齐，而不是提前退出，这样 shuffle 才不会少一方。

tid = threadIdx.x; lane = tid % 32; warpId = tid / 32;
value = (fid < n) ? input[fid] : 0.0f;               // 尾部补 0，不提前退出
for (int offset = 16; offset > 0; offset /= 2) {
    float other = __shfl_down_sync(0xffffffff, value, offset);
    if (lane < offset) value += other;
}
if (lane == 0) partial[warpId] = value;               // 用 warpId，不是 lane
__syncthreads();                                      // 跨 warp 合并仍需屏障

shuffle 只在一个 warp 内起作用，线程 31 取不到线程 32，所以每个 warp 的 lane 0 把结果写进 partial[warpId]，等屏障后再合并。这里曾写错成 partial[lane]：每个 warp 的 leader 的 lane 都是 0，会互相覆盖。

整个过程是：256 线程 → 8 个 warp 的部分和 → 1 个 block 的结果 → 多个 block 写到 out[blockIdx.x] → 第二个 kernel 合并。比如 1000 个 1、4 个 block × 256 线程，部分和应为 [256, 256, 256, 232]。

RMSNorm 的一 warp 一行版本用 xor 版。每轮和距离 offset 的线程交换并相加，5 轮后 32 个 lane 都有总和，不用再把结果传给别人：

for (int offset = 16; offset > 0; offset /= 2) sum += __shfl_xor_sync(0xffffffff, sum, offset);

要同步几次：256 线程的 block 求和，用 shared memory 树形规约是 256 → 128 → … → 1，8 轮，每轮一次 __syncthreads()，共 8 次。

先 warp 内 shuffle、再合并 8 个 warp 的结果，只要 1 次：每个 warp 自己规约，lane 0 写 partial[warpId]，同步一次，第 0 个 warp 读这 8 个数再 shuffle 一次。像 RMSNorm 这样所有线程都要用总和的，还要把结果写回 shared 再同步一次，共 2 次。

为什么 warp 内不用同步：关键是"同一个 warp"，不是"同一个 SM"。每个线程有自己的寄存器：编译器给变量分配一个寄存器编号（比如 R5），对一个 warp 来说 R5 是 32 个格子并排、每个 lane 一格。

同一个 warp 的 32 个 lane 执行同一条指令，shuffle 在这一条指令里直接读别的 lane 那一格，不存在"对方还没写完"。不同 warp 的寄存器互相看不见，只能经 shared memory 交换，再用 __syncthreads() 确认写完。

归约用于 RMSNorm

RMSNorm 对每行做一次：先算这一行平方的平均值，得到缩放系数，再乘回每个元素和权重。它不减均值，权重 w 各行共享。

y_i = x_i * rsqrt(Σx²/D + eps) * w_i
x=[3,4]、w=[1,1] → 约 [0.849, 1.131]

启动时写 <<<rows, threads>>>：每行一个 block，threads 是合作处理这一行的线程数，不是列数。所以 <<<4096,128>>> 既能处理 [4096,256]，也能处理 [4096,4096]：线程数不用等于数据量。D=4096、256 线程时，每个线程跨步处理 16 个元素。Nsight 的 Size 字段也看不出 n。

流程分两段：所有线程先合作求和，线程 0 算出 scale 并写入共享内存；__syncthreads() 之后，其他线程才能安全读取它并计算输出。

用 CUB 写时，BlockReduce 在 kernel 内部协作，不会启动新 kernel。Sum 的输入是每个线程的局部和，结果只在线程 0 有效。

4硬件映射

代码到硬件的映射

一个 block 驻留在一个 SM 上。Active Warps 是平均驻留量，不是累计启动数。内存方面，L1 属于 SM，L2 全 GPU 共享，__shared__ 每个 block 一份。

读内存的单位是 32 字节的 sector，它和 32 线程的 warp 只是数字相同，不是一回事。对齐的 32 个 FP32 正好覆盖 4 个 sector（32 × 4 = 128 字节）；起点偏 4 字节，就可能覆盖 5 个。这也是 RMSNorm 优化时行对齐重要的原因。

行为什么会不对齐？矩阵紧密存放时，第 r 行起点是 r × n × 4 字节。n=4096 时起点是 0、16384、32768……都能被 32 整除，每次读 4 个 sector；n=4095 时起点是 0、16380、32760……第 1 行就偏 28 字节，每行偏移还不一样，实测平均每个读请求从 4 个 sector 变成约 4.44 个。

数据量没变，只是多碰了 sector，于是多占带宽。这里的 4 字节是一个 float 的大小，不是 L1 的什么单位，和 L1 大小也没有关系。

起点对齐：  | sector 0 | sector 1 | sector 2 | sector 3 |              读 4 个
            [------------- 128 字节 --------------]
起点偏 4 字节：| sector 0 | sector 1 | sector 2 | sector 3 | sector 4 |  读 5 个
                  [------------- 128 字节 --------------]

padding：n=4095（逻辑长度），stride=4096（实际行距）
每行 [4095 个有效 float][1 个空位]，第 r 行起点 = r × 4096 × 4 字节，始终对齐
rowOffset = blockIdx.x * (stride > 0 ? stride : n);   // rmsNormReg 的 stride 参数

计算时分母仍是逻辑长度 n（4095），不是 stride，所以空位不影响结果。补齐后 sector/请求恢复到 4 个。

Orin 的 CPU 和 GPU 共用一套 LPDDR DRAM，但 host 和 device 缓冲区仍可能是不同分配，cudaMemcpy 仍可能需要。

5复习

面试要求

必须会

  • CUDA 线程层次：grid / block / warp / thread；一个 warp 32 个线程、按 SIMT 执行；warp 分歧（divergence）的代价。
  • 内存层次：寄存器 → shared memory / L1 → L2 → 显存，各自的大小、速度、作用域。
  • __syncthreads() 的作用和使用限制（不能放在只有部分线程能走到的分支里）。
  • 归约（reduction）：shared memory 树形归约 → warp shuffle（__shfl_down_sync）；能当场手写一个 block 内求和。
  • 锁页内存（pinned）为什么快：GPU 能用 DMA 直接读，pageable 内存要驱动先拷一次；异步拷贝必须用 pinned。
  • stream 和异步：拷贝和计算重叠、同一 stream 内按顺序执行。

应该会

  • 合并访存、bank conflict、占用率（寄存器 / shared memory / 线程数怎么限制每个 SM 的 block 数）；GEMM 里的实例见模块 11 ④ 和"为什么变慢"。
  • 把归约用到 RMSNorm：一行一个 block、先求平方和再归约、rsqrt、写回。
  • engine 和 context 的关系；多个 context 共享一个 engine。

加分

  • SM、warp 调度器、SIMT 的硬件对应；Ampere 的 cp.async、Tensor Core。
  • 原子操作的代价和替代方案。
