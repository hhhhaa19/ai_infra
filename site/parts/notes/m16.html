模块 16

FlashAttention：从 roofline 到 FA2 的分工

主线：标准 attention 慢，不是因为算得多，而是因为把 N×N 的中间矩阵反复写进、读出显存。FlashAttention 用分块 + online softmax 把 matmul、softmax、matmul 融合进一个 kernel，N×N 矩阵从不落到 HBM；FA2 数学不变，靠改分工让 GPU 少闲着。这一模块目前全部是讲解，还没有手写或实测。

先会判断：受带宽限制还是受算力限制

FLOP 和 FLOPS：FLOP 是运算次数（计算量，和硬件无关），FLOPS 是每秒能做多少次（硬件速度）。一次乘加 a·b + c 是一条指令，但按 2 FLOP 计，所以矩阵乘是 2MNK。峰值是按周期算出来的：

峰值 FLOPS = SM 数 × 每 SM 每周期 FLOP × 频率
A100 FP16 Tensor Core：108 × 4 个 Tensor Core × 256 次乘加（= 512 FLOP）× 1.41 GHz ≈ 312 TFLOPS
A100 FP32 CUDA Core：19.5 TFLOPS（Tensor Core 快约 16 倍）
Orin FP32：2048 个 CUDA Core × 2 × 1.3 GHz ≈ 5.3 TFLOPS（手写 GEMM 2895 GFLOPS 约 55%）

roofline：算术强度 = FLOPs ÷ 读写 HBM 的字节数；拐点 = 峰值算力 ÷ 峰值带宽（A100 FP16 Tensor Core 约 312 T ÷ 2 TB/s ≈ 156 FLOP/B）。低于拐点受带宽限制，高于拐点受算力限制。拐点要用实际干活的单元算：softmax 在 CUDA Core 上，A100 的拐点约 10、Orin 约 26。近似地 耗时 ≈ max(FLOPs / 峰值算力, 字节 / 带宽)，两个下限谁大谁是瓶颈；实测时看 ncu 的 Compute% 和 Memory%。

操作（FP16，d = 64，N ≫ d）FLOPsHBM 字节强度结论
GEMM 4096³2·4096³3·4096²·2约 1365受算力限制
S = QKᵀ2N²d读 4Nd，写 2N²约 64受带宽限制
softmax(S)每元素约 5读 2N²，写 2N²约 1.25严重受带宽限制
O = PV2N²d读 2N²，写 O约 64受带宽限制

QKᵀ 虽然是矩阵乘，但形状很扁：输出 N×N 很大，累加维只有 d = 64，每个输出只做 64 次乘加却要写一次 HBM。代一组数（N = 4096，d = 64，一个头，A100）：计算 4N²d ≈ 4.3 GFLOP，÷ 312 TFLOPS ≈ 14 μs；朴素实现 S 写读一次、P 写读一次，各 32 MB，约 128 MB ÷ 2 TB/s ≈ 64 μs。搬运比计算多好几倍，而融合后只读 Q、K、V、写 O，各约 0.5 MB，耗时就由计算决定。softmax 单独作为 kernel 怎么优化都受带宽限制（5 FLOP 对 4 字节），唯一的办法是不让它单独成为一个 kernel。

KV cache 和 FlashAttention 不冲突：KV cache 本身就在 HBM 里（7B 模型 4K token 约 2 GB，SRAM 放不下），每次计算还是要读进片上。KV cache 省的是跨 decode 步的重复计算，FlashAttention 省的是一次 attention 之内 S、P 的读写。decode 时 Q 只有 1 行，S 只有 1×N，"不写 S"几乎没收益，真正的开销是把整个 KV cache 读一遍。

FA1：分块 + online softmax，N×N 不进 HBM

把 Q、K、V 切成小块搬进 shared memory，在片上算完 S 的一小块、softmax、乘 V，只把 O 写回。难点是 softmax 要整行的最大值和总和，分块时只看得到一部分——用模块 14 的 online softmax 维护 m（目前最大值）、l（目前指数和）、acc（目前的加权和），新块来了最大值变大就把旧结果按 e^(m_old − m_new) 缩小。结果和一次性计算完全一样（标题里的 Exact）。

一行分数 [1, 3 | 2, 5]，对应 v = [10, 20 | 30, 40]，分两块
第 1 块：m = 3，l = e^−2 + e^0 = 1.135，acc = 0.135×10 + 1×20 = 21.35（不除）
第 2 块：m = 5，α = e^(3−5) = 0.135
        l   = 0.135×1.135 + e^−3 + e^0 = 1.203
        acc = 0.135×21.35 + 0.050×30 + 1×40 = 44.4
最后：  O = acc / l = 36.9      一次性算：权重 [0.015, 0.112, 0.041, 0.831]，O = 36.9 ✓

每来一块 K、V 的三步：① S 块 = Q·K 块ᵀ（Tensor Core）→ ② 用 S 块更新 m、l，算出 P 块（寄存器里）→ ③ acc = α·acc + P 块·V 块（Tensor Core）；全部看完 O = acc / l。online softmax 让融合成为可能，融合让"受带宽限制"消失。额外显存只有 m、l，是 O(N)；反向时只存 m、l，在片上重算 S、P，FLOPs 更多但读写少得多，整体更快——受带宽限制时多算比多搬划算。

FA2：数学不变，让 GPU 少闲着

FA1 只用到 A100 峰值的 25～40%，FA2 到 50～73%，约快 2 倍。浪费在三处，对应三项改动：

  1. 很多 SM 没活干 → 外层改成遍历 Q。FA1 的实现里一个 block 包办一个头，1 句话 × 12 个头只有 12 个 block，A100 的 108 个 SM 有 96 个闲着。FA2 每 128 行 Q 是一个独立的 block：12 × (4096 ÷ 128) = 384 个。外层是 Q 还有一个好处：O 一直留在寄存器里，看完所有 K、V 才写一次；FA1 外层是 K、V，每个 O 块只算了一部分就得存回显存、下一轮再读回（4 块 × 4 轮约 16 次对 4 次）。代价是 K、V 被每个 Q 块读一遍，但它们只读、常在 L2 里。
  2. Tensor Core 在等慢计算 → 最后才除一次 l。max、exp、求和、缩放只能在 CUDA Core 上做，每个 FLOP 慢约 16 倍（exp 还要用 SFU）。按 d = 64 粗算，S 每个元素的矩阵乘约 256 FLOP，非矩阵乘约 5～10 FLOP，后者 FLOPs 只占约 3%，耗时却可能达到前者的 30～60%。FA1 每块都把 O"乘回 l_old、再除以 l_new"，FA2 中间只存不归一化的 acc，整行只除一次。
  3. warp 互相等 → 按 Q 的行分给 warp。FA1 按 key 切（split-K）：每个 warp 只看到 16 列，行最大值、行和、部分 O 都要经 shared memory 交换并同步。FA2 让 4 个 warp 各负责 32 行的全部 64 列，行内归约在 warp 内用 shuffle 完成，算出的就是完整的 O，不用交换。类比：4 个老师批 128 份卷子，按题分要凑总分，按卷子分各自就能算完。

四层分工（d = 64，s = 4096，12 个头）：

层级负责什么数量
block某个头里 128 行 Q 的全部输出；shared 里放当前一块 K、V（各 64×64）12 × 32 = 384
warp这 128 行里的 32 行，S 块 32×64每 block 4 个
线程由 mma.m16n8k16 的格式决定：16×8 的结果块每个线程拿 4 个数（第 t/4 和 t/4+8 行、第 2·(t%4) 和 2·(t%4)+1 列），所以一行由 4 个相邻线程（quad）分着拿每 block 128 个

每个线程做的事：搬 K、V 时搬自己那一份（一块 64×64 FP16 共 8 KB，128 个线程每人约 64 字节，4 次 16 字节的 cp.async），然后 __syncthreads()；S = QKᵀ 和 acc += PV 由整个 warp 一起发 mma；行最大值先在自己的 16 个数里找，再和同一行的另外 3 个线程用 __shfl_xor 合并，行和同理；最后自己的 acc 片段除以 l 写回。"一个线程负责一行"是教学版的简化，真正的 FA2 不是这样。块大小（128 行 Q、64 行 K/V）受寄存器和 shared memory 限制，d = 128 时要更小——和 GEMM 里选 BM、BN、BK 是同一个权衡。

对照 PyTorch 代码

q_proj 是 hidden × hidden 的 GEMM（[4096×768] × [768×768] 约 4.8 GFLOP，强度约 350，受算力限制）；reshape(b, s, heads, d).transpose(1, 2) 只改 shape 和 stride、不搬数据，把 [b, heads] 当成 batch，每个 (b, head) 是一道独立的题，到 kernel 里对应 grid 的一维；输出的 transpose(1,2).reshape 内存不连续，会真拷一次。F.scaled_dot_product_attention 只是入口，背后三个后端：FLASH（要求 fp16 / bf16、head_dim ≤ 256、sm80 及以上，本质是 FA2）、EFFICIENT（可以 fp32）、MATH（朴素版，N×N 写进显存）。fp32 输入用不上 Flash，可以用 with sdpa_kernel(SDPBackend.FLASH_ATTENTION): 强制，不满足条件会直接报错。Orin（sm_87）的 Jetson 版 PyTorch 有没有编进 Flash 后端没确认。

加 KV cache 后的坑：decode 时 q 是 [b, H, 1, d]、k / v 是 [b, H, T, d]，PyTorch 的 is_causal=True 在长度不同时左上角对齐，1 个 query 只能看到第 0 个 key，结果错而且不报错；decode 应该用 is_causal=False，prefill 和 decode 混在一起时传显式 attn_mask。

讲解时用 PyTorch 写了分块参考实现 flash_attn_ref（外层 Q 块、内层 K/V 块、causal 时对角线以上整块跳过、只在对角块上加 mask），说明结构和 kernel 的对应关系；这段代码没有实际运行。朴素版和 Flash 后端的实测对比（s = 1K / 4K / 8K 的耗时和峰值显存）还没做。

之后的版本：每一代消掉当时的瓶颈

版本针对瓶颈做法
FA1（2022）A100N×N 反复进出显存融合 + 分块 + online softmax
FA2（2023）A100非矩阵乘太慢、并行度不够、warp 互等只除一次 l、外层遍历 Q、按行分 warp
FlashDecoding（2023）通用decode 时 Q 只有 1 行，只能派 b × heads 个 block沿 KV 长度切成多段，各段算自己的 m、l、O，最后用同一套合并公式合起来
FA3（2024）H100搬运和计算没同时进行，FP8 没用上TMA 异步搬运 + WGMMA；生产者 / 消费者 warp；两组 warp ping-pong 让矩阵乘和 softmax 交替重叠；FP8（分块缩放、随机正交变换打散异常值）
FA4（2025）B200exp 成了最慢的一环一部分 exp 用多项式在乘加单元上算；最大值只略微变大时先不缩放；用 CuTe DSL 写

规律：每消掉一个瓶颈，下一个就冒出来。讲任何优化都可以按"什么瓶颈 → 怎么判断 → 怎么消掉 → 新瓶颈是什么"来讲。Orin 是 Ampere，和 A100 同代，手写目标是 FA2；FA3 / FA4 了解思路即可。各版本的速度数字按论文转述，没有逐条核对。

LSE：把 online softmax 的 m、l 暴露成接口（读 FlashInfer issue）

问题：一行 attention 被拆成几段分别算（split-KV、FlashDecoding，或者 KV cache 切到多张 GPU 上），每段只看到自己那部分 key，各自得到一个局部输出。怎么把几段合成正确结果？答案就是 online softmax 的合并公式：每段除了输出 O_i，还要交出自己的 m_i（最大值）和 l_i（指数和），通常合成一个数 LSE_i = m_i + log l_i。合并时 LSE = log Σ exp(LSE_i)，O = Σ exp(LSE_i − LSE) · O_i——和模块 14 里两组 (m, d) 合并、FlashDecoding 跨 SM 合并是同一个式子，只是从"跨 block"变成了"跨 GPU"。

实际例子：flashinfer-ai/flashinfer#9592 是一份在 GB300（Grace CPU + Blackwell Ultra GPU，SM103）上做的推理 kernel 差距调研：用 SGLang、vLLM 部署 6 个模型、打真实 agent 流量，按调用次数加权找出 FlashInfer 比其他实现慢的 kernel。其中一项是给 prefill kernel 补 return_lse，因为某个模型用了 DCP8（decode context parallel：一个请求的 KV 切到 8 张卡上各算一段），要靠 LSE 合并。同一张表里的其他术语：ragged prefill（batch 里长短不一的序列首尾相接、不补 padding，每个 block 要知道自己负责哪个序列的哪一段）；MLA（KV 压成一个小向量存）和 sparse MLA（先用轻量 indexer 挑出 top-k 个 token，只对它们做 attention，减少 decode 的读取量）；paged KV；fp8 KV、NVFP4；qk-norm + RoPE 融合（对每个头的 q、k 做 RMSNorm 再加旋转位置编码，和 RMSNorm 融合是同一类逐元素融合）。

这份调研的方法（值得照搬）：用真实负载 profile 而不是随便挑形状、按调用次数加权算收益；固定时钟、用 CUPTI 测设备时间；先和 fp32 参考对比精度再谈速度；先判断是不是真需要新 kernel——有几行的结论是换一个路由或升级版本就行，还有一行写明端到端上限约 0%、优先级低。只在真正有收益的地方写 kernel。以上是对 issue 的阅读整理，没有实验。

面试要求

attention 是推理优化面试里几乎必考的一题，常和 softmax、GEMM 一起问。

必须会

  • 标准 attention 三步的形状、FLOPs 和中间矩阵的显存；为什么朴素实现受带宽限制（用 roofline 算给面试官看）。
  • FlashAttention 的核心：分块 + online softmax + 融合，N×N 不写 HBM；能手算两块的 m、l、acc 更新。
  • KV cache 和 FlashAttention 各省的是什么；decode 为什么受带宽限制。

应该会

  • FA2 相对 FA1 的三项改动，以及各自消掉了哪种浪费。
  • FA2 的 block / warp / 线程分工；mma 片段怎么分到线程、行内归约为什么只在 4 个线程间做。
  • FlashDecoding 为什么要沿 KV 长度切、怎么合并（和 online softmax 合并公式相同）。
  • FLOP / FLOPS、峰值怎么算、一次 FMA 为什么算 2 FLOP。

加分

  • FA3 的 TMA / WGMMA / ping-pong / FP8，FA4 处理 exp 的办法。
  • 反向传播为什么重算比存 P 更快。
  • SDPA 的后端选择条件、decode 时 is_causal 的对齐问题。
