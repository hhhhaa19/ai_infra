模块 1

全流程总览：从模型到 C++ 推理

这一模块讲什么：把一个训练好的 PyTorch 模型放到 C++ 程序里，在 GPU 上跑起来，并证明结果正确。整件事可以看成三条线：先把程序编译出来，再把模型变成 engine，最后加载 engine 执行。下面用 ResNet-50 走一遍。

1三条线

编译 C++ 程序

我们要写的 build_engine 和 infer 是普通的 C++ 程序，它们会用到 TensorRT 和 CUDA 的头文件和库。所以第一步是让编译器能找到这些东西。module load 和环境脚本负责选好工具和路径；CMakeLists.txt 写清楚要编译哪些程序、用哪些源文件、链接哪些库。

接着 cmake -S . -B build 读取这份配置，生成构建规则；cmake --build build 再按规则调用 nvcc、g++ 和链接器，得到可执行程序。这条线只产出程序，还没有碰到模型。

module / 环境脚本 → CMakeLists.txt + 命令行配置 → CMake 生成规则 → 编译链接 → C++ 可执行程序

模型变成 engine

PyTorch 模型是 Python 对象，C++ 程序没法直接用，所以先导出成 ONNX。ONNX 是一个不绑定硬件的模型文件，里面有计算图和权重。导出的同时，我们用 PyTorch 跑一张真实图片，把输入存成 input.bin，把结果存成 output_ref.bin，之后用来检查 C++ 的结果对不对。

然后 build_engine 把 ONNX 编译成 engine。Builder 先创建一个空的 Network 和一份 Config；Parser 解析 ONNX，把图、权重和输入输出描述填进 Network；buildSerializedNetwork 根据 Network 和 Config 做优化，得到一段放在 CPU 内存里的字节（IHostMemory），写进 .engine 文件。

这里容易把两种"构建"混起来：CMake / GCC 构建的是程序，TensorRT Builder 构建的是模型的执行方案。

图片 → 预处理 → input.bin → PyTorch → output_ref.bin
                 模型 → ONNX → ORT 数值验证
Builder 创建 Network 和 Config
ONNX → Parser 解析 → 填充 Network（图、权重、I/O 描述）
Network + Config → buildSerializedNetwork → IHostMemory（CPU 里的序列化字节）→ .engine
初始 engine 130,783,044 B；A100-PCIE-40GB 重建版 129,788,252 B。文件大小不是运行显存。

加载 engine 并执行

infer 程序先把 .engine 读进 CPU 内存，交给 Runtime 反序列化，得到 ICudaEngine。Engine 是建好的执行方案，真正运行还需要一份执行状态和内部工作内存，所以再创建 Context。

接着准备数据。程序用 cudaMalloc 申请输入输出的显存，用 setTensorAddress 告诉 Context 去这些地址读写。这一步只是登记地址，没有搬数据。真正运行时，三件事排进同一个 stream：把输入拷到 GPU（H2D）、执行推理、把输出拷回 CPU（D2H）。最后 CPU 调用 cudaStreamSynchronize 等待完成，再读取结果。

"异步"只表示 CPU 提交后不用立刻等，同一个 stream 里的三步还是按顺序执行，并不是同时运行。

.engine → CPU 字节缓冲区 → Runtime.deserializeCudaEngine → ICudaEngine
        → createExecutionContext → Context（执行状态、内部工作内存）
cudaMalloc 输入/输出 → setTensorAddress 登记地址（不搬数据）
H2D → enqueueV3(stream) → D2H → cudaStreamSynchronize → CPU 读 hostOutput

输入 FP32 [1,3,224,224] 602112 B；输出 FP32 [1,1000] 4000 B
1000 项容差 PASS，Top-1 均为 258。

2验证与衔接

确认结果、衔接算子优化

C++ 输出保存下来后，和 output_ref.bin 逐项比较。1000 个 logits 都在容差内，Top-1 都是 258，说明这张图上 C++ 推理是对的。这只证明单个样本正确，不等于整个数据集都验收通过；基线和对照测量放在模块 6。

那手写算子放在哪？TensorRT 负责组织和优化整个模型，一次 enqueue 背后会提交很多 kernel，自写 kernel 只完成其中一项计算。接入方式可以是 TensorRT plugin，也可以是 PyTorch 自定义算子。框架把 GPU 上的输入输出地址、shape 和 stream 交给我们的代码，kernel 在这个 stream 上运行，结果留在 GPU 给下一个节点用，不用每层都拷回 CPU。

ResNet-50 本身没有 RMSNorm，它只是用来学部署流程。RMSNorm 的收益要放在包含它的模型里看：已在 LLaMA 风格 decoder layer 里测量，见模块 7；TensorRT plugin 的接入见模块 9。

3复习

面试要求

必须会

  • 讲清三条线：编译 C++ 程序（CMake → nvcc / g++ → 链接 TensorRT 库）、把模型变成 engine（PyTorch → ONNX → TensorRT builder）、加载 engine 执行（runtime → deserialize → context → 绑定地址 → enqueue）。
  • ONNX 和 engine 的区别：ONNX 记录"算什么"，engine 决定"在这块 GPU、这个 TensorRT 版本上怎么算"；所以 engine 不能跨 GPU / 版本拷贝，要保留 ONNX 到目标机器上再建。
  • 怎么确认结果对：和 PyTorch 输出逐元素比（ResNet-50 的 1000 个 logits 都在容差内，Top-1 一致）。

应该会

  • 每一步出错时的典型现象和排查思路（找不到库、ONNX 解析失败、不支持的算子、输出全 0 / NaN）。
  • 建 engine 时 TensorRT 做了什么：层融合、精度选择、对每层实测挑 kernel（tactic）。

加分

  • 动态形状（optimization profile）、多 engine / 多 stream 部署。

高频问题并在下面的自测里。三档的含义见复习笔记顶部说明。
