核心算子

RMSNorm：从一个 kernel 到整层追平编译器

主线：RMSNorm 是 LLaMA 每层都有的归一化。每行先求平方和（一次规约），再逐元素缩放，计算很少、读写很多，是带宽问题，目标是 x 只读一次、y 只写一次。优化分两段：先把单个 kernel 写快（①～④，瓶颈在 kernel 内部），再把它放进真实推理路径（⑤～⑪，瓶颈依次变成 Amdahl 和 CPU 发射、和编译器的融合边界、真实形状、TensorRT 挑的矩阵乘 kernel）。

y[r][i] = x[r][i] · rsqrt( (1/n)·Σj x[r][j]² + ε ) · w[i]

公式、瓶颈与 kernel 骨架

为什么要手写：PyTorch eager 写法要启动 6 个 kernel，每个单独看都接近带宽上限，但中间结果来回写显存。Orin 上 [4096, 4096] 总共搬了 448 MiB、用 2887 μs，而 x 读一次、y 写一次只需要 128 MiB。手写一个 kernel 的目标就是只搬这 128 MiB。

和 LayerNorm 的区别：RMSNorm 不减均值、没有 bias，只要一次规约（平方和）；LayerNorm 要均值和方差两样。

骨架：下面每个版本都是这四步，区别只在"一行交给多少线程、每个线程拿几个数、怎么规约"。

row = …;  tid = …;  if (row >= rows) return;          // 1. 定位：哪一行、行内第几号线程
#pragma unroll
for (i = 0; i < PER; i++) {                              // 2. 读取：存进寄存器，同时累加平方
    idx = i * 线程数 + tid;
    v[i] = idx < n ? x[rowOffset + idx] : 0;
    sum += v[i] * v[i];
}
sum = 规约(sum);                                          // 3. warp 版 xor 5 轮；block 版 warp 内 + shared memory
scale = rsqrtf(sum / n + eps);                           // 4. 除以 n，不是线程数
for (…) if (idx < n) y[rowOffset + idx] = v[i] * scale * w[idx];
检查五件事：下标用 size_t；读时越界补 0、写时越界跳过；规约后谁拿到结果（down 只有 lane 0，xor 全部 lane）；除数是 n；cuobjdump 确认 LOCAL 为 0。

2单个 kernel 的优化

① own：一个 block 一行

做法：一个 block 负责一行，线程跨步循环读这一行，先在 warp 内用 5 轮 __shfl_down_sync 合并，每个 warp 的 lane 0 把部分和写进 shared memory，再合并成一个数。

正确性：和 float64 参考逐元素比较，输出先填 NaN 查漏写，15 组形状全部 PASS（最大误差 2.38e-7）。

问题：和 CUB 的 BlockReduce 版对比，128 × 4096 上 CUB 快 15～36%。

规约为什么用 warp shuffle：规约要让线程之间传数据，最慢的是全部经过 shared memory。能在寄存器里合并就不进 shared，能少一次屏障就少一次：

写法线程怎么合并256 线程时的屏障数代价和效果
shared 规约全部数写进 shared memory，一层层两两相加9每层都要读写 shared，而且每层一个屏障
warp shuffle + sharedwarp 内用 5 轮 __shfl_down_sync 在寄存器里合并，只有 warp leader 把部分和写进 shared，再合并 8 个部分和4A100 四轮中位数：100 万元素 16.527 → 13.394 μs（−18.96%），1600 万元素 131.092 → 99.471 μs（−24.12%）
warp-per-row一行只用 1 个 warp，5 轮 __shfl_xor_sync 后 32 个线程都有总和0没有 shared，也没有屏障；一行元素要放得进这个 warp，所以用于 n ≤ 256

这张表的耗时来自单独的规约练习，不是 RMSNorm 的整体提速；own → own_t → own_reg 的主要收益来自读请求和展开，不是规约。

② own_t：编译期线程数

怎么查：先猜"CUB 让更多 warp 处于就绪状态"，ncu 显示 CUB 的 eligible warp 反而更低，猜测被推翻。再看 SASS：own 只有 3 条 LDG，CUB 有 39～105 条。

原因：CUB 的线程数是模板参数，编译器知道循环次数，能把循环展开，一次发出很多个读请求，等待只付一次；own 的线程数是运行时值，循环展不开，每次只有一个读请求在路上。

改法：把 own 的线程数也改成模板参数（own_t），和 CUB 差距缩到 4% 以内，说明差别和 BlockReduce 本身无关。

结论：带宽受限的 kernel 要让足够多的读请求同时在路上；高占用率、高发射率本身不是目标。

③ own_reg：x 存寄存器

问题：n 除不尽时 own_t 变慢。ncu 显示两个原因。

  1. 零头分支：展开后最后一段只有部分线程有数，最后一个 warp 分叉，其他 warp 在 __syncthreads() 等它：barrier stall 约 7 倍，活跃线程 31.6 → 27.7。
  2. 行不对齐：n 不是 32 的倍数时，行起点不在 32 字节 sector 边界上，每个读请求平均从 4 个 sector 变成约 4.44 个。padding（行跨度补到对齐，计算仍除以逻辑长度 n）后恢复到 4 个。

改法：每个线程固定处理 PER_THREAD 个元素（模板参数），循环完全展开，越界用 col < n 屏蔽，不再有零头分支；读进来的 x 存在寄存器 v[PER_THREAD] 里，算完 scale 直接用，x 只读一遍。

结果：18 个配置里 15 个最快，比 own 快 15～33%。cuobjdump 确认 LOCAL:0（数组没有掉进 local memory）。

易错：数组下标必须是编译期能确定的（固定次数循环 + #pragma unroll），否则 v[] 会被放进 local memory，比寄存器慢很多。

④ 按 n 分档

问题：n 很小时一个 block 一行会闲置大部分线程，还要付 shared memory 和屏障的代价；n 很大时寄存器放不下。一个 kernel 管不了所有 n。

n 的范围一行交给谁规约模板参数为什么
n ≤ 2561 个 warp（每 block 4 个）__shfl_xor_sync 5 轮PER_LANE ∈ {1,2,4,8,9,16,17,32}行短时整个 block 会闲置；不需要 shared memory 和 barrier，可以提前 return
≤ 337921 个 block（128～1024 线程）warp shuffle → shared memoryBLOCK, PER_THREAD ∈ {1,2,4,8,9,16,17,32,33}x 存寄存器，只读一次；n % 4 == 0 且对齐时换成 float4 版（VPT = PER_THREAD / 4 ∈ {1,2,3,4,5,8,9}，n ≤ 36864）
更大1 个 block（512 线程），循环同上BLOCK = 512寄存器放不下，读 x 两遍

参数怎么定：

  • BLOCK（按行数分档之前）：128～1024 中满足 BLOCK × 16 ≥ n 的最小 2 的幂。分档后改为 BLOCK × per ≥ n，per 看行数：行数 < 2 × SM 数（A100 216 行、Orin 32 行）时 per = 4，否则 8。n=2048 时 decode（1、8 行）用 512×4，prefill（512 行）用 256×8。sms 用 static 变量只查一次 multiProcessorCount。rms_norm 和 fused_add_rms_norm 共用这条规则。
  • PER_THREAD：档位里第一个 ≥ ⌈n / BLOCK⌉ 的值。
  • 9、17、33：接住比 2 的幂略大的 n，比如 n=4100 每线程 17 个，没有这一档就得用 32。
  • 每 block 4 个 warp：Orin 每 SM 最多 16 个 block，4 × 16 = 64 ≥ 48 个 warp 才能占满。

边界从哪来：

  • 256：扫描实测。warp / own_reg 时间比 n=224 时 0.97、256 时 1.02、320 时 1.08；rows=16384、n=32 时 warp 版快 3.6 倍。
  • 33792 = 1024 × 33：最大一档是人为的预编译容量选择，不是硬件上限；所有 own_reg 实例 ≤ 48 个寄存器、LOCAL:0。
  • switch 加宏把运行时的 n 映射到编译好的模板实例。

易错：一个 warp 一行最多能放下 n = 1024（每个 lane 32 个数），但"能放下"不等于"更快"。实测 n ≥ 320 时 own_reg 更快，所以阈值是 256，不是最初猜的 1024。

测量陷阱：L2 容量悬崖

现象：有一次 n = 3840 比 n = 4096 快一倍。

原因：工作集小于约 3.5 MiB 时，数据在两次计时之间留在 L2 里，有效带宽 240～253 GB/s，超过了显存峰值 204.8 GB/s。那次只是恰好在 L2 里，不是 kernel 更快。

做法：带宽类 kernel 用远大于 L2 的数据量测；ncu 的 kernel replay 会打乱 L2，不能用来看"热缓存"下的表现。

3接入 PyTorch 与 torch.compile

⑤ PyTorch 扩展

做法：写成 CUDA 扩展。TORCH_CHECK 检查设备、dtype、形状、连续；empty_like 分配输出；在 PyTorch 的当前 stream 上启动 kernel（否则和前后的 PyTorch 操作没有顺序保证）；load() 编译时把被 include 的 kernel 文件哈希加进编译选项，改了 kernel 才会重编。

测试：23 个形状、160 个强制走某条路径的用例、5 个非法输入检查，全部通过。

结果：Orin 上 4096 × 8192 是 1396 μs，比 eager 快 4.1 倍，约 192 GB/s（峰值的 94%）。A100 上和 torch.compile 生成的 Triton kernel 打平：Inductor 在 n ≤ 1024 时用 persistent reduction（一行整个放进一个 block），n ≥ 4096 时用循环规约（读两遍，第二遍靠 L2）。

⑥ 整层收益与 Amdahl

做法：写一个 LLaMA 风格的单层（hidden 2048），RMSNorm 可以切换成 eager / ours，用 NVTX 标记各模块，nsys 按模块统计 kernel 时间，再不开工具用 CUDA event 计时。

结果：RMSNorm 只占整层约 2%。prefill 整层快 1.5%（按 Amdahl 预测 1.4%）；decode batch 1 快 10%、batch 8 快 2%。

为什么 decode 收益大：decode 每次只算 1 个 token，GPU 很快就算完，时间有一部分花在等 CPU 发 kernel 上。每个 eager RMSNorm 是 6 个 kernel，换成 1 个，每层少发 10 个 kernel，每个约 15 μs 的 CPU 开销。batch 越大 GPU 越忙，这部分占比越小。

易错：一开始在 nsys 下测到 decode 快 20%，不开工具复测只有 10%。nsys 会放大每次发 kernel 的开销，结论要用不带工具的计时确认。

⑦ TORCH_LIBRARY 与融合边界

为什么要注册：pybind 只是把 C++ 函数交给 Python，PyTorch 不知道这个算子，compile 遇到它只能切断图。用 TORCH_LIBRARY 注册成 torch.ops.ai_infra.rms_norm，提供 schema、CUDA 实现和 Meta 实现（只推形状，compile 抓图时用）。

compile 怎么处理它：

  1. Dynamo：抓 FX 图。算子不实际运行，走 Meta 实现推形状。
  2. AOTAutograd：把 PyTorch 写法转成 aten 层的 FX 图，算子已经是注册过的节点，不会被拆开。
  3. Inductor：融合其他算子，生成 Triton kernel，矩阵乘交给 cuBLAS。我们的算子是黑盒，只能在它前后融合。
  4. 运行：生成的 Python 文件按顺序调用各个 kernel，走到这个节点时调用我们的算子，经 dispatcher 进入 CUDA 实现。reduce-overhead 时再录 CUDA Graph。

结果：A100 整层 decode b1，eager+ours −29%，compile −30%，但 compile+ours 只有 −23%，比只用 compile 还慢。读 inductor_cache 生成的代码发现，Inductor 会把"残差相加 + norm2"融成一个 kernel；我们的算子是黑盒，这次融合做不了，kernel 从 14 个变成 15 个。

易错：explain 报过一次 graph break，原因是扩展在 forward 里第一次调用时才加载。改成在 __init__ 里加载（先注册、再 compile、最后调用）后切断消失，但计时不变，变慢的真正原因是少了一次融合。

⑧ fused add + RMSNorm

做法：h = x + residual 只写一次，归一化直接用寄存器里的值，不再从显存读回 h。

// 和 rmsNormReg 只差第一个循环；h = x + r 只写一次，归一化直接用寄存器里的 v[i]
for (int i = 0; i < PER_THREAD; ++i) {
    int col = xid + i * BLOCK;
    v[i] = col < n ? x[rowOffset + col] + r[rowOffset + col] : 0.0f;   // 读：越界给寄存器 0，不读内存
    if (col < n) h[rowOffset + col] = v[i];                             // 写：越界必须跳过
    sum += v[i] * v[i];
}
// 之后 warp 内规约 → shared 规约 → scale → y[rowOffset + col] = v[i] * scale * w[col]，和 rmsNormReg 完全一样
  • 接口：fused_add_rms_norm(Tensor x, Tensor residual, Tensor weight, float eps) -> (Tensor, Tensor)，返回新张量 h、y（不原地，Meta 只要两个 empty_like）。检查三个张量 CUDA / float32 / 连续，residual.sizes() == x.sizes()，weight 是 [n]。只支持 n ≤ 33792（1024 × 33），没有循环版后路；对 LLaMA-3-405B 的 16384 也够。
  • 接进层里：a = attn(norm1(x)); h, n = fused_add_rms_norm(a, x, norm2.weight, norm2.eps); return h + mlp(n)。kernel 参数叫 x 的传的是 attn 输出、叫 r 的是原输入（加法顺序无所谓）。norm2 模块保留只为参数结构一致，load_state_dict 能直接加载同一组权重。
  • 为什么"残差最后加"也能融合：LLaMA 是 pre-norm，注意力子块最后的 h = x + a 和 MLP 子块开头的 norm2(h) 时间上紧挨着；MLP 最后的 out = h + m 后面接的是下一层的 norm1，多层叠起来也能融合（vLLM 把 residual 在层间传下去）。单层里 norm1 和最后那个 add 暂时没融合。
  • 自己写 TODO 时踩的坑：x[...] + r 加的是指针；h = … 是改指针变量本身，要写 h[下标]；if (h = col < n) 把 bool 赋给指针；h = v[rowOffset+col] 下标放反——h 是显存里所有行（下标 rowOffset + col），v 是这个线程自己的 PER_THREAD 个寄存器（下标 i）。条件里只放判断，赋值放在后面。

结果：kernel 数追平（14 对 14），eager+fused 334.6 μs 已接近 compile 的 332.0 μs；但 compile+fused 是 362.9 μs，GPU kernel 时间还多 26 μs。kernel 数一样以后，比的是 kernel 本身。

⑨ 按行数分档

怎么查：Inductor 生成的 kernel 用 num_warps=16，每行 512 个线程。单 kernel 扫描（CUDA Graph 重放计时，n = 2048）：1 行时 128 × 16 在所有切法里最慢（升频前测得 8.25 μs，预热后复测 4.52 μs），Triton 3.24 μs；512 行时 256 × 8 最好。

原因：之前的分档只看 n，是按几千行调的，那时 GPU 上有很多 block，追求吞吐。decode 只有 1～8 行，GPU 上只有几个 block，看的是延迟：每行要更多线程，每个线程少拿几个数。

改法：chooseBlock(n, rows)：行数 < 2 × SM 数（A100 216 行、Orin 32 行）时每线程 4 个元素，否则 8 个。rms_norm 和 fused 版共用这条规则。

结果：整层 GPU 差距 26 → 5 μs，CUDA Graph 下 b1 只差 2.4%、b8 差 1.0%。

这条规则是按 A100 的数据定的，Orin 上还没复测。

⑩ float4 向量化

怎么查：Triton 生成代码里有 tt.divisibility 16，说明它知道地址 16 字节对齐，用的是 128 位读取。

改法：n % 4 == 0 且指针 16 字节对齐时用 LDG.E.128 一次读 4 个 float，否则退回标量版。指令少了，等待的轮数也少。

结果：1 行 norm 2.28 μs（Triton 3.25），add + norm 4.43 μs（Triton 2.71）。整层 GPU kernel 时间 278.0 vs Inductor 276.4 μs；CUDA Graph 下 decode b1 只慢 0.6%，b8 打平。

易错：计时前要先让 GPU 升频（预热）。有一次扫描在升频前测，1 行 128 × 16 测成了 8.25 μs，预热后实为 4.52 μs。

5复习

易错与被推翻的猜测

  • "CUB 让更多 warp 就绪"：ncu 显示 CUB 的 eligible 反而更低。
  • "256 线程不受零头影响"：错，只是 rows=512 时被"不对齐反而更快"抵消。
  • "行间距是 2 的幂导致冲突"：错，4128 和 4096 一样快。
  • "n=3840 比 4096 快一倍"：那次运行数据恰好在 L2 里。
  • "kernel replay 的 ncu 能看热缓存"：不能，它会打乱 L2。
  • "warp 版到 1024 都更快"：320 起就更慢。
  • "graph break 让 compile+ours 变慢、cg 要录两段"：切断只发生在脚本里第一次 explain，修好后耗时不变，变慢只因少了一次融合。
  • "Inductor 的融合 kernel 写出 h"：读生成代码后发现它不写 h，最后用 x + attn + mlp 重算。
  • "128×16 对所有行数都合适"：只在很多行时对；1 行时它在所有切法里最慢。
  • "warp 版能救 1 行的情况"：方向反了，warp 版每行只有 32 线程，适合 n 小、行多。
  • "1 行 128×16 norm 要 8.25 μs"：那组是在 GPU 升频前测的，预热后实为 4.52 μs。
  • "插入 plugin 后 b8 快一倍是因为我们的 norm 快"：逐层看，norm 只差 1 μs 左右，快的是被切出 Myelin 的 MLP 矩阵乘。
  • "engine 显示 1 层就是 1 个 kernel"：ForeignNode 内部仍启动很多个 kernel，要用 nsys 看。

常见说错的地方：

  • 公式漏了平方根倒数：是 x · rsqrt(Σx²/n + eps) · w，不是 (Σx²/n + eps) · x · w。
  • padding 和 L1 无关：它让每行从对齐地址开始，读请求从约 4.44 个 sector 回到 4 个。
  • AOTAutograd 产出的是 aten 层的 FX 图，还是 PyTorch 算子；CUDA / Triton kernel 是之后 Inductor 生成的。
  • torch.compile 和导出 ONNX 是两条路，导出不是 compile 的下一步。
  • TensorRT 没有 schema 和 Meta，对应的是 ONNX 节点 + creator 和 getOutputDimensions。

未解决的问题

  • 不用 CUDA Graph 时 compile+fused 比 compile 多约 30 μs CPU 时间，是不是 torch.ops 调用路径（待测）。
  • float4 之后，1 行 add+norm 仍比 Triton 慢 1.7 μs（4.43 vs 2.71），而 1 行 norm 我们更快：候选是 warp 间规约改成只同步 1 次，未验证。
  • 单 kernel 扫描差 14 μs，整层里差 26 μs，多出来的部分从哪来（推测是缓存状态）。
  • 按 A100 数据定的行数规则，在 Orin 上很多行时（变成 256×8）是快是慢，需要锁频后测。
  • TensorRT FP32 + 禁 TF32 时，Myelin 为什么在 b8 给矩阵乘挑了 sliced1x4 sgemm（每个 2.4 ms，PyTorch 整层才 1.8 ms）。开 FP16 后换成 h16816gemm 系列，b8 2.44 ms，但仍慢于 PyTorch FP32 的 1.80 ms（不同时间测的）；开 TF32 没测。
  • ours engine 里 norm1 16.5 μs、norm2 只要 5.9 μs，差在哪（未查）。
  • 不对齐为什么让 own_t / cub 在 rows=512、256 / 512 线程时更快。
  • own_reg 128 线程为什么把对齐代价放大到约 27%，256 / 512 线程只有约 2%。
  • n=3840 的 L2 悬崖更早、更不稳定（猜测组冲突或物理页分配）。
  • warp 版在 n 较大时变慢（候选：每线程 56 个寄存器）。

面试追问

kernelRMSNorm 和 LayerNorm 有什么区别？

RMSNorm 不减均值、没有 bias，只用均方根缩放，只需一次规约（平方和）；LayerNorm 要算均值和方差。计算更少，在 LLM 里效果接近，所以 LLaMA 等模型都用它。

kernel为什么说它受带宽限制？理论上限怎么算？

每个元素只做几次乘加，却要读 4 字节、写 4 字节。理论最短时间 = 必须搬的字节数 ÷ 带宽。rows=4096、n=8192 时 x+y 共 256 MiB ≈ 268 MB，÷ 204.8 GB/s ≈ 1.31 ms；实测 1.396 ms，约峰值的 94%（有效字节口径，不含权重读取）。

kernelCUB 为什么比你最初的版本快？

不是因为 BlockReduce。CUB 的线程数是模板参数，编译器能展开循环、一次发多个读请求、指令更少；SASS 里 own 3 条 LDG，CUB 39～105 条。把自己的线程数也改成模板参数（own_t）后速度一致。结论限定在已测配置。

kerneln 除不尽时为什么变慢？怎么解决？

展开后的零头分段让最后一个 warp 分叉，其他 warp 在 __syncthreads() 等：barrier stall 约 7 倍，活跃线程 31.6 → 27.7。另外 n 不是 32 的倍数时行起点不对齐，sector / 请求从 4 变 4.44。own_reg 每线程固定元素数、用 col < n 屏蔽，没有零头分支；padding 解决对齐。

kernel为什么把 x 存在寄存器里？有什么风险？

求平方和读一遍、算输出又读一遍；存寄存器就只读一次。风险是寄存器不够溢出到 local memory（实际在显存）反而更慢，寄存器多也降低 occupancy。所以 PER_THREAD 有上限，并用 cuobjdump 确认 LOCAL:0。

kernelshfl_down 和 shfl_xor 有什么区别？

down 规约完只有 lane 0 有总和，要再广播；xor 是蝶形交换，5 轮后 32 个 lane 都有总和，每个 lane 可以直接算 scale 写自己的输出。

kernel为什么要按 n 分档？阈值怎么定的？

n 小用整个 block 会闲置线程并付 shared memory 和 barrier 的代价；n 大要更多线程才读得快；寄存器放不下只能循环。阈值靠扫描：强制两种实现，rows 4096 / 16384，n 从 32 扫到 384，找时间比交叉点，结果定为 256。

硬件warp 版为什么每个 block 放 4 个 warp？

Orin 每 SM 最多 16 个 block、48 个 warp。每 block 1 个 warp 最多 16 个 warp，占用率只有三分之一；4 个 warp 时 16 个 block 就有 64 个，能填满 48 个。

硬件occupancy 由什么决定？

每 SM 能驻留的 block 数取最小值：硬件 block 上限（Orin 16、A100 32）；SM 线程上限 ÷ 每 block 线程数；65536 寄存器 ÷ 每 block 寄存器（按分配粒度）；shared memory ÷ 每 block 用量。occupancy 高不一定更快。

硬件为什么有些形状的有效带宽超过显存峰值？

数据留在了 L2。连续运行时 x+y 小于 L2（Orin 实际约 3.5 MiB，A100 40 MB），下一次直接从 L2 读。这类形状不能用来评价 kernel。A100 的大 L2 也让"读两遍"代价很小，所以 own_reg 只读一次的优势在那里体现不出来。

PyTorch怎么把 CUDA kernel 接进 PyTorch？
  • TORCH_CHECK：GPU、float32、weight 形状 [n]、连续；
  • empty_like 分配输出，data_ptr 取指针；
  • 在 getCurrentCUDAStream() 上启动，保证顺序；
  • C10_CUDA_KERNEL_LAUNCH_CHECK 检查启动错误；
  • 导出：最初用 PYBIND11，后来改为 TORCH_LIBRARY 注册 CUDA + Meta 实现，调用 torch.ops.ai_infra.rms_norm；load() 只看列出的源文件，所以把被 include 的 kernel 文件哈希加进编译选项。
PyTorcheager 写法为什么慢？4 倍从哪来？

6 个 kernel 单独看都接近带宽上限，但中间结果都要写回显存再读出，总搬运 448 MiB 对 128 MiB；广播乘法没向量化；小形状还要付 6 次调用开销。4 倍主要来自融合，和 kernel 内部优化（own → own_reg）要分开说。

PyTorchtorch.compile 生成的 kernel 是什么样的？

Dynamo 记录图，Inductor 融合后生成 Triton。n ≤ 1024：persistent reduction，一个 program 处理 XBLOCK 行，整行进寄存器，tl.sum 规约，思路同 own_reg。n ≥ 4096：循环规约，第一遍带 evict_last 求平方和，第二遍再读 x。A100 上和我们打平。

PyTorch有了 torch.compile 还需要手写 kernel 吗？

简单融合编译器已能做到同样水平，整层编译时还能把残差加法和下一个 norm 融合。实测：只替换 RMSNorm，compile 下反而慢（decode b1 341 → 378 μs）；写了 fused add + RMSNorm 并按行数分档后，CUDA Graph 下只差 2.4%。

所以只做单个算子赢不了编译器的融合，要按真实数据流设计融合边界、按真实形状分档。手写的价值在：没有 Triton 的平台（Orin 的 torch 2.1，eager+fused 已接近 compile）、eager + CUDA Graph 的推理引擎（vLLM 式）、TensorRT plugin、编译器做不好的复杂算子（FlashAttention、量化 GEMM）。

PyTorch自定义算子直接放进 torch.compile 会怎样？怎么支持训练和多卡？

pybind 导出的函数 Dynamo 不认识，会切断计算图。要用 TORCH_LIBRARY 注册成 torch.ops.xxx 并提供只推形状的 Meta 实现，vLLM 就是这样做的；已完成，explain 确认整层 1 张图。

注意扩展要在 compile 之前加载，否则加载代码本身会造成 graph break。即使不切断，自定义算子在 Inductor 眼里仍是黑盒，不能和前后融合。训练需要反向 kernel + autograd；多卡需要 device guard 和同设备检查，目前都没有。

端到端算子快了 4 倍，整个模型快了多少？

decoder layer 里 RMSNorm 只占约 2%，矩阵乘法 95% 以上。prefill 整层快约 1.5%（Amdahl 预测 1.4%，p=2%，s=3.5）；decode batch 1 快约 10%、batch 8 约 2%，原因是少发射 10 个 kernel，而不是 kernel 时间。最初在 nsys 下测到 20%，不开工具复测后更正。

端到端decode 时 GPU 为什么会空闲？

CPU 把 kernel 放进队列、GPU 按顺序执行，两者异步。decode 每个 kernel 只要几 μs，CPU 发射一个要几十 μs，GPU 做完只能等。不开 nsys 时，Orin 上 eager decode b1 每层 1436 μs，kernel 合计约 1264 μs，GPU 约 12% 时间空闲；ours 只多约 30 μs。batch 8 时 kernel 变大，几乎不空闲。判断方法：比较实际耗时和 kernel 合计。

端到端CUDA Graphs 是什么？有什么限制？

把一串 kernel 录成图，之后一次 cudaGraphLaunch 重放。kernel 不变快，只去掉 CPU 发射开销，所以 decode 收益大、prefill 几乎没用。限制：地址固定（新输入要拷进录制时的缓冲区）、形状固定（vLLM 为常见 batch 各录一张）、没有 CPU 分支。

端到端decode 为什么 batch 8 的 kernel 时间只比 batch 1 多一点？

decode 的 kernel 时间主要在读权重：一层 205 MB，按约 190 GB/s 读一遍约 1.08 ms，实测 1.26 ms。batch 8 仍只读一遍权重，8 个 token 共用，所以只到 1.73 ms。这就是推理服务要批处理的原因。

测量你怎么保证性能数据可信？
  • 先验证正确性；
  • Orin 锁频并记录频率；
  • 预热，CUDA event 包住多次调用，多样本取中位数，多轮交替；
  • 关键结论 3 个独立进程确认；
  • 算有效带宽和峰值比，超过峰值说明在 L2；
  • 知道工具偏差：ncu 冷缓存基础频率，nsys 放大发射开销。
测量举一个你被数据推翻的猜测。

曾看到 n=3840 比 4096 快一倍，以为和 n 有关。3 个独立进程重复扫描后只有部分运行出现，原因是那次工作集刚好留在 L2。之后把"避开接近 L2 大小的形状"作为规则。warp 版阈值 1024 → 256 也是类似例子。

PyTorch你的算子在 torch.compile 下为什么反而变慢？后来怎么追回来的？
  • Inductor 把"残差相加 + norm2"融合成一个 Triton kernel；我们的算子是黑盒，残差只能单独一个 kernel，kernel 14 → 15，decode b1 341 → 378 μs。
  • 写 fused add + RMSNorm 后 kernel 数持平，但 GPU 时间还多 26 μs，说明问题变成 kernel 本身。
  • 读 inductor_cache：Triton 每行 512 线程（num_warps=16），我们 128；单 kernel 扫描证实 1 行时 128×16 最慢。分档加行数维度后，GPU 差距 26 → 5 μs，CUDA Graph 下整层只差 2.4%；再加 float4 后 GPU 时间 278.0 vs 276.4 μs，CUDA Graph 下 b1 只差 0.6%、b8 打平。
  • 排除频率：同作业交替测、三次独立作业差距稳定、只多在 RMSNorm 部分（间接证据）。
PyTorchtorch.compile 从调用到执行经过哪几步？融合发生在哪？

torch.compile 只包一层；第一次调用时 Dynamo 用 FakeTensor 逐行读 forward 抓 FX 图和 guards（自定义算子靠 Meta 推形状，非张量代码会 graph break）→ AOTAutograd 翻译成核心 aten 算子 → Inductor lowering、scheduler（融合在这里）、codegen 出 Triton，矩阵乘交给 cuBLAS → reduce-overhead 时再录 CUDA Graph。

缓存按 guards 存多份，默认上限 8。Dynamo 管图完不完整，Inductor 管 kernel 少不少，CUDA Graph 管 CPU 发射开销。

kernel为什么分档不能只看 n，还要看行数？

行数 = batch × seq，决定一次启动多少 block。decode b1 只有 1 行、整张 A100 只有 1 个 block，速度由延迟决定：128 线程每个串行读 16 个数，比不过 512 线程每个读 4 个（8.25 vs 5.01 μs）。

行多时 GPU 已满，block 小一点能让一个 SM 同时放几个、更好地藏延迟（512 行时 256×8 最好）。同一模型 hidden 固定，行数每一步都在变，所以两个维度都要看。之前单算子测试都是几千行，看不出来，放进整层测 decode 才暴露。

端到端eager+ours、compile、compile_cg 在 decode 下的收益分别来自哪？

都是在减少 CPU 发 kernel 的开销。eager+ours：RMSNorm 从约 5 个 kernel 变 1 个，一层少 10 个，每个约 14 μs，−29%；compile：Inductor 自动融合，约 14 个 kernel，−30%；compile_cg：再加 CUDA Graph，整串一次重放，CPU 开销基本消失，−57%。prefill 时 GPU 被矩阵乘占满、CPU 发射和计算重叠，所有写法差距 ≤2%。

kernelfloat4 向量化是什么？有什么前提？

把指针当 float4* 读，一条 LDG.E.128 读 16 字节（4 个 float）进寄存器：数据量不变，读指令变成四分之一，延迟受限和带宽受限时都有帮助。线程按 float4 跨步，一个 warp 一条指令读连续 512 字节，仍是合并访问。

前提：地址 16 字节对齐（n % 4 == 0 才能保证每行开头对齐，切片可能不对齐），否则 misaligned address；所以 C++ 先检查，不满足就退回标量版。用 cuobjdump 看 SASS 确认有 LDG.E.128。

实测 1 行 add+norm 5.91 → 4.43 μs，整层 GPU 时间追平 Inductor。Triton 从 tt.divisibility=16 知道对齐，自动就做了。

端到端你是怎么把自己的算子接进 TensorRT 的？
  • 先把选档和启动代码从 PyTorch 扩展里剥出来，放进只依赖 CUDA 的 launch.cuh，PyTorch 扩展和 plugin 共用（不带 PyTorch 路径单独 nvcc 编译验证）；
  • 导出时写 symbolic：ai_infra::rms_norm → ONNX 自定义节点 RmsNorm，eps 作属性；老导出器追踪时真的跑 CUDA kernel，所以在 GPU 上导出；
  • plugin（IPluginV2DynamicExt）：getOutputDimensions 对应 Meta，supportsFormatCombination 声明只要 FP32 + 连续，enqueue 里调 launchRMSNorm，serialize 存 eps；creator 是工厂，REGISTER_TENSORRT_PLUGIN 让 .so 一加载就登记；
  • CMake 编成只链接 CUDA 和 TensorRT 的 .so，trtexec --plugins= 建 engine；用导出时存的同一个输入对 PyTorch 结果，误差约 1e-6。
端到端加了 plugin 以后 b8 快了一倍，是你的 kernel 快吗？

不是。逐层看 norm 只有几 μs，和 Myelin 自己生成的差 1 μs 左右。原来 Myelin 把整层包成一个节点，在 FP32、禁 TF32、M=8 下给 MLP 矩阵乘选了 sliced1x4 sgemm，每个 2.4 ms；plugin 是黑盒，Myelin 被切成 17 段，MLP 矩阵乘交给普通矩阵乘层后只要 0.87 ms。

代价是多了独立的 Add 和 reshape 拷贝（各约 6 μs）。而且两个 engine 在 b8 都比 PyTorch eager（1.80 ms）慢，真正的问题是矩阵乘的 kernel 选择（推测，待开 TF32 / FP16 验证）。这和 compile 下"我们的算子挡住融合"是同一类现象：插入黑盒会改变编译器的整体决策。

kernel标量版每个线程也读 4 个 float，为什么 float4 还有收益？

标量版是一个线程发 4 条 LDG.E、分 4 次读（线程 0 读 x[0]、x[512]、x[1024]、x[1536]）；float4 是一条 LDG.E.128 一次读 x[0..3]。数据量一样，读指令差 4 倍；一个 warp 一条指令从 128 字节变成 512 字节。

每条读指令都有发出、追踪、等数据的固定开销：1 行时速度看延迟，指令少等待轮数就少；行多时每条指令带更多数据，更容易用满带宽。Quest n=2048、1 行 add+norm：标量 512×4 5.91 μs，float4 512×4 4.43 μs。

它和 sector 对齐是两件事：对齐决定这段数据跨几个 32 字节块，float4 决定读这段数据要发几条指令；float4 还要求 16 字节对齐。

端到端导出那边和 plugin 那边怎么对上？写错会怎样？

两段代码互不调用，只靠 ONNX 里两个字符串：节点名 RmsNorm（symbolic 写 g.op("ai_infra::RmsNorm", …)，plugin 的 getPluginName() 返回 "RmsNorm"、版本 "1"）和属性名 eps（导出写 eps_f，creator 按 "eps" 读）。

加载 .so 时 creator 登记；Parser 遇到不认识的 RmsNorm 就按名字查注册表、调 createPlugin；engine 里只存 plugin 名字、版本和 eps。节点名写错：导出成功，建 engine 时报找不到 plugin；没加载 .so：建或加载 engine 时失败；属性名写成 epsilon：可能不报错，悄悄用默认值 1e-6，结果只差一点，所以必须和 PyTorch 输出比误差。

端到端TensorRT 给矩阵乘挑了慢的 kernel，你能怎么办？
  • 先证明问题在哪：--exportLayerInfo、--dumpProfile、nsys 看实际 kernel；b8 下 PyTorch eager（cuBLAS）1.80 ms，说明硬件本身没问题；
  • 验证原因：FP16 或开 TF32 重建，看 kernel 和时间变不变。用 eager ONNX 开 FP16 重建：矩阵乘换成 Tensor Core 的 h16816gemm，b8 8.92 → 2.44 ms，说明和 kernel 选择有关（TF32 没测）；
  • 调整模型结构，比如改 ONNX 图、切分节点，影响 Myelin 分组；换 TensorRT 版本或平台比较；
  • 某个矩阵乘特别值得时自己写 plugin；或用 ONNX Runtime CUDA EP 跑同一个 ONNX 作开源对照，隔离问题是否在 TensorRT。

之前 b8 变快恰好是 plugin 切开了 Myelin，不是主动设计，不能当成稳定方法，真实项目里要把这种依赖写进风险。
