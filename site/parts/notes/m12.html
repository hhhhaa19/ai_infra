模块 12

核心算子：矩阵转置，把"跳着访问"挪进 shared memory

主线：转置没有计算，纯搬数据，是带宽问题。难点是读和写的方向不一致：读 A 连续，写 B 就要跳着写。优化分两段：先让读写全局内存都连续（①～③），再让同时在路上的读请求变多（④⑤）。衡量标准是有效带宽 GB/s，天花板是同样数据量的 copy。

1概览

结果总览

Orin，锁频 1300 MHz，4096 × 4096，FP32；GB/s = 2·M·N·4 / 时间。所有版本和 CPU 结果逐元素按位相等。

两条访存规则

全局内存shared memory
在哪DRAM，经过 L1 / L2SM 内部，不是缓存，直接按地址取
喜欢一个 warp 的 32 个地址连续32 个地址落在不同的 bank
做不好的后果按 32 字节一箱搬，跳着读写时每箱只用 4 字节，浪费带宽同一 bank 的不同地址排队，一条指令分几轮
规则—bank = 线性位置 % 32；同一地址是广播，不算冲突
  • 判断方法都是"竖着看一条指令"：一个 warp 的 32 个地址，看连不连续（全局）、% 32 有没有重复（shared）。
  • 一个 warp 是哪 32 个线程：tid = x + y × blockDim.x，每 32 个一组。block 宽 32 时一个 warp 正好是一行。

2优化步骤

① naive

int x = blockIdx.x * blockDim.x + threadIdx.x;   // A 的列
int y = blockIdx.y * blockDim.y + threadIdx.y;   // A 的行
if (y < M && x < N) B[x*M + y] = A[y*N + x];    // A 是 M×N，B 是 N×M，行优先
  • 同一个 warp 里 x 连续：读 A 连续；写 B[x*M + y] 相邻线程相隔 M 个 float，每个数占一整箱，写的带宽只用上 1/8。
  • 只用寄存器解决不了：每个线程只能写自己读进来的数，读和写不可能同时连续。转置里一个线程要写出去的数是别的线程读进来的，必须经过大家都能访问的 shared memory 交接。

动画 · naive 和 shared 中转的数据流（缩小版）：对比读写各搬了几箱。

动画：缩小版转置。8×8 的 A 里右上角那块 4×4 小块，用 naive 和 shared memory 两种方法搬到 B 的左下角，统计读写各搬了多少箱数据。

② shared memory 中转

__shared__ float tile[32][32];
int tx = threadIdx.x, ty = threadIdx.y;          // 块内坐标，只用来访问 tile
int bx = blockIdx.x * 32, by = blockIdx.y * 32;  // 小块在 A 里的起点
if (by+ty < M && bx+tx < N) tile[ty][tx] = A[(by+ty)*N + bx+tx];   // 按 A 的行读，连续
__syncthreads();                                                      // 不能放在 if 里
if (bx+ty < N && by+tx < M) B[(bx+ty)*M + by+tx] = tile[tx][ty];   // bx、by 对调；按 B 的行写，连续
  • tile 只用块内坐标，全局坐标会越界。
  • 写 B 时块的起点对调：A 的第 (by, bx) 块落在 B 的第 (bx, by) 块。
  • 验证：B 的 (bx+ty, by+tx) 应等于 A 的 (by+tx, bx+ty)，在 tile 里是第 tx 行第 ty 列，即 tile[tx][ty]。
  • 边界：读 A 查行 < M、列 < N；写 B 查行 < N、列 < M。B 每行 M 个数，方阵测不出乘错，测试要用非方阵、非 32 倍数的形状。
  • 代价：第二步一个 warp 读 tile[0..31][ty]，同一列都在同一个 bank → 32 路冲突。

③ padding

  • 只改一行：__shared__ float tile[32][33];。bank = (r × 33 + c) % 32 = (r + c) % 32，竖着取一列时 32 行正好落在 32 个 bank。
  • 只改 tile 的宽度：线程数、块大小、A 和 B 的下标都不变，块的起点仍是 blockIdx.y * 32。
  • 和 GEMM 的 +4 对比："行宽 % 32"决定往下一行 bank 挪几格。转置一个 warp 跨 32 行，每行挪 1 格正好铺满；GEMM 写 As 跨 8 行、每行 4 个数，要挪 4 格，而且 float4 要求每行起点是 4 的倍数。

动画：一个 warp 竖着读 tile 的第 c 列时，32 个地址落在哪些 bank；切换 tile[32][32] 和 tile[32][33] 对比。

5

④ 每线程搬 4 个数

  • 瓶颈：③ 已是 copy 的 89%，但 copy 自己只有约 100 GB/s，是 Orin 上限的一半。每个线程只发 1 个读请求就得等它回来，同时在路上的请求太少。
  • 改法：block 32×32 → 32×8，一个 block 仍负责 32×32 的小块，每个线程循环 4 次，第 i 次处理第 ty + i*8 行。
// block(32, 8)；grid 不变：((N+31)/32, (M+31)/32)
#pragma unroll
for (int i = 0; i < 4; ++i)
    if (by+ty + i*8 < M && bx+tx < N) tile[ty + i*8][tx] = A[(by+ty + i*8)*N + bx+tx];
__syncthreads();
#pragma unroll
for (int i = 0; i < 4; ++i)
    if (bx+ty + i*8 < N && by+tx < M) B[(bx+ty + i*8)*M + by+tx] = tile[tx][ty + i*8];
  • 结果：copy 101.7 → 170.5，padding 版 90.7 → 184.3 GB/s；naive 只到 38.2（它的瓶颈是跳着写，不是请求太少）。
易错：① 块的起点要写 blockIdx.y * 32，写成 blockIdx.y * blockDim.y 后 blockDim.y 变成 8，相邻 block 重叠、大部分行没人管；② 边界要判断实际访问的那一行（ar + i*8），只查 ar 会越界，而且测试不一定报错；③ 改分工要同时改 launch 的 block 形状。

⑤ __restrict__

  • 现象：④ 之后转置 184.3 比 copy 170.5 还快，工作量不比 copy 少，说明 copy 没写到最快。
  • SASS：copy 是 LDG STG LDG STG…，读一个写一个；转置是 4 个 LDG 连着发出。
  • 原因：别名（aliasing）：编译器不知道 A、B 会不会指向重叠的内存（比如 copy(p, p + N)），写 B 第 0 行可能改到 A 第 1 行，所以不敢把下一个读提前到上一个写之前。转置是读进 shared，写 shared 不可能改到全局的 A，所以敢提前。
  • 改法：const float* __restrict__ A, float* __restrict__ B，承诺两者不重叠。SASS 变成 LDG.E.CONSTANT × 3 连着发出；copy 4096² 170.5 → 187.8，转置是 copy 的 98%。
  • 注意：这个承诺编译器不检查，真的重叠时结果错而且不报错。

动画 · 一个线程的读写时间线（示意）：每线程 1 个数 / 4 个数读写交替 / 4 个数 + __restrict__。

示意动画：一个线程的读写指令时间线。每线程 1 个数时每次只有 1 个读请求在路上；每线程 4 个数但读写交替时编译器不敢提前读；加 __restrict__ 或经过 shared 后几个读请求一起发出。

示意图：横轴是时间，长度不按实际周期比例；"等"是读请求从 DRAM 回来之前的空等。
和 RMSNorm、GEMM 是同一个道理：RMSNorm 用编译期常量让循环展开、GEMM 用 double buffering、转置每线程搬 4 个、copy 加 __restrict__，都是为了让更多读请求同时在路上，带宽才能用满。

3复习

面试要求

转置是手写 CUDA 题里最常见的"shared memory + bank conflict"题，也是 padding 的标准例子。

必须会

  • 当场手写三版：naive、shared memory 中转、tile[32][33]；下标（行优先、乘的是每行元素数）、块内坐标和全局坐标分开、bx / by 对调、两处不同的边界判断、__syncthreads() 不能放在 if 里。
  • 说清为什么 naive 慢（写全局跳着，每个数搬一整个 32 字节扇区）、为什么 shared 版快、为什么还有 32 路冲突、为什么 +1 能消掉（bank = (r + c) % 32）。
  • 全局内存和 shared memory 各自"喜欢"什么样的访问；合并访存和 bank conflict 分别发生在哪。
  • 一个 warp 是哪 32 个线程：tid = x + y × blockDim.x；32×32、16×16 的 block 各是什么样。

应该会

  • 为什么不能只用寄存器（线程私有）；__shfl_sync 只能在一个 warp 内交换。
  • shared memory 和 L1 在同一块存储上但不是缓存；同地址是广播、同 bank 不同地址才冲突。
  • 用数字讲：4096² 下 naive 37.3 → shared 61.9 → padding 91.1 GB/s，copy 101.9；每线程 4 个数后 padding 184.3，copy 加 __restrict__ 后 187.8，转置是 copy 的 98%；怎么测的（逐元素按位相等、锁频、GB/s 的定义、copy 当天花板）。
  • 每个线程搬多个数为什么快（同时在路上的读请求多）；32×8 block 时 4 次循环怎么不重不漏地盖住 32 行、起点为什么是 × 32 而不是 × blockDim.y、边界要判断实际访问的那一行。
  • __restrict__：别名是什么、为什么编译器不敢把读提前、加了以后 SASS 怎么变、为什么写 shared 的版本不需要它、它是不检查的承诺。
  • padding 的 +1 和 GEMM 的 +4 为什么不同。

加分

  • 不用 padding 的修法：斜着存（diagonal / swizzle），知道思路。
  • 全局读写用 float4（还没做）；8192² 上转置只有 copy 的 80% 的原因（TLB / DRAM 分页，未验证）。
  • 原地转置（in-place）为什么难并行；非方阵的处理。
