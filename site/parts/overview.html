各主线怎么优化的

  • RMSNorm（受带宽限制的算子）：目标是 x 只读一次、y 只写一次。warp shuffle 规约 → 线程数改成编译期常量（循环展开，同时发出更多读请求，追平 CUB）→ 每线程元素数固定、x 存寄存器 → 按 n 分档（n ≤ 256 时一个 warp 算一行）→ float4。放进整层后，收益主要来自少发 kernel；在 torch.compile 下要做 fused add + RMSNorm，才不会挡住 Inductor 的融合；CUDA Graph 下整层追平 Inductor。见 RMSNorm 优化主线。
  • GEMM（受计算限制的算子）：核心是数据搬一次、用多次。4096³ 下：naive 408 → shared memory 分块 614 → 寄存器分块 1744 → 交错分工消除 bank conflict 2091 → float4 + As 转置 1790（反而变慢，ncu 看到占用率 33%）→ padding + 展开 kk 2366（cuBLAS 的 70%，ncu 里最大的停顿是等全局内存）→ double buffering 2895 GFLOPS（cuBLAS 的 85%，long_scoreboard 1.81 → 0.02）。见 模块 11 优化主线。
  • 转置（受带宽限制、读写方向不一致）：读 A 连续，写 B 就要跳着写，全局内存那一半的带宽被浪费。把"跳着访问"挪到 shared memory 里做：按行读进 32×32 的 tile，再按 B 的行连续写出；竖着取 tile 的一列有 32 路 bank conflict，tile[32][33] 消掉。4096² 下：naive 37.3 → shared 61.9 → padding 91.1 GB/s（copy 的 89%）。之后发现 copy 自己只有 Orin 带宽的一半：每个线程只搬 1 个数，同时在路上的读请求太少。block 改成 32×8、每个线程搬 4 行后 padding 版到 184 GB/s；再给 copy 的指针加 __restrict__（编译器才敢把几个读一起提前发出），copy 到 188 GB/s，转置是它的 98%。见 模块 12。
  • Softmax（受带宽限制、每行要两次规约）：每行先减最大值再取指数、除以总和。优化分两个方向：分工（一行交给 1 个线程 / 1 个 block / 1 个 warp）和算法（读几遍）。一个线程一行时 warp 内地址不连续，只有 copy 的 4～11%；一个 block 一行后 n = 1024、4096 接近 copy（后两遍读命中缓存）；n = 32000 一行 125 KB 放不进缓存，三遍读 → 49%，online softmax 把最大值和分母合成一遍 → 63%；n = 128 时 256 个线程、16 次同步只为 128 个数，只有 20%；改成一个 warp 一行、整行放进寄存器、只读一遍、用 xor shuffle 规约不要同步后到 190 GB/s（copy 的 108%，峰值的 93%）。最后按 n 分档：n ≤ 1024 用 warp 版、中等用 block 版、很长用 online 版。见 模块 14。
  • MoE all-to-all（FAST 复现，跨机网卡是瓶颈）：流量不均衡时，NCCL 的用时由最忙那张 GPU 的网卡决定。FAST 先用 NVLink 在服务器内把要发出去的数据匀给 4 张卡，再让第 k 张卡只发给对面第 k 张。Quest 2 台 × 4 张 H100 上：先逐层排查跨机带宽（关掉 GPUDirect 后每张网卡 13.7 → 20.2 GB/s）→ 第一版 FAST 比最强 NCCL 慢（0.63～0.82×），在均匀流量上多出的时间就是实现开销 → 三步分开计时，发现跨机一步网卡跑不满，打包成一整块 + 每对卡 8 条通道后 Zipf 0.99 从 28.3 降到 13.0 ms → 切块流水线放在同一次 NCCL 调用里只到 1.69× → NVLink 和网卡各用一个 communicator、一个 stream，用 event 衔接，Zipf 0.99 时 1.96×、离理论最快约 2%（之后 2 台 × 4 卡复测只有 1.72×，查明不是机器波动，而是后来改代码引入的 bug：机内直传被并进第一块的准备步骤，网卡要等它传完才开始发，本来能重叠的两件事变成了先后；同一对机器上旧版 1.92×，修复后的数字待验证）；均匀流量仍是 0.86×。换成 4 台 × 每台 2 卡后最多只有 1.25×，补上的 BvN 分解只比简单轮流配对快 2～7%：收益几乎全部来自机内的卡互相分担，取决于每台有几张卡。见 Lina 模块第 10 节、第 11 节。
  • TensorRT 部署：ONNX → engine；FP16 让矩阵乘换成 Tensor Core kernel（Orin，b8 8.92 → 2.44 ms）。TensorRT 会自己把 RMSNorm 的 7 个节点融成 1 个 kernel；换成自定义 plugin 后结果对，但 Myelin 的子图被切开，性能会跟着变（b8 反而快了一倍）。SmolVLA 拆成视觉 A、前缀 B、去噪一步 C 三个 engine：直接全 FP16 会算错（LayerNorm / RMSNorm 的平方超出 FP16 范围、RoPE 角度大到 240 弧度精度不够），把这些节点留 FP32、矩阵乘仍走 FP16，每次观测 336 → 约 95 ms，端到端动作误差低于模型原生 bf16 和 FP32 的差距。见 模块 9、模块 10、SmolVLA。

设备：Jetson AGX Orin 64GB（sm_87，TensorRT 8.5.2）是主力平台；Quest A100-PCIE-40GB（sm_80）用于交叉验证。

面试要求怎么看

每个模块在「自测」前加了一块「面试要求」，按推理优化 / 端侧部署 / CUDA 算子方向常见的面试内容分三档：必须会 = 不看资料能当场讲清或写出来，答不上来基本会被判定为"没真正做过"；应该会 = 能讲清原理、写出关键片段、结合自己的项目举例；加分 = 知道是什么、解决什么问题，能说出思路。各模块的「高频问题」并进了自测。档位是按这类岗位常见面试内容整理的经验判断，具体公司会有差异。

通用原则：面试官最常问的不是"这是什么"，而是"你为什么这么做、你怎么知道它有效、数字是多少"。每个模块都准备一个自己做过的具体例子 + 一个数字。
