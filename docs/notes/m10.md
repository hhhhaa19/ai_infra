# 策略模型上机：ACT 部署到 Orin

**主线**：把公开的 ACT 策略模型（LeRobot `act_aloha_sim_transfer_cube_human`）从 PyTorch 部署到 Orin 的 TensorRT。每一步只看三件事：**做了什么、为什么、结果是多少**。数字都是实测，误差目前只用了随机输入。

<a id="act"></a>

## 结果总览

| 步骤 | 在哪 | 结果 |
|---|---|---|
| ① PyTorch 参考输出 | Quest（CPU） | 4 组固定输入 + 输出存成 `io_samples.pt` |
| ② 导出 ONNX（归一化放进图里） | Quest | 131.4 MiB；ONNX Runtime vs PyTorch rel L2 ≈ 1e-7 |
| ③ TensorRT FP32 | Orin（锁频 1300 MHz） | 中位 **17.04 ms**，CUDA Graph 12.52 ms；误差 ≈ 1e-7 |
| ④ TensorRT FP16 | Orin | 中位 **5.56 ms**（3.1×），CUDA Graph **3.70 ms**；rel L2 4.5e-4～1.1e-3，最大 2.2e-3 rad |
| ⑤ 图清理、INT8、真实数据、仿真闭环 | — | 还没做 |

- **为什么 Quest 导出、Orin 只跑 TensorRT**：LeRobot 要 Python ≥ 3.12、torch ≥ 2.7；Orin 是 JetPack 5（torch 2.1），容器换不掉底层的驱动和 JetPack。Orin 部署本来也只需要 ONNX + TensorRT。代价是没有 Orin 上的 PyTorch 基线。

```text
Quest（或 Mac / 其他 x86 机器）：LeRobot 加载 ACT → 保存输入和 PyTorch 输出 → 导出 ONNX
                 ↓ 拷贝 ONNX 和输入输出样例
Orin：TensorRT FP32 / FP16 / INT8 → C++ 推理 → 和 PyTorch 输出比误差、测延迟
```

## 模型长什么样

- 模仿学习模型：输入相机图像 + 14 维关节状态，一次输出接下来 100 步动作（action chunking，一次预测一段，减少误差累积和抖动）。
- 约 5170 万参数；推理时潜变量 z = 0，不需要 VAE encoder。
- 对部署来说就是一个标准网络：一次前向出动作，没有扩散去噪循环，也没有 LLM。

## ① 定边界：归一化放进 ONNX

- **做了什么**：包一层 `ActForExport`，只取 `policy.model`，把图像、状态、动作的 6 个均值 / 标准差用 `register_buffer` 登记；forward 里先归一化 → ACT → 取动作 → 反归一化。
- **为什么**：部署程序只喂原始数据，不会漏步骤或用错参数；训练和部署的预处理必须完全一致。
- **坑**：新版 LeRobot 加载这个旧 checkpoint 时不会自动用归一化参数，要自己从 `model.safetensors` 取出来。
- buffer 和 parameter 都会导出（buffer 作为常量），但 buffer 训练时不更新，正适合放统计量。
- 不需要 TORCH_LIBRARY 注册：里面全是 PyTorch 已有算子，直接翻译成标准 ONNX 节点。只有换成自己的 CUDA kernel 时才要注册和写 plugin。

## ② 导出 + 两层验收

```text
输入：image [1,3,480,640]（[0,1]）、state [1,14]      输出：action [1,100,14]（已反归一化）
ONNX 131.4 MiB（官方 checkpoint 约 207 MB：VAE encoder 推理用不到所以没导出；BatchNorm 被常量折叠进卷积，只剩 21 个 Conv）
ONNX Runtime vs PyTorch：最大绝对误差 2.4e-7～3.6e-7，rel L2 8e-8～1e-7（FP32 数值误差范围内）
在 Quest 登录节点 CPU 上跑完约 156 秒，没有提交 Slurm 作业
```

- **先用 ONNX Runtime 对答案**：它只当"导出验收器"。ORT 和 PyTorch 一致，之后 TensorRT 再出误差，就能确定问题在 TensorRT 的优化或精度，而不是导出。
- 两层检查：PyTorch vs ONNX Runtime 查导出；PyTorch vs TensorRT 查部署。
- engine 绑定 GPU 型号和 TensorRT 版本，Quest 上建的不能拿到 Orin 用，所以 engine 必须在 Orin 上建。

## ③ 建 engine：opset 17 → 16，看 TensorRT 怎么融合

- **问题**：opset 17 把 LayerNorm 导出成 1 个 `LayerNormalization` 节点，Orin 的 TensorRT 8.5 不认识。
- **改法**：只改 `OPSET = 16`，LayerNorm 被拆成 9 个基础节点；重新导出后 ORT 误差仍约 1e-7。

```text
opset 17：LayerNorm → 1 个 LayerNormalization（共 12 个）            节点总数 2825
opset 16：LayerNorm → ReduceMean → Sub → Pow → ReduceMean → Add → Sqrt → Div → Mul → Add（9 个）
          LayerNormalization 0 个，ReduceMean 24、Pow 12、Sqrt 12      节点总数 2945
重新导出后 ONNX Runtime 误差仍约 1e-7
```

## ④ FP16：17.04 → 5.56 ms

- **做了什么**：同一个 FP32 ONNX，`trtexec --fp16 --noTF32`。精度在建 engine 时决定，导出时不用改。
- **不要导出 FP16 ONNX**：TensorRT 能按层选精度，敏感层留 FP32；直接导出 FP16 会强制所有层 FP16。
- **为什么快 3 倍**：卷积和矩阵乘用上了 Tensor Core。

```text
FP32：647 层；Transformer 部分被包成 1 个 Myelin 节点 6.45 ms；ResNet 卷积每层约 0.3～0.6 ms
FP16：651 层；同一个 Myelin 节点 2.57 ms；卷积大多约 0.07 ms（用上了 Tensor Core）
卷积后面的 Mul + Add（BatchNorm 折叠后的样子）和 ReLU 已和卷积合成一层，如 conv1/Conv + bn1/Mul + bn1/Add + …
拆开的 LayerNorm 节点没有单独出现 → 推测已经在 Myelin 节点里被融合（根据层名推断，没用 nsys 确认）
```

| 精度 | 中位 | P99 | CUDA Graph | engine | 最大误差 | rel L2 |
|---|---|---|---|---|---|---|
| FP32（--noTF32） | 17.04 ms | 17.11 ms | 12.52 ms | 161 MB | ≤ 4.5e-7 | ≈ 1e-7 |
| FP16 | 5.56 ms | 5.80 ms | 3.70 ms | 68 MB | ≤ 2.2e-3 | 4.5e-4～1.1e-3 |

- P99 和中位只差 0.1～0.2 ms，很稳定。
- FP16 最大误差 2.2e-3 rad ≈ 0.13°（动作是关节角）。

> 误差是 4 组
>
> 随机噪声输入
>
> 算的，只说明 engine 没把数算错；真实画面下动作对不对，要靠数据集回放和仿真闭环。随机输入也不能用来做 INT8 校准。

## ⑤ CUDA Graph：发射开销有多大

- FP32 17.04 → 12.52 ms，FP16 5.56 → 3.70 ms：CPU 逐个发射 kernel 的开销不小。
- 原因是层太多：导出带来 1206 个 Squeeze / Unsqueeze；逐层 profile 加起来 13.5 ms，远大于正常的 5.56 ms（每层都有额外开销）。

## 下一步优化（按顺序）

| 步 | 做什么 | 为什么 |
|---|---|---|
| 图清理 | 改写导出代码，直接 reshape / permute / cat，去掉多余 Squeeze / Unsqueeze；位置编码预先算成常量 | 不改数学结果，减少层数和发射开销 |
| 真实数据误差 | 数据集里几十帧真实观测，比 PyTorch 和 FP32 / FP16 engine | 替换随机输入的结果 |
| INT8 PTQ | 几百帧真实数据做校准；掉点时逐层定位，敏感层回退 FP16 | 可能继续降延迟 |
| 仿真闭环 | gym-aloha，每种精度跑多回合，报成功率和置信区间 | 确认任务没变差 |

> 现在不给 LayerNorm 写 plugin
>
> ：它不是瓶颈，而且已经在 Myelin 里融合；plugin 是黑盒，会把 Myelin 切开、打断融合（RMSNorm plugin 时切成了 17 段）。只有 TensorRT 不支持、或某个算子在 profile 里明显很慢时才写。

## 怎么判断部署效果：三层指标

| 层次 | 测什么 | 证明什么 |
|---|---|---|
| 系统指标 | 延迟均值 / P95 / 最大值，各阶段时间，engine 大小、显存、功耗 | 跑得够不够快、够不够稳 |
| 离线动作误差 | 同一帧真实输入下，原模型和 engine 的动作误差（按关节） | 部署没改变模型行为 |
| 仿真闭环成功率 | 每种精度多回合，报次数和置信区间 | 任务没有变差 |

- **延迟预算**：控制频率决定上限。15 Hz → 每次 66.7 ms，扣掉相机、预处理、通信（假设 30 ms），模型只剩约 36 ms。要看 P95 和最大值，不能只看平均。
- **成功率要带次数和区间**：19/20 和 18/20 的 95% 区间大幅重叠，20 次分不出谁好。
- **误差小 ≠ 任务一定成功**：闭环里误差会累积，所以要三层都看。

## 部署工程师在流水线里做什么

流水线：定任务 → 采数据 → 训练 → 仿真验证 → **模型部署** → 系统集成 → 真机测试 → 迭代。部署这一环负责让模型在真实硬件上跑得够快、够准、够稳。

| 工作 | 内容 | ACT 里对应 |
|---|---|---|
| 导出和转换 | PyTorch → ONNX → TensorRT，处理不支持的算子、版本不兼容 | opset 17 → 16 |
| 性能分析 | 逐层 profile、nsys 找时间花在哪 | Myelin 2.57 ms、层太多 |
| 量化 | FP16 / INT8；难点是掉点后定位哪层、怎么修 | FP16 已做，INT8 待做 |
| 精度验证 | 离线误差、仿真、实机 | 两层验收 + 三层指标 |
| 工程整合 | C++ 推理程序、前后处理上 GPU、接 ROS 2、延迟抖动 | CUDA Graph |
| 自定义算子 | TensorRT 不支持或很慢时写 kernel / plugin | RMSNorm plugin |

| 改动 | 公式变了吗 | 要重训吗 |
|---|---|---|
| 换 kernel 实现、融合、ONNX → TensorRT | 没变 | 不用，比输出误差 |
| FP16 | 有舍入 | 通常不用，比误差 + 任务测试 |
| INT8 PTQ | 近似 | 不用，要校准数据 |
| QAT | 近似 | 要微调（PTQ 不够时） |
| 换激活 / norm、剪枝、改结构 | 变了 | 要重训或微调 |

掉点时的顺序：FP16 → INT8 PTQ → 敏感层回退 FP16 → QAT → 换小模型 / 蒸馏，把训练成本放到最后。

## 真机效果差：分层排查

```text
排查梯子：从最简单的环境开始，哪一步开始变差，问题就大概率在新加的那一层
1. 桌面 GPU + PyTorch + 数据集          第 1 步就不好        → 模型或数据
2. Orin + TensorRT + 同一批数据         1 好、2 差           → 导出或量化
3. Orin + 录制的真机数据回放            2 好、3 差           → 真实数据和预处理
4. 仿真闭环
5. 真机，不执行动作，只输出预测
6. 真机低速运行                         3 好、6 差           → 延迟、控制或动力学
7. 真机正常运行                         6 好、7 差           → 速度相关的动力学或控制频率
```

- **记录一切**：原始图像、预处理后的张量、状态、模型输出、实际动作和时间戳，失败后能回放。
- **回放对比**：同一份真机日志在 PyTorch 和 Orin 上各跑一遍，动作近似相同就说明部署层大概率没问题。
- sim-to-real 里和部署最相关的是**延迟对齐**：把实测的端到端延迟及其波动告诉训练端，在仿真里加进去。

## 推理程序怎么分层

```text
应用和任务
  ↓
机器人接口层：相机、状态、动作        ← ROS 2 消息和节点隔离；URDF 和配置文件描述关节、相机位置
  ↓
推理接口层：输入张量 → 输出动作        ← C++ 里统一的 infer(input) → action
  ↓
后端：TensorRT / llama.cpp / ONNX Runtime
  ↓
硬件：Orin / Thor / x86 GPU            ← Docker 或固定 JetPack、CUDA 版本；保留 ONNX，到目标机器重建 engine
```

不要写死模型形状和路径：模型 / plugin 路径、输入输出名称和形状、图像尺寸和归一化参数、控制频率、关节顺序放进配置文件，换模型或换机器人时只改配置。

## 下一个模型：SmolVLA

**为什么换**：ACT 做到 FP16 engine 跑通、和 PyTorch 对上误差就停了（INT8 和仿真闭环都没做）。ACT 一次前向就出结果，部署上没有难点；SmolVLA 是"VLM 主干 + 动作生成头"的结构（π0、GR00T 也是这一类），约 4.5 亿参数，Orin 能跑，LeRobot 原生支持。更重要的是它的一次推理和 LLM 推理几乎一样：

```text
前缀：VLM 跑一遍（类似 prefill），得到 KV cache
  ↓
去噪循环 × 10：action expert 每次读同一份前缀 KV cache（类似 decode 循环）
```

|  | ACT | SmolVLA |
|---|---|---|
| 大小 | 约 8000 万 | 约 4.5 亿 |
| 视觉 | 每个相机一个 ResNet-18 | 预训练 VLM 里的 SigLIP |
| 听指令 | 不能，一个模型一个任务 | 能，靠语言指令换任务 |
| 生成动作 | 一次前向输出 100 步 | flow matching，从噪声开始去噪 10 次，输出 50 步 |

**⓪ 可行性检查（Quest CPU）**：加载 `lerobot/smolvla_base`，随机输入跑一次，记下结构和形状。

| 部分 | 参数 | 结构 |
|---|---|---|
| 视觉编码器（SigLIP） | 86M | 12 层 ViT，512×512 输入，16×16 patch → 每张图 1024 个 |
| connector | 12M | pixel shuffle 把相邻 4×4 个 patch 拼成一个（1024 → 64），线性层投影到 960 |
| VLM 语言层 | 205M | 16 层 Llama（原模型 32 层留一半），hidden 960，15 个 Q 头 / 5 个 KV 头（GQA），head_dim 64 |
| lm_head | 47M | 不生成文字，推理用不上 |
| action expert | 98M | 16 层，hidden 720；每隔一层是交叉注意力，读 VLM 的 KV |

```text
① 3 张图 ──SigLIP + connector──▶ 3 × [64, 960]
② 前缀 = 192 个图像 token + 48 个文本 token（总是补齐到 48）+ 1 个状态 token = 241 个
   ──VLM 16 层──▶ KV cache：16 层，每层 K、V 都是 [1, 5, 241, 64]
③ 去噪 × 10：噪声动作 x [1, 50, 32] ──action expert──▶ 速度 v [1, 50, 32]，x = x + dt·v
④ 输出 50 步动作 [1, 50, 32]（只有前 6 维对应 6 个关节）
```

1. **形状全部静态**：相机数固定、文本补齐到 48，前缀永远是 241 个 token。TensorRT 处理静态形状最简单。
2. **计算量主要在视觉**（粗估）：视觉约 530 GFLOP（约 75%），VLM 前缀约 76，expert 每步约 10、10 步约 100。所以优化的重点是视觉编码器，不是去噪循环。CPU 一次 6.7 s，只作参考。
3. **能省的重复计算**：expert 的交叉注意力层每一步都把 VLM 的 KV 重新过一遍自己的 k_proj / v_proj，而 KV 在 10 步里不变，算一次就够（原代码没做）。

**拆成 3 个 engine**（带循环的图不好导出成一个 ONNX，循环放 C++）：

| engine | 输入 | 输出 | 次数 |
|---|---|---|---|
| A 视觉 | [3, 3, 512, 512] | [3, 64, 960] | 1 |
| B 前缀 | 241 个 token 的嵌入、掩码、位置 | 16 层 K、V | 1 |
| C 单步去噪 | x_t、时间步、16 层 K、V | 速度 v | 10 |

风险：原代码的 KV cache 是 Python 对象 `DynamicCache`（还带追加再裁剪），要写包装层换成纯张量；自定义二维注意力掩码导出后要验证；FP16 精度要逐块对比；opset 要按 TensorRT 8.5 选。后续步骤：② Orin 上先 FP32 再 FP16，逐块和 PyTorch 参考输出对比 → ③ C++ 串起来（预处理 kernel、KV 常驻显存、Euler 更新 kernel、循环在 C++）→ ④ 固定输入和噪声做端到端对比 → ⑤ nsys 找瓶颈，依次试提前算交叉注意力 K/V、CUDA Graph、视觉 INT8、减少去噪步数、异步推理 → ⑥ 延迟 / 离线动作误差 / 仿真成功率三层评估（`smolvla_base` 没有在具体任务上微调，到这一步要找 LIBERO 微调权重或自己微调）。

**① 引擎 A 的导出**：`src/vla/export_vision.py`把 ×2−1 → SigLIP → post_layernorm → connector → ×√960 包成一个模型，resize 和补边留在外面；PyTorch 跑两组随机图把输入输出存成 `vision_io.pt`，以后 onnxruntime 和 TensorRT 都拿它对答案。PyTorch 在这里只做两件事：导出需要它实际跑一遍来记录计算图（tracing），以及留下标准答案；部署到 Orin 后不需要 PyTorch。三次 CPU 作业：

1. **tracing 时报 IndexError**：SigLIP 每层前要生成 attention mask，要用到 patch 总数 1024；导出时这个数被换成"会记账的张量"，transformers 误以为是旧版本的调用方式（传一串位置编号），去取第一个元素就越界。这是库的兼容 bug，只在导出时触发。我们的图都是满图，mask 全是"可以"，于是不调用 `embed_image`，手动依次调用 embeddings → encoder（不传 mask）→ post_layernorm → connector，和原版的最大差值 0。
2. **onnxruntime 加载失败**：SmolVLM 为了支持任意尺寸的图，位置编号的算法是"相对坐标 → 查落在哪个格子 → 按条件写回"，导出后变成 NonZero、ScatterND 这类"按数据决定往哪写"的节点，ScatterND 的输入类型前后不一致（float 和 int64）；就算能加载，TensorRT 对这类节点的支持也差。满图时编号就是 0～1023，改成直接加整张位置编码表 [1024, 768]。
3. **通过**：与原版差值 0；ONNX 374.9 MiB、855 个节点，NonZero / ScatterND 消失；onnxruntime 与 PyTorch rel_l2 1.46e-6 / 1.34e-6（max_abs_err 3.66e-3 / 1.83e-3，输出范围约 [−2420, 1121]）。

| ONNX 节点 | 数量 | 对应 ViT 的哪部分 |
|---|---|---|
| Conv | 1 | patch embed（16×16、stride 16，就是 conv bench 里的 siglip_patch） |
| Softmax | 12 | 12 层 attention |
| MatMul | 97 | 每层 Q、K、V、O 四个投影 + QKᵀ、PV + MLP 两个 = 8，× 12 = 96，再加 connector 1 个 |
| ReduceMean | 50 | 25 个 LayerNorm（每层 2 个 × 12 + 最后 1 个），每个拆出均值和方差两次 |
| Pow / Sqrt / Div | 各 25 | 同样是那 25 个 LayerNorm（opset 16 没有 LayerNorm 节点） |
| Tanh | 12 | GELU 的 tanh 近似，每层 MLP 一个 |

ViT 本身：图切成 16×16 的块，每块 16×16×3 = 768 个数乘一个矩阵变成 768 维向量（这正是 K = 768 的 16×16 stride 16 卷积），加上可学的位置编码；每层 LayerNorm → attention（12 个头、每头 64 维，[1024, 1024] 的分数表每行 softmax）→ 残差 → LayerNorm → MLP（768 → 3072 → 768，GELU）→ 残差。每层约 4.8 G（四个投影）+ 3.2 G（QKᵀ 和 PV）+ 9.7 G（MLP）FLOP，12 层约 200 GFLOP 一张图，几乎全是矩阵乘，所以 Orin 上快不快主要看能不能用上 FP16 Tensor Core。Orin 上的结果见下面 ②。

**② 引擎 A 在 Orin 上编 TensorRT**：ONNX 和参考数据经本机 ssh 管道从 Quest 拷到 Orin（用 md5 核对），`trtexec --onnx=… --noTF32` 编 FP32（`--noTF32` 保证矩阵乘真用 FP32 而不是 TF32，和 PyTorch 比才公平），再编 FP16；检查脚本 `src/vla/check_vision_trt.py` 仿照 ACT 的 `check_trt.py`，喂 2 组参考输入，比 rel_l2、max_abs、cos。

| 引擎 | 延迟（普通 / CUDA Graph） | rel_l2 | cos |
|---|---|---|---|
| FP32（`--noTF32`） | 226.5 / 224.7 ms | 2.0e-6 | 1.000000 |
| FP16 全部层 | 49.0 / 48.0 ms | **0.26（算错）** | 0.966 |
| FP16 + LayerNorm 留 FP32 | 49.5 / 48.3 ms | 8.5e-3 | 0.99996 |

Orin，TensorRT 8.5，一次处理 3 张 512×512 的图。

1. **FP16 为什么算错**：opset 16 没有 LayerNorm 节点，导出时拆成"减均值 → 平方（Pow）→ 求平均 → 开方 → 相除"。平方那一步只要某个值偏离均值超过 256，结果就超过 FP16 最大值 65504 变成 inf，于是部分 token 错得面目全非（最差的 rel_l2 超过 1）。输出范围本来就有约 [−2420, 1121]，中间激活值很大。
2. **怎么修**：这些节点名字有统一规律，用 trtexec 的 `--layerPrecisions` 把 225 个 LayerNorm 相关节点指定为 FP32，加 `--precisionConstraints=obey` 让 TensorRT 必须遵守，其余仍是 FP16。延迟几乎不变，因为大头是矩阵乘，矩阵乘仍走 FP16 Tensor Core。这串层名目前是手工生成的，还没做成可复用的构建脚本。
3. **FP32 速度合理吗**：3 张图约 650 GFLOP，226 ms 约 2.9 TFLOPS，约 1300 MHz 下 FP32 峰值的 55%（估算）。FP16 快约 4.6 倍。
4. **8.5e-3 够不够**：对 FP16 的 ViT 常见，但最终要等整条管线输出动作后在动作上看。

**③ 引擎 B（VLM 前缀 → KV cache）的导出脚本已写好、还没跑**（`src/vla/export_prefix.py`）。输入 `img_emb [3,64,960]`（直接接引擎 A 输出）、`lang_tokens [1,48]`（int32）、`lang_mask [1,48]`、`state [1,32]`；输出 `k_cache`、`v_cache` 各 [16, 5, 241, 64]。attention mask 和位置编号只依赖 `lang_mask`，放在图里算，原版的 cumsum 改成乘一个上三角全 1 矩阵（TensorRT 一定支持矩阵乘）。和原版的两处不同（导出后会逐层对比）：RoPE 原版用下标赋值写结果，导出会变成 ScatterND，改成 cat，数学上一样；补齐的 token 让它至少能看自己，否则这一整行 softmax 在 FP16 下是 NaN，并通过 V 传给所有 token，真 token 的 K、V 不受影响。提前记下的 FP16 风险：RoPE 的角度最大约 240 弧度，FP16 在 240 附近的精度只有 0.125，所以编 FP16 时 RoPE 也要留在 FP32（**待验证**）。

**④ 引擎 A 的算子按计算量拆开（讲解）**：855 个节点里真正做计算的只有 5 类，其余 Reshape / Transpose / Constant 只是挪数据、摆形状。一张图的路径：像素 [0,1] → [−1,1] → Conv patch embed（[3,512,512] → [1024,768]，约 1.2 GFLOP，本质是每块 768 个像素乘 [768,768] 的矩阵）→ 加位置编码 → 12 层 transformer（约 213 GFLOP）→ post LayerNorm → pixel shuffle（4×4 块拼成一个 token，1024 → 64 个 token、每个 12288 维，只挪数据）→ connector MatMul 12288 → 960（约 1.5 GFLOP）→ 乘 √960。

| 每张图约 215 GFLOP | 计算量 | 占比 |
|---|---|---|
| 线性层 q / k / v / o / fc1 / fc2（每层 1024 × 7.08M × 2 ≈ 14.5 GFLOP × 12） | ≈ 174 GFLOP | ≈ 81% |
| 注意力 QKᵀ、PV（每层 2 × 1024² × 768 × 2 ≈ 3.2 GFLOP × 12） | ≈ 39 GFLOP | ≈ 18% |
| LayerNorm、Softmax、GELU、Add | 很小 | < 1% |

1. **时间在 MatMul，但小算子的时间占比会高于 1%**：它们受带宽限制，时间花在读写显存而不是计算上，具体多少要逐层 profile，**还没测**。
2. **Tensor Core 只用到三成左右**：FP32 226 ms ≈ 2.9 TFLOPS（CUDA core）；FP16 49 ms ≈ 13 TFLOPS，按 64 个 Tensor Core、1300 MHz 估的 FP16 峰值约 42 TFLOPS（**没查文档核实**），还有优化空间。
3. **精度问题只出在 LayerNorm**：ViT 残差流里有少数"离群通道"值到几百，|x − 均值| > 256 时平方超过 65504。另外两个看起来危险的算子没事：Softmax 在 TensorRT 里先减每行最大值；GELU（tanh 近似）里的 x³ 在 |x| > 40 时会变成 inf，但 tanh(±inf) = ±1，正数原样输出、负数输出 0，结果仍正确。
4. **引擎 B 为什么还要再跑一次导出**：上次的脚本虽然加载了整个模型，但只 trace 了 SigLIP + connector，16 层 Llama 从没导出过；参考答案（原版 RoPE 和 mask 下的 K / V cache，存成 `prefix_io.pt`）也要在加载模型的那次运行里算。可以把引擎 C（去噪一步）的导出写进同一个脚本，一次 srun 都导出（还没定）。到了引擎 B，同样几类算子的变化是：LayerNorm 换成 RMSNorm、多了 RoPE、注意力变成 15 个 Q 头配 5 个 KV 头（GQA）。

**⑤ A、B、C 全部在 Orin 上跑通**。先解决一个导出前的问题：checkpoint 里 VLM 文本部分和动作专家存成 **bf16**，transformers 按 config 的 `torch_dtype: bfloat16` 把这两部分建成 bf16（视觉部分是 FP32，所以 A 当初没事）。onnxruntime CPU 版没有 bf16 矩阵乘，TensorRT 8.5 不支持 bf16，所以导出前整体 `.float()`：bf16 的 8 位指数和 FP32 相同、尾数是 FP32 的前 7 位，转成 FP32 只是在尾数后面补 0，值完全不变。

怎么判断 FP16 误差"够小"：同一个模型用原生 bf16 算一遍、用 FP32 算一遍，两者的动作差距就是模型在自己训练精度下本来就有的误差，叫**噪声底线**。TensorRT FP16 的端到端误差只要不超过它，就说明 FP16 没有带来超出模型本身的精度损失。这比凭经验定一个 1e-2 之类的阈值更有依据，因为阈值随模型和输出范围变（动作范围约 ±1.7）。

| 引擎 | FP32 | FP16 方案 | 留 FP32 的部分 | FP16 单引擎误差（rel_l2） |
|---|---|---|---|---|
| A 视觉（SigLIP + connector） | 224.7 ms | 48.3 ms | LayerNorm | 8.5e-3 |
| B 前缀（16 层 Llama → KV cache） | 29.2 ms | 8.6 ms | RMSNorm、RoPE | k 1.8e-3，v 2e-3 |
| C 去噪一步（动作专家） | 8.2 ms | 3.78 ms | 无 | 2.3e-3 |
| 每次观测 A + B + C×10 | ≈ 336 ms | ≈ 95 ms |  |  |

Orin，GPU 锁 1300 MHz，延迟为 CUDA Graph 下的中位数。

| 端到端动作（B → C×10，和 PyTorch FP32 比） | rel_l2（样本 1 / 2） | max_abs |
|---|---|---|
| TensorRT FP32 | 4e-6 | — |
| TensorRT FP16 方案 | 3.9e-3 / 4.9e-3 | 7e-3 |
| 噪声底线：PyTorch 原生 bf16 | 6.2e-3 / 9.6e-3 | ≈ 1e-2 |
| 只把 RMSNorm 留 FP32（RoPE 仍 FP16） | 样本 2：1.26e-2 | — |

1. **B 直接全 FP16 为什么错（rel_l2 0.97）**：和 A 的 LayerNorm 是同一个问题。RMSNorm 要先算 x² 的平均，Llama 的隐藏层里有很大的值，平方后超过 FP16 最大值 65504 变成 inf，整行归一化就坏了。RMSNorm 留 FP32 后单引擎误差降到 4e-3。
2. **只修 RMSNorm 还不够**：第二个样本的端到端误差 1.26e-2，超过噪声底线，而且是 K 的误差偏大。RoPE 用位置 × 频率得到旋转角度，最大约 240 弧度，FP16 在 240 附近相邻两个数相差 0.125，角度误差这么大时 cos / sin 就不准了。RoPE 也留 FP32 后 K 的误差减半，端到端降到底线以下。
3. **怎么确认是 RoPE**：RoPE 只作用于 Q、K，V 不经过它。改完之后 K 的误差变了、V 的没变，正好对上；如果是别的层的问题，V 也应该跟着变。
4. **代价**：两步共 594 个节点留 FP32，延迟只多约 0.2 ms。这些都是逐元素或规约的小算子，时间在矩阵乘上，矩阵乘仍走 FP16 Tensor Core（和 A 的情况相同）。
5. **下一步看哪**（**没做逐层 profile**）：C 跑 10 步共约 38 ms，是最大的一块；每步约 10 GFLOP 却要 3.78 ms，只有约 2.6 TFLOPS，大概率卡在 kernel 启动和小矩阵乘上。可做的：把 10 步整个录成一个 CUDA Graph；cross-attn 层的 K/V 投影只依赖 B 的输出、10 步里都一样，可以挪进 B 只算一次。A 的 48 ms 排第二。

还没做：选 FP32 节点的脚本是临时的，还没做成可复用的构建脚本。
