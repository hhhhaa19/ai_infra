# 环境与工程构建：Quest、Orin、CUDA、CMake

**这一模块讲什么**：一段代码要变成能运行的程序，需要找到正确的编译器、头文件和库。下面按实际顺序走一遍：先准备环境，再写规则、生成构建文件、编译，最后运行。纯 C++ 推理不需要 PyTorch。

## 先分清几个软件各管什么

GPU 驱动管理硬件；CUDA Toolkit 提供 `nvcc`、头文件和运行库；TensorRT 提供推理优化接口。`g++` 是 GCC 的 C++ 编译器。`.cu` 文件由 `nvcc` 处理，它在编译时也会调用主机的 C++ 编译器。

## 第一步：准备环境

登录服务器后，shell 默认找不到我们需要的编译器和 SDK。`module load` 选择集群提供的工具，`source` 项目脚本设置自己安装的 SDK 路径。它们修改的是当前 shell 的环境变量，并没有安装软件。因为只影响当前 shell，所以 `source x.sh | tail` 这种写法没用：管道让脚本在子 shell 里执行，子 shell 结束后环境就没了。

这些路径各有用途：`PATH` 用来找命令；include 目录用来找头文件；link 配置决定链接哪些库；`LD_LIBRARY_PATH` 是运行时找动态库的来源之一；`CUDA_ROOT` / `TENSORRT_ROOT` 是这个项目自己约定的变量。

## 第二步：用 CMakeLists.txt 写规则

编译一个 TensorRT 程序要写很长的命令，文件多了很难手动维护，所以把规则写进 `CMakeLists.txt`：有哪些目标、用哪些源码、头文件在哪、链接哪些库。`add_executable` 只是登记一个目标，不会马上编译。`add_cuda_example` 是本项目写的辅助函数，不是 CUDA API。

什么时候要改这个文件？只改函数内容时，不用动它，直接构建；新增一个独立程序时，要先加目标；换工具链时，用一个新的构建目录。

## 第三步：配置，生成构建规则

运行 `cmake -S . -B build-gcc`。CMake 读取 `CMakeLists.txt`，检查工具链，生成 Makefile，并把找到的路径缓存到 `CMakeCache.txt`。这一步不编译代码。`build-gcc` 只是目录名，不会因为名字里有 gcc 就选 GCC；实际用哪个编译器要看配置结果，所以 `g++ --version` 也不能证明 CMake 用的是它。

GPU 架构也在这里决定：`CMAKE_CUDA_ARCHITECTURES=80` 对应 A100，`87` 对应 Orin。它选择的是设备代码的目标架构，和 Slurm 实际分到哪张卡是两回事。`-D` 只设置配置变量，也不会帮你安装 SDK。

## 第四步：编译和运行

运行 `cmake --build build-gcc --target X`，CMake 调用 Make，Make 再调用 `nvcc`、`g++` 和链接器，生成程序。如果只保存了源码却没有构建，运行的还是旧二进制。GPU 程序还要在分配到的 GPU 节点上运行，不能在登录节点上跑。

```text
【Quest 作业】
squeue -u "$USER"
srun --account=p53267 --partition=gengpu --gres=gpu:a100:1 --constraint=pcie ... --pty bash
srun --jobid=实际ID --overlap --ntasks=1 --pty bash -l     # 附加到已有作业
非交互 srun 用 bash -lc "..."，module 才可用

【Orin 锁频 / 恢复】
sudo nvpmodel -m 0 && sudo jetson_clocks       # 测前
sudo jetson_clocks --restore                   # 测完
```

## 把配置和构建再拆开看

运行 `cmake -S . -B build` 时命令里不用写文件名：`-S` 给源码目录，CMake 自己在里面找固定名字的 `CMakeLists.txt`，大小写不能错；`-B` 给构建目录，不存在就创建。CMake 会把这个文件当脚本从头到尾执行一遍，主要做四件事：

1. **检查编译环境**：`project(... LANGUAGES CXX CUDA)` 去找 `g++` 和 `nvcc`，并试编译一个小程序。
2. **查找依赖**：`find_package(CUDA)` 找头文件和库在哪，找不到就报错，不会下载或安装。
3. **记录目标和关系**：`add_library`、`target_link_libraries` 只是记下"这个 .so 由哪些文件编译、链接时带哪些库"，这时还没有编译或链接。
4. **生成规则**：把这些信息写成具体命令，放进 `build/` 里的 Makefile 或 build.ninja。

所以 `build/` 是第一条命令创建的，但里面还没有成品。`cmake --build build` 才调用 make / ninja，再由它们调用 `nvcc`、`g++`，这时才真正编译和链接。改了 `.cu` 或 `.cpp` 后只要再跑第二条，它只重编改动过的文件；改了 `CMakeLists.txt`，第二条通常也会自动重新配置。找到的路径缓存在 `build/CMakeCache.txt`，环境变了（比如换 CUDA 版本）却还用旧路径时，可以删掉 `build/` 重新配置。

## 库：.a、.so 和 dlopen

配置里声明的目标有两种：`add_executable(app main.cpp)` 生成可执行文件，`add_library` 生成库。库的类型由第二个参数决定，生成的文件名前缀 `lib` 和后缀是 CMake 按 Linux 惯例加的。不写类型时由 `BUILD_SHARED_LIBS` 决定，没设置就生成静态库。

| 写法 | 文件 | 代码什么时候进入程序 | 改了库以后 |
|---|---|---|---|
| `add_library(foo STATIC a.cu)` | `libfoo.a`（静态库） | 链接时拷进可执行文件，运行时不再需要 .a | 要重新链接程序 |
| `add_library(foo SHARED a.cu)` | `libfoo.so`（动态库） | 运行时才加载：链接时写 `-lfoo` 则启动时自动加载；或程序自己调 `dlopen` | 换掉 .so 即可 |

为什么 plugin 必须是 `.so`？`trtexec` 是 NVIDIA 编译好的程序，不知道 RmsNorm 存在，也不可能再把代码链接进去，只能在运行时接收路径：`trtexec --onnx=model.onnx --plugins=librmsnorm_trt_plugin.so`。打开 `.so` 时，系统初始化里面的全局变量，`REGISTER_TENSORRT_PLUGIN` 定义的全局对象构造时把 creator 注册给 TensorRT，之后 Parser 才找得到它。所以 trtexec 一行代码没改，就能用上我们的算子。`.a` 只是给链接器用的归档文件，不能用 dlopen 打开。`build_engine.cpp` 的源码在自己手里，所以链接时带上或 dlopen 都可以。

```text
void* h = dlopen("./librmsnorm_plugin.so", RTLD_LAZY);   // 运行到这一行才打开文件，编译时不用知道这个库
```

## 三个平台的环境

这些步骤在不同平台上都一样，只是环境入口不同。Quest 做 C++ / TensorRT 和 PyTorch 交叉验证，Orin 是主力平台。Orin 上的 torch 2.1 wheel 没有 Triton，所以 `torch.compile` 跑不了，profiler 也抓不到 GPU kernel。

| 平台 | 怎么进入 | 要点 |
|---|---|---|
| Quest（C++ / TensorRT） | module load + source env_tensorrt.sh | GCC 11.2、CUDA 12.4、TensorRT 10.9；build-gcc 构建目录 |
| Quest（PyTorch） | source scripts/env_quest.sh | 共享 conda 环境 aiIfa：torch 2.14.1+cu130、Triton 3.8.0；加载 cuda/13.0、gcc 12.4、ninja；不要往共享环境里 pip install |
| Orin | source ~/venvs/ai_infra/bin/activate | JetPack 5.1.2、CUDA 11.4；NVIDIA 的 Jetson torch 2.1 wheel（无 Triton，profiler 抓不到 GPU kernel）；测性能前必须锁频 |

## 出错时怎么排查

按这个流程想：先看是配置、编译、链接还是运行阶段报错，再对应查找。这些是实际踩过的问题：

| 现象 | 阶段 | 原因和处理 |
|---|---|---|
| `NvInfer.h` / `kWARNING` 找不到 | 编译 | 大小写必须正确 |
| CXXABI 链接错误 | 链接 | 编译器和 C++ 标准库版本不一致，用 GCC 11.2 重新配置后通过 |
| `ofstream` incomplete type | 编译 | 缺少 `#include <fstream>` |
| 环境脚本好像没生效 | 环境 | `source x.sh \| tail` 在子 shell 里执行，环境不会留下 |
| 改了被 include 的 `.cu`，torch 扩展不重编 | 构建 | `load()` 只看列出的源文件，把依赖文件的哈希放进编译选项 |

## 代码怎么同步

Orin 和 Quest 都不存 GitHub 凭据。流程是：在 Orin 提交，由你自己 `git push`，Quest 再用 `git pull --ff-only` 更新。提交身份用 `git config --global user.name / user.email` 设置，它只是署名，不等于远端认证。

## 面试要求

### 必须会

- CMake 的"配置"和"构建"是两步：配置执行 CMakeLists.txt、找依赖、生成构建规则；构建才调用编译器和链接器。
- 静态库 `.a`（链接时拷进程序）和动态库 `.so`（运行时加载 / `dlopen`）的区别；为什么 TensorRT plugin 必须是 `.so`。
- `-arch=sm_80` / `sm_87` 是什么，为什么 A100 和 Orin 要分别编译。

### 应该会

- 常见报错的排查顺序：找不到头文件（include 路径）→ 找不到符号（链接哪个库）→ 运行时找不到 `.so`（`LD_LIBRARY_PATH` / rpath）→ 版本不匹配（CUDA / 驱动 / TensorRT）。
- 两类平台各自的限制：集群（Slurm，登录节点不跑 GPU）和 Jetson（JetPack 决定 CUDA / TensorRT 版本，不能随便升级）。

### 加分

- `target_link_libraries` 的 PUBLIC / PRIVATE、生成器表达式、CMake 的 CUDA 语言支持。
- 容器能换什么、不能换什么（换得了 Python / 库，换不了驱动和 JetPack）。
