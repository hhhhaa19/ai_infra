*模块 6*

# 性能测量：基线、对照与轮次波动

**这一模块讲什么**：结果正确后，怎样测量性能、定位瓶颈。先定义测的是什么，再排除干扰，然后看实验结果，最后总结成规则。

## 第一步：先想清楚测的是哪段时间

性能数字要先说清楚测的是什么。`enqueueV3` 只是把任务提交给 GPU，CPU 很快就返回，所以不能只计 CPU 调用耗时。我们用 CUDA event：在 stream 上放两个事件，测它们之间的区间，也就是 GPU 这一段。这段时间可能包含提交不足造成的空隙。

测 kernel 时有两种方式。**single** 用事件包住一次 kernel 并等待；**batch** 包住连续 N 次同流 launch，再除以 N。batch 是均摊值，它的 P95 不是单次的 P95，所以两者不能直接比。nearest-rank P95 的取法是：200 个样本排序后取第 190 个（索引 189）。

## 第二步：排除干扰

只测一次的数字不可靠，所以要多层重复，每一层防一种干扰：每个样本连续 N 次前向再除以 N，减少计时点误差；30 个样本取中位数，防止偶发打断；3 轮交替顺序，防止先测的吃亏；3 个独立进程，防止整次运行偏快或偏慢。保留全部轮次，报告稳定区间和异常，不只挑最快值。

还要分清几种状态。重复用同一份输入会享受硬件缓存，构建、启动、稳态耗时要分开报告。Timing Cache 是构建 engine 时的实现计时信息，不是推理结果缓存。

## 第三步：看工具时别误读

GPU-Util 和 occupancy 都不等于有效算力效率。时间线上 `cudaStreamSynchronize` 的长条表示 CPU 在等 GPU；GPU 上的空档也可能是 GPU 在等 CPU。

nsys 的数据要分开看：kernel 执行时间由 GPU 记录，可信，可以用来算占比；整层墙钟时间被每次发射的拦截开销拉长，不能用来报加速比。所以 nsys 用来找瓶颈，计时用 CUDA event。

## 四层工具怎么配合

前面实验用到的工具分别回答不同的问题。一般顺序是：先用 CUDA event 确认差距有多大，再用 nsys 找瓶颈在哪；问题在 kernel 内部时用 ncu 看原因，最后看 SASS 确认编译器到底生成了什么，改完再用 CUDA event 验证。

| 工具 | 回答什么 | 典型用法 | 不能用来做什么 |
|---|---|---|---|
| CUDA event | 这一段实际要多久 | 比较快慢，算优化百分比 | 解释为什么慢 |
| nsys | 时间花在哪，CPU 和 GPU 谁在等谁 | 看时间线、每个 kernel 的时间、算占比 | 报整层加速比 |
| ncu | kernel 内部为什么慢 | 看带宽、stall、cache、活跃线程 | 测实际耗时（默认冷缓存、基础频率，kernel replay 还会打乱 L2） |
| SASS（机器码） | 编译器到底生成了什么 | 数 `LDG`，确认 `LDG.E.128`、循环有没有展开 | 知道运行时发生了什么 |

为什么 nsys 不能报整层时间？它要记录每次 CUDA 调用，CPU 每发一个 kernel 都多了拦截开销。kernel 的执行时间由 GPU 记录，不受影响；但 decode 时 GPU 本来就在等 CPU，CPU 一变慢，整层时间就被拉长。所以 nsys 下 decode b1 / b8 是 −23% / −20%，CUDA event 下是 −10% / −2%：kernel 少了 10 个，每个 kernel 在 nsys 下省得更多，收益就被放大了。

CUDA event 在 stream 上放两个时间点，测的是中间这一整段，不只是 kernel 的执行时间。GPU 在等 CPU 发下一个 kernel 时，空等也算进去。这正是整层测速要的，因为用户感受到的就是这段时间；只想要单个 kernel 自身的时间，就看 nsys 的 kernel 时间。

```text
【例一：own 为什么比 CUB 慢】
CUDA event：发现 own 慢
ncu：       CUB 的 eligible 更低却更快，推翻"更多 warp 就绪"的猜测
SASS：      own 3 条 LDG，CUB 39～105 条，定位到循环展开
改成 own_t：再用 CUDA event 确认追平 CUB

【例二：decode 的问题】
CUDA event：整层有多快
nsys：      wall 远大于 kernel 合计 → GPU 在等 CPU，问题不在 kernel 内部
```

PyTorch 自己还有一层工具。它们不替代上面四个，而是多了"PyTorch 视角"：nsys 告诉你 GPU 上跑了什么，`torch.profiler` 告诉你这是哪一行 PyTorch 操作产生的。所谓"看 GPU kernel"，就是知道一次 forward 实际启动了哪些 kernel、各跑了多久、grid 和 block 多大，"少 10 个 kernel 省约 141 μs"就是这样数出来的。

| 工具 | 回答什么 | 我们用过吗 |
|---|---|---|
| `torch.profiler` | 每个 PyTorch 操作调了哪些 kernel，kernel 的 GPU 时间和 grid / block | Quest 上用过；Orin 抓不到 GPU kernel |
| `torch.cuda.Event` | 一段 GPU 时间，也就是 CUDA event | 一直在用 |
| `torch._dynamo.explain` | 图有几段、有没有 graph break、原因是什么 | 用来查 graph break |
| `TORCH_LOGS` | 打印 compile 各阶段的图和生成的代码 | 讲过，用法见模块 8 |
| `inductor_cache` | 生成的 Triton 源码、`.ptx`、`.cubin` | 读过，发现融合 kernel 不写 h |
| `torch.cuda.memory_allocated` 等 | PyTorch 申请了多少显存 | 还没用过 |

```text
from torch.profiler import profile, ProfilerActivity
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA]) as prof:
    layer(x)
print(prof.key_averages().table(sort_by="cuda_time_total"))

PyTorch 里 kernel 从哪来       → torch.profiler
torch.compile 有没有切断图      → torch._dynamo.explain
compile 把算子融合成了什么      → TORCH_LOGS=output_code 或 inductor_cache
PyTorch 里实际要多久            → torch.cuda.Event
不在 PyTorch 里（如 TensorRT）  → nsys、trtexec --dumpProfile
```

`torch.profiler` 要通过 CUPTI（NVIDIA 的 CUDA 性能分析接口）拿 kernel 记录。NVIDIA 的 Jetson torch 2.1 编译时没带上这部分，所以 Orin 上能看到 `aten::mm` 这样的 CPU 操作，看不到 GPU 上运行了什么。这是 wheel 的打包问题，不是 GPU 不支持（依据是实测和排查，没有查 wheel 的编译配置）。nsys 是独立工具，不经过 PyTorch，所以能用；kernel 也照常运行，只是 profiler 拿不到记录。

| 工具 | Quest | Orin |
|---|---|---|
| `torch.profiler` 看 GPU kernel | 能 | 不能 |
| `torch.cuda.Event` 计时 | 能 | 能 |
| nsys | 应该可以，没试过 | 能，一直在用 |
| ncu | 报过 `ERR_NVGPUCTRPERM`（权限不够） | 能（有 sudo） |
| `torch._dynamo.explain` | 能 | 能 |
| `torch.compile` 实际运行 | 能 | 不能，没有 Triton，所以 `output_code` 和 `inductor_cache` 也用不了 |
| TensorRT + trtexec | C++ 环境有 TensorRT 10.9 | 能，主力平台 |

所以 Quest 做 compile 对比，用 profiler 数 kernel、CUDA event 计时；Orin 做开发和 TensorRT，用 nsys + NVTX 把 kernel 归到模块、CUDA event 计时、ncu 看 kernel 内部。

## 最后：从这些实验里总结的规则

每次实验都按这个顺序做。先保证正确，再测性能：用 float64 做参考，输出先写 NaN，再逐元素比对，这样漏写和算错都能发现。测量时 Orin 要锁频，并记录开始和结束频率；比较要在同一次运行内进行，关键结论再用 3 个独立进程确认。

结果出来后算有效带宽和峰值比。超过峰值说明数据还在 L2（Orin 约 3.5 MiB），这类形状要单独列出来。解释时要记住工具条件不同：bench 是热缓存、最高频率；ncu 默认冷缓存、基础频率，kernel replay 还会打乱 L2；nsys 会放大发射开销。最后，静态指令条数不是动态执行次数，加载指令少也不代表读的字节少。

## 面试要求

这是区分"做过"和"跑过"的关键模块，面试官很喜欢追问"你怎么测的"。

### 必须会

- 先想清楚测的是哪段时间：GPU kernel 时间、含拷贝的请求时间、端到端时间，不能混在一起比。
- 排除干扰：锁频、预热、多次取中位数、多进程重跑看波动；Jetson 上 `jetson_clocks`。
- 四层工具的分工：CUDA event（量多久）→ nsys（时间花在哪）→ ncu（kernel 内部瓶颈）→ SASS（编译器生成了什么）。
- 至少一次"工具误导"的例子：nsys 会放大 CPU 启动开销（报告的 −20% 实际是 −10%），用不带工具的计时纠正。

### 应该会

- ncu 的关键指标：吞吐率（SM / 内存占峰值百分比）、占用率、warp stall 原因（long / short scoreboard、barrier、math pipe throttle）、bank conflict、sector / request。GEMM 里完整用过一遍，见[模块 11"为什么变慢"](m11.md#m11-s16)。
- Roofline：计算强度、拐点，判断访存密集还是计算密集。
- L2 缓存对测量的影响（数据量小于 L2 时测得偏快；Orin 可用 L2 约 3.5 MiB）。

### 加分

- 用 SASS 验证编译器行为（循环有没有展开、有没有生成 `LDS.128` / `LDG.128`）。
- 统计意义：波动多大时结论才可信、要报几次运行。

## 自测

- 为什么不能只计 enqueueV3 的 CPU 调用耗时？batch 的 P95 为什么不能和 single 的 P95 比？
- 为什么第一轮慢不能直接归因于 block 大小？下一次实验要记录哪些状态？
- 为什么 CUB 的 Eligible 更低、No Eligible 更高，却仍更快？long_scoreboard 84% 能否当成 84% 时间停工？
- 有效带宽超过 DRAM 理论值说明什么？为什么未解问题可以留档而不阻止进入下一阶段？
- CUDA event、nsys、ncu、SASS 各回答什么问题？nsys 的 kernel 时间可信吗，什么数字不可信，为什么？
- CUDA event 测的是 kernel 的执行时间吗？GPU 空等 CPU 算不算进去？
- Orin 上 `torch.profiler` 抓不到 GPU kernel 是什么原因？kernel 还在运行吗？哪些 PyTorch 工具在 Orin 上还能用？
