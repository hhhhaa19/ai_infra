# torch.compile、融合与 CUDA Graph：整层对照里学到的

**这一模块讲什么**：生产里真正用的是 torch.compile、ONNX → TensorRT，或 eager + 自定义算子 + CUDA Graph。要判断手写算子放进这些路线后还有没有收益，就得先知道时间花在哪，再弄清 compile 每一步做了什么、融合发生在哪、CUDA Graph 省了什么。最后用五次整层对照，把这些原因串起来。

## 第一步：先看时间花在哪里

模型形状是 hidden 2048、16 头、intermediate 5632、FP32。prefill b1 s512 是 `[1, 512, 2048]`，decode b1 是 `[1, 1, 2048]`，decode b8 是 `[8, 1, 2048]`。权重完全一样，变的只是一次送入多少 token。一层约 5100 万参数，FP32 约 205 MB，不管算几个 token，都要把这 205 MB 读一遍。

prefill 时，每个权重要和 512 个 token 各乘一次，约 52 GFLOP（1 GFLOP 是十亿次浮点运算）。A100 FP32 约 20 TFLOPS，所以要约 3 ms。瓶颈是算力。CPU 发 26 个 kernel 约 0.3 ms，这段时间和 GPU 计算重叠，等于没花时间，所以 6 种写法都在 3.6 ms 左右。

decode 的计算量只有 prefill 的 1/512（约 0.1 GFLOP），读完 205 MB 约 140 μs。而 CPU 发 26 个 kernel 约 0.3 ms，比 GPU 干活还慢，GPU 大部分时间在等。所以 token 差 512 倍，耗时只差约 7 倍（3.6 ms 对 0.49 ms）。

这里可以用一个比喻：GPU 是厨师，CPU 是递菜单的服务员。prefill 每道菜做很久，服务员慢一点看不出来；decode 每道菜几微秒做完，总时间几乎由菜单数量和服务员速度决定。

所以每层耗时 ≈ GPU 真正干活 + GPU 空等 CPU。eager 的 RMSNorm 是 pow → mean → +eps → rsqrt → ×scale → ×w，约 5 个 kernel，每发一个，CPU 要跑 Python + dispatcher + launch 约 10～15 μs。换成我们的 1 个后，488 − 347 = 141 μs，÷ 10 个 ≈ 14 μs / 个，和 Orin 上"每少一个 op 省约 15 μs"对得上。**这 −29% 省的是 CPU 时间，不是 GPU 算得更快。**

## 第二步：GPU 上的执行层次

为什么不能多开几条 stream 让它们并行？先看执行层次：

```text
CPU（Python / PyTorch）按顺序发 kernel
  ▼
CUDA stream（默认 1 条）：一条队列，前一个 kernel 跑完下一个才开始
  ▼
一个 kernel = 一个 grid → 很多 block 分配到各个 SM（A100 108 个，Orin 16 个）
                          → 每个 block 很多 thread，每 32 个一个 warp
```

单 stream 上 kernel 之间串行，**并行只发生在一个 kernel 内部**，能不能用满 GPU 要看有多少个 block。decode b1 的 RMSNorm 只有 1 行，一行一个 block 时，整张 A100 只有 1 个 SM 在干活，这就是后来按行数分档要解决的问题。

一层里 norm → attn → add → norm → mlp → add 每步都依赖上一步，多开 stream 也没用。生产中多 stream 用在通信和计算重叠、拷贝和计算重叠。

还有一个关键点：**寄存器的数据活不过一个 kernel**。kernel 结束后，寄存器和 shared memory 就分给下一个，不同 kernel 之间能保留数据的只有显存。这正是融合有价值的原因。

## 第三步：torch.compile 全流程（以 decoder layer 为例）

针对上面的问题，`torch.compile` 负责减少 kernel 数和显存读写。它的过程如下：

```text
第 0 步  准备：load_rmsnorm() → .so 加载 → TORCH_LIBRARY 注册（必须在 compile 第一次调用之前）
第 1 步  torch.compile(model, dynamic=False, mode=...)：只包一层，什么都不做
第 2 步  第一次调用 cmodel(x)：Dynamo 抓图
           · 拦住 forward，逐行读 Python；输入换成 FakeTensor（有形状 / dtype / device，没数据）
           · 每个张量操作记进 FX 图；PyTorch 自带算子自己推形状，我们的算子调 Meta 实现推形状
           · 读到非张量代码（读文件、调编译器、print、依赖张量值的 if）→ graph break
           · 同时记下 guards（这张图成立的前提）
           产出：FX 图（进程内存里的 torch.fx.GraphModule，print(gm.code) 可看）+ guards
第 3 步  AOTAutograd：把 Python 写法翻译成 aten 算子（nn.Linear → aten.t + aten.mm），
           拆成约 200 个核心算子，去掉原地修改；训练时还生成反向图
第 4 步  Inductor：① lowering 把每个 aten 算子改写成循环描述（逐元素 / 规约）
                   ② scheduler 决定哪些循环合进同一个 kernel   ← 融合发生在这里
                   ③ codegen 生成 Triton kernel；矩阵乘交给 cuBLAS（extern_kernels.mm），注意力调 aten SDPA
                   我们的 ai_infra::rms_norm 也被当成外部 kernel：原样调用，不能和前后合并
           产出：一个按顺序调用各 kernel 的 Python 文件 + Triton 源码 + cubin，存在磁盘缓存
第 5 步  （只有 mode="reduce-overhead"）CUDA Graph：预热几次 → 录制整串 kernel（参数、地址）
           → 以后每次先把新输入拷到录制时的固定地址（多一个 multi_tensor_apply kernel），再一次重放
第 6 步  缓存：forward 的缓存 = [(guards, 编译版本), …]，默认最多 8 份（cache_size_limit /
           新版 recompile_limit），超过就退回 eager
第 7 步  之后每次调用：检查 guards → 命中哪份用哪份；都不命中 → 回到第 2 步重新编译（recompile）
第一次调用不是空跑：抓图、编译完以后会用真实输入跑一遍返回正确结果，只是特别慢，所以计时前要预热。
```

这三层各管一件事：Dynamo 决定图**完不完整**，graph break 发生在这里；Inductor 决定 kernel **少不少**，compile+ours 少一次融合就发生在这里；CUDA Graph 决定 CPU **发 kernel 的开销**，decode −57% 来自这里。

Meta 的作用只是推形状，它本身不产生图，也不做融合。每个节点的形状存在 `node.meta["val"]`，Inductor 靠它判断循环长度是否对得上，并给缓冲区分配形状，比如生成代码里的 `empty_strided_cuda((1, 1, 2048), ...)`。

guards 检查的是输入规格，不检查数值：形状（`dynamic=False` 时）、dtype、设备、stride、是否在 no_grad / inference_mode 下，以及抓图时写死的 Python 常量（`self.impl == "ours"`、`self.eps`）。所以权重数值变了不用重编，形状或 dtype 变了才会重编。

aten 算子早就注册好了，为什么还要"翻译成 aten"？因为 Dynamo 记下的是 Python 层面的写法，AOTAutograd 把它换成统一的基础算子，这样 Inductor 只要认识约 200 种。我们的算子本来就是正式注册的，不会被拆开。

## 第四步：融合是怎么判断的

Inductor 先把算子改写成循环，再看哪些循环能合并。以 norm2 为例：

```text
norm2 经过 lowering 以后：
add:    h[i]   = x[i] + a[i]          逐元素，长度 2048
pow:    p[i]   = h[i]²                逐元素，长度 2048
mean:   m      = Σ p[i] / 2048        规约
rsqrt:  s      = 1/√(m + eps)         1 个值
mul:    out[i] = h[i] * s * w[i]      逐元素，长度 2048
→ 遍历的是同一行的 2048 个元素，依赖只在同一行内 → 合成一个 kernel（纵向融合：生产者和消费者合并）
```

能不能融合看两点：循环对得上（处理同一批元素），依赖允许（只用同一位置或同一行的结果）。如果要用别的 block 的结果就不行，因为 block 之间不能直接同步。

融合以后，中间结果要不要写回？这要看外面还用不用。只在组内用，就留在寄存器；外面还要用，也能融合，只是顺手写出去一份。Inductor 对 h 做得更进一步：**宁可重算也不存**。融合 kernel 只写 norm2(h)，最后的残差 kernel 读 x、attn_out、mlp_out 三个输入重新加一次，省一次写和一次读。

有三类融合不了：矩阵乘（cuBLAS 外部 kernel）、自定义算子（黑盒）、规约后接一个不同维度的规约（循环对不上）。TensorRT 也一样，融合发生在 builder 构建 engine 时，plugin 同样是黑盒，形状由 `getOutputDimensions` 提供，作用类似 Meta。想让自己的算子参与融合，两条线的办法相同：**自己把要融合的操作写进同一个 kernel**。

## 第五步：读 Inductor 生成的代码

光推理容易出错，所以要看它实际生成了什么。代码在 `inductor_cache` 里，也可以用 `TORCH_LOGS=output_code` 打印：

```text
inductor_cache/
├── fxgraph/       第 2、3 步结果的缓存（同一张图下次复用）
├── aotautograd/   第 3 步的缓存
├── ft/ vz/ pn/ …  第 4 步生成的 Python 文件，每张图（每种形状 × 每个变体）一个
└── triton/0/<哈希>/  每个 Triton kernel 的中间产物：.source → .ttir/.ttgir → .llir → .ptx → .cubin，.json 记 num_warps 等

decode b1、compile 变体的调用函数（精简）：
triton_red_fused_add_mean_mul_pow_rsqrt_0.run(x, norm1.w, buf1)             # norm1：6 个运算合成 1 个
extern_kernels.mm(buf1, Wq/Wk/Wv, out=buf2/3/4)                             # cuBLAS（kernel 列表里的 gemv2T_kernel）
buf5 = torch.ops.aten._scaled_dot_product_efficient_attention(...)          # 注意力
buf10 = buf4; extern_kernels.mm(buf6, Wo, out=buf10)                        # 复用已经用不到的显存
triton_red_fused__unsafe_view_add_mean_mul_pow_rsqrt_1.run(x, buf10, norm2.w, buf12)  # 残差+norm2，只写 norm2(h)
extern_kernels.mm(buf12, Wgate/Wup); triton_poi_fused__unsafe_view_mul_silu_2; extern_kernels.mm(…, Wdown)
buf17 = buf10; triton_poi_fused__unsafe_view_add_3.run(buf17, x, buf16)    # out = attn + x + mlp，原地写
自己看：TORCH_LOGS=output_code python 脚本.py
```

kernel 名是 `triton_<类型>_fused_<被合并的操作>`：red 是规约，poi 是逐元素。注释里的 `Original ATen: [aten.pow, aten.mean, …]` 就是第 3 步翻译出的算子。

融合 kernel 是**两遍循环**：第 1 遍读 x、attn_out 求平方和，第 2 遍再读一次，`eviction_policy='evict_last'` 让数据留在缓存。我们把数据存在寄存器里只读一次，所以当时变慢的原因不在读写量。`.json` 里两个 RMSNorm kernel 都是 `num_warps=16`（每行 512 线程）；`triton_meta` 里 `tt.divisibility 16` 表示指针 16 字节对齐，于是自动生成 128 位读取。

这里有一个教训：我最初说"融合 kernel 写出 h 和 norm2(h)"，后来又说"h 要写回一次"，读代码后发现两种都不对，它根本不写 h。**没读代码前的推断要标明是推断。**

## 补充：怎么自己看 FX 图和 ONNX 节点

先分清两个词。FX 是图的**数据结构**，用节点和连接表示计算；aten 是图里节点的**层级**，也就是 PyTorch 底层算子。所以 FX 图不一定都是 aten 层：Dynamo 抓到的图是较高层的 torch 调用（`torch.nn.functional.silu`），AOTAutograd 之后才是 aten（`torch.ops.aten.silu.default`）。不用加新工具，PyTorch 自带日志开关（下面这些命令是讲解用法，没有实际运行过）：

```text
TORCH_LOGS="graph_code,aot_graphs" python src/llama/compile_layer.py <报告目录>
  graph_code    Dynamo 抓到的图，还是较高层的 torch 调用
  aot_graphs    AOTAutograd 之后的图，已拆成 aten 算子
  output_code   Inductor 最后生成的代码

FX 图打印出来大致是这样（示意）：
%x : [# users=2] = placeholder[target=x]
%add : [# users=1] = call_function[target=torch.ops.aten.add.Tensor](args = (%x, %y), kwargs = {})
output(%add)

%add                节点名字，也就是它的结果
# users=1           有几个节点用到这个结果
placeholder/output  图的输入和输出
call_function[...]  调用什么算子
args                输入；写 %x 就是引用前面的节点，这样一行行连成一张图

TorchScript 图长这样（Orin 老导出器）：%y = aten::add(%a, %b, %alpha)，有 aten:: 节点，但不是 FX。
```

ONNX 这边，`export_onnx.py` 第 48～56 行已经会加载模型并打印节点。想看全图，就在后面加一行 `print(onnx.helper.printable_graph(m.graph))`，每行有输出名、`op_type`、输入和属性，比如 RmsNorm 那行能看到输入 x、weight 和属性 eps。

## 第六步：CUDA Graph 和计算图的区别

融合之后，还剩 CPU 发 kernel 的开销，这由 CUDA Graph 解决。它和 FX 计算图名字相近，但不是一回事：计算图是先读完菜谱，发现可以合并步骤，把菜谱改短；CUDA Graph 是把改好的菜谱整张交给厨师，不用服务员一道一道递。

|  | 计算图（Dynamo + Inductor） | CUDA Graph |
|---|---|---|
| 是谁的 | PyTorch，处理"张量操作" | CUDA 驱动，处理"kernel 调用" |
| 记录什么 | 有哪些操作、谁依赖谁（`add → pow → mean → rsqrt → mul`） | 一串确定好的 kernel 调用，含参数、显存地址、启动配置 |
| 做什么 | 看整层，合并操作，生成更少更大的 kernel | 录一次，以后一次调用重放整串 |
| 解决的问题 | kernel 太碎、显存来回读写 | CPU 一个个发 kernel 太慢 |
| 要求 | 代码 Dynamo 读得懂，否则切断 | 形状和地址固定，没有 CPU 分支 |
| 我们的表 | compile 列 | compile_cg 列（在 compile 上再加这一步） |

接着是动态形状。`dynamic=True` 时 FX 图和 Inductor 代码可以共用，但 CUDA Graph 录的是具体地址和 grid 大小，所以还是每种形状一个：

|  | `dynamic=False`（我们） | `dynamic=True` |
|---|---|---|
| FX 图 | 每种形状一张（batch、seq 不同都算） | 可共用一张（batch 维记成符号 s0） |
| Inductor 代码 | 每种形状一份，形状是常量（decode b1 文件里 `'xnumel': 1` 是 constexpr） | 共用一份，形状是运行时参数（prefill 文件里 xnumel 是 i32） |
| CUDA Graph | 每种形状一个 | **还是每种具体形状一个**：录的是具体地址和 grid 大小 |
| 代价 | 编译次数多 | kernel 没法针对具体形状专门优化 |

默认 `dynamic=None` 介于两者之间：先按具体形状编译，同一函数又遇到新形状时，把变化的那一维标成动态再编一次。vLLM 的做法是 compile 一次（batch 维动态），再为 1、2、4、8、16… 各录一个 CUDA Graph 存成 map，运行时把实际 batch 补齐到最近一档重放（batch=5 补到 8）。超过最大档（比如很长的 prefill）就不用 CUDA Graph。这和 RMSNorm 的"设计分档"是同一个思路。

CUDA Graph 不是只有 compile 才能产生：

| 产生 CUDA Graph 的方式 | 怎么用 | 我们用过吗 |
|---|---|---|
| CUDA C++ API | cudaStreamBeginCapture → 发 kernel → cudaStreamEndCapture → cudaGraphInstantiate → cudaGraphLaunch | 没有 |
| PyTorch 手动录制 | g = torch.cuda.CUDAGraph(); with torch.cuda.graph(g): …; g.replay() | 用过：sweep_block.py 计时 |
| torch.compile | mode="reduce-overhead" | 用过：compile_cg 列 |
| TensorRT | trtexec --useCudaGraph | 用过：Orin engine 计时（b1 1.31 → 1.25 ms） |

CUDA Graph 只是把已有 kernel 录下来一次发出，**不合并任何 kernel**。不用 Inductor 就没有自动融合，vLLM 的 decode 走 eager + CUDA Graph，所以 `fused_add_rms_norm`、`silu_and_mul` 都是手写的。eager+fused 比 compile 多的那 1 个 kernel，就是 MLP 里没融合的 `silu(gate) * up`。

## 第七步：rows、batch、seq 和生产里的 batching

分档要看形状，所以先把这几个词对应到 kernel 上：

```text
x 的形状 [batch, seq, hidden]，例如 [1, 512, 2048]
           │      │     └ hidden：每个 token 的向量长度 = RMSNorm 的 n（同一模型固定）
           │      └ seq：每个请求有几个 token（decode 时 = 1）
           └ batch：同时处理几个请求
rows = batch × seq = 总 token 数 = kernel 启动的 block 数（一行一个 block 时）

padding：[3, 100, 2048]，A 5 个 + 95 空位、B 100 个、C 1 个 + 99 空位 → 300 行，194 行白算
packing：[106, 2048]，cu_seqlens = [0, 5, 105, 106] → 106 行，没有浪费（vLLM）
```

RMSNorm、投影、MLP、残差都是每行独立计算，packing 后混在一起算也不会读错，因为 RMSNorm 每个 block 只读自己那一行，规约也只在 block 内部。

只有注意力会跨 token。vLLM 用 varlen FlashAttention，每个线程块从 `cu_seqlens` 查出自己请求的范围，只在范围内循环读 k、v，再加因果掩码；decode 时 PagedAttention 按每个请求的块表读 KV cache。边界写在 kernel 的循环范围里，不是算完再屏蔽。padding 写法则要额外传 padding mask。

我们的层用 `F.scaled_dot_product_attention(q, k, v, is_causal=True)`，默认整个 seq 属于同一个请求，也没有 KV cache。要接近生产，得换 varlen 注意力并加 KV cache，FlashAttention 暂时搁置。

两个量各决定一件事：**hidden 决定每行多长**（每线程几个元素、要不要 warp 版）；**行数决定启动多少 block**（行少时 GPU 吃不满，要看延迟，每行需要更多线程；行多时 GPU 满了，block 小一点更好）。同一模型 hidden 固定，行数每一步都在变，所以分档两个都要看。

|  | LLaMA | 我们的 decoder layer |
|---|---|---|
| pre-norm RMSNorm、SwiGLU、线性层无 bias | 有 | 一样 |
| RoPE 位置编码 | 有 | 没有 |
| KV cache | 有 | 没有 |
| GQA | LLaMA-2-70B、LLaMA-3 用 | 没有，每个头都有自己的 k、v |
| 层数 / 权重 | 几十层、训练好的 | 1 层、随机初始化（不影响测速） |

尺寸同 TinyLlama-1.1B（它是 32 头 + GQA，我们 16 头）。vLLM 是推理引擎（框架），不是模型：模型 = 结构 + 权重（菜谱和食材），推理引擎 = 高效跑模型、服务很多请求（后厨运作），PyTorch = 厨具，GPU / CUDA = 灶台。我们做的事在生产里的位置：给推理引擎提供更快的算子，并验证它在模型的一层里有收益。

## 第八步：float4 向量化读写

按行数分档后，kernel 还差一点。Triton 自动生成了 128 位读取，所以我们也让每个线程一条指令读 4 个 float：

```text
float4：CUDA 自带结构体，4 个连续 float（.x .y .z .w），16 字节
一个线程一条指令从显存读 16 字节进自己的寄存器（GPU 内部：显存 → L2 → L1 → 寄存器，和 CPU 无关）

原来（按 float 跨步）：线程0 → 元素 0, 512, 1024, 1536；线程1 → 1, 513, …（每次 1 条 LDG.E，4 字节）
float4（一行看成 n/4 个 float4，按 float4 跨步）：线程0 → 元素 0..3；线程1 → 元素 4..7 …
两种都是合并访问；float4 一个 warp 一条指令读 32 × 16 = 512 字节

template<int BLOCK, int VPT>                       // VPT：每线程几个 float4 = PER_THREAD / 4
__global__ void fusedAddRmsNormVec4(…) {
    const int n4 = n / 4;
    const std::size_t row4 = blockIdx.x * n4;        // 下标单位变成 float4
    const float4* x4 = reinterpret_cast<const float4*>(x) + row4;   // r4、w4、h4、y4 同理
    float4 v[VPT];
    for (i) { c = xid + i * BLOCK;
              if (c < n4) { float4 a = x4[c], b = r4[c];             // 各 1 条 LDG.E.128
                            v[i] = make_float4(a.x+b.x, a.y+b.y, a.z+b.z, a.w+b.w);
                            h4[c] = v[i]; }                          // 1 条 STG.E.128
              sum += v[i].x*v[i].x + v[i].y*v[i].y + v[i].z*v[i].z + v[i].w*v[i].w; }
    …warp 内规约 → shared 规约 → scale：和标量版完全一样…
    y4[c] = make_float4(v[i].x*scale*ww.x, …);
}
n=2048、行少（512 线程）：每线程正好 1 个 float4；行多（256 线程）：每线程 2 个
```

为什么更快？读进来的数据量一样，只是"跑腿次数"少了。每条读指令都有发出、追踪、等待的固定开销。1 行时速度由延迟决定，指令少等待轮数就少；行多时每条指令搬得多，更容易用满带宽。

条件是地址必须 16 字节对齐，否则报 misaligned address。PyTorch 新分配的张量起始对齐，每行开头 = 行号 × n × 4 字节，所以要 n % 4 == 0；切片（比如起始偏 4 字节的连续 view）可能不对齐。C++ 用 `aligned16(p)` 检查 x / r / w / h / y，不满足就退回 own_reg。`rms_norm(…, impl=4)` 用来强制 float4 做测试。最大 n = 1024 × 9 × 4 = 36864。

怎么确认生效？用 `nvcc -cubin` 实例化两个模板，`cuobjdump -sass` 里出现 `LDG.E.128` / `STG.E.128`，条数和预期一致（`rmsNormVec4<512,1>` 读 x、w 各 1 条；`fused<128,4>` 读 8 + 4 条、写 1 + 8 条）。512 线程 × 1 个 float4，和 Triton 的 num_warps=16、每线程 4 个元素是同一个切法。

这和之前的对齐研究是一类问题：n 不是 32 的倍数时，每个请求从 4 个 sector 变 4.4 个。**对齐决定一次能读多宽。**

## 第十步：这些结论是怎么观测到的

| 工具 | 能看到 | 看不到 | Quest | Orin |
|---|---|---|---|---|
| torch.profiler | 每个 PyTorch 操作调了哪些 kernel、每个 kernel 的 GPU 时间、grid / block | kernel 内部 | 能用（这次就用它） | Jetson torch 2.1 编译时没带 CUPTI 部分，抓不到 GPU kernel |
| nsys | 整条时间线：CPU 何时发、GPU 何时跑 / 空等；在驱动层拦截，不依赖 PyTorch | kernel 内部 | 应该可以，没试过 | 一直在用（导出 sqlite + analyze_nsys.py） |
| ncu | 单个 kernel 内部：读写字节、带宽、occupancy、缓存命中 | 整体时间线 | 报过 ERR_NVGPUCTRPERM（权限不够） | 可以（有 sudo） |

profiler 拖慢的是 CPU，不是 GPU。开着它时，kernel 的种类、个数、每个 kernel 本身的 GPU 时间都不变；整层耗时变长，多出来的是 GPU 在等 CPU。所以脚本分两次测：开 profiler 只跑 1 次前向数 kernel，关掉，预热 2 秒，再不开任何工具用 CUDA event 计时。

Orin 上和 GPU / CUDA 相关的软件都要用 Jetson 版（JetPack 5.1.2 自带 CUDA 11.4、TensorRT 8.5.2，NVIDIA 的 torch 2.1 wheel，nsys / ncu）；Python 3.8 是普通的 Ubuntu 20.04 自带版本。原因是 CPU 是 ARM，GPU 集成在芯片里和 CPU 共用内存。分工上，Orin 做开发和 TensorRT，Quest 做需要新版 PyTorch 的 compile 对比。

## 最后：FX 图和 ONNX 的关系

compile 全程留在 PyTorch 里。要脱离 PyTorch 运行，就要走 ONNX，这条路在模块 9 展开。两者的对比是：

|  | FX 图 | ONNX |
|---|---|---|
| 是什么 | PyTorch 内部的 Python 对象 | 标准文件格式（protobuf，.onnx） |
| 存在哪 | 进程内存，退出就没了 | 磁盘，可拷到别的机器 |
| 给谁用 | PyTorch 自己（Inductor 等后端） | 别的推理引擎：TensorRT、ONNX Runtime |
| 算子词汇 | torch / aten（核心约 200 个） | ONNX opset（约 200 个），各家都认 |
| 权重 | 不在图里，运行时从模型取 | 打包进文件（initializer） |
| 自定义算子 | 直接写 torch.ops.ai_infra.rms_norm | 只能写成自定义节点，目标引擎自己提供实现（plugin） |

```text
torch.compile：Python forward → Dynamo → FX 图 → AOTAutograd → Inductor → Triton/cuBLAS → 在 PyTorch 里运行
ONNX 部署：    Python forward → 导出   → ONNX  →             TensorRT 构建 → engine     → 脱离 PyTorch 运行
新版 torch.onnx.export(..., dynamo=True)：通过 torch.export 得到 aten FX 图，再翻译成 ONNX
torch 2.1 的默认导出：TorchScript tracing 真跑一遍，再用 symbolic 翻译成 ONNX（模块 9 用的是这条）

两条线要做的对应：TORCH_LIBRARY 注册 ↔ 导出成自定义节点；Meta 实现 ↔ plugin 的 getOutputDimensions；
CUDA 实现 ↔ plugin 的 enqueue。kernel 原样复用，只换外面的壳。
```

## 面试要求

### 必须会

- torch.compile 流程：Dynamo 抓图（FX）→ AOTAutograd → Inductor 生成 Triton / C++ 代码。
- 算子融合为什么快：少读写显存、少启动 kernel；哪些能融合（逐元素、归约尾部）、哪些难（GEMM 前后，一般交给库）。
- CUDA Graph 解决什么：把一串 kernel 录下来一次提交，省掉 CPU 启动开销；和"计算图"不是一回事。
- 你的关键结论：自定义算子作为黑盒，会挡住 Inductor 的 residual-add + norm 融合；写 fused add + RMSNorm 后，整层 GPU kernel 时间追平 Inductor（278.0 vs 276.4 μs），CUDA Graph 下 decode b1 只慢 0.6%。

### 应该会

- 怎么读 Inductor 生成的代码（inductor_cache）、怎么看 FX 图。
- float4 向量化读写的条件（对齐、长度是 4 的倍数）。
- rows / batch / seq 对 kernel 选择的影响；生产中的 batching。

### 加分

- 自定义算子怎么让 Inductor 也能融合（写成 Triton、或提供 decomposition）。
- CUDA Graph 的限制（静态形状、静态地址、不能有 CPU 同步）。
