# 核心算子：Scan（前缀和）

**主线**：scan 求每个位置的前缀和。reduction 只要最后一个总和，scan 要保留每一个中间结果。串行写法是一条长度 n 的依赖链，能并行是因为加法满足结合律、顺序可以重排：先在小范围里算局部前缀和，再把各段拼起来。和 softmax 一样是带宽问题，优化同样沿"分工"（一个 block / 一个 warp / 多个 block）和"算法"（读几遍、几个 kernel）两个方向走。

<a id="m15-s0"></a>

## 结果总览

计时长度 1M、16M、64M 个 int，参考是 CUB 的 `cub::DeviceScan::InclusiveSum` 和同样数据量的 copy（Orin，锁频 1300 MHz，GB/s，括号是占 copy 的比例）。① ② ③ 已完成；④ 只讲了思路，暂不写。

| 版本 | 分工 | 做法 | 能处理的 n | 结果 |
|---|---|---|---|---|
| ① block | 1 个 block | shared memory 里做 Hillis-Steele | n ≤ 1024 | 所有 n ≤ 1024 的长度 PASS（太短，没有计时） |
| ② multi | 多个 block | 三级：局部 scan → block 和 scan → 加偏移 | 任意 | 全部 PASS；1M 30.0（18%）、16M 31.7（16%）、64M 22.0（12%） |
| ③ warp | 多个 block | 每线程 4 个数（int4）+ `__shfl_up_sync` + warp 之间经 shared | 任意 | 全部 PASS；1M 63.0（37%）、16M 68.6（36%）、64M 51.1（27%），比 ② 快 2 倍多 |
| ④ lookback（可选） | 多个 block | decoupled look-back，单个 kernel | 任意 | 只讲了思路（见下面 ④），暂不写 |
| CUB（参考） | — | look-back + 每线程多个数 | 任意 | 1M 138（84%）、16M 159（82%）、64M 159（84%） |

## 定义：inclusive 和 exclusive

```text
输入：      [3, 1, 7,  0,  4,  1,  6,  3]
inclusive： [3, 4, 11, 11, 15, 16, 22, 25]   第 i 个 = in[0] + … + in[i]，包含自己
exclusive： [0, 3, 4,  11, 11, 15, 16, 22]   第 i 个 = in[0] + … + in[i-1]，不含自己，前面补 0
```

两者只差一位：exclusive 就是 inclusive 整体右移一格、前面补 0。reduction 的结果 25 就是 inclusive 的最后一个数。

## 为什么难并行，又为什么能并行

CPU 上只有一行：`out[i] = out[i-1] + in[i]`。每一步都要等上一步的结果，形成一条长度 n 的依赖链，看起来没法并行。

但加法满足结合律：`(3 + 1) + (7 + 0)` 和 `((3 + 1) + 7) + 0` 一样。所以可以先让不同线程各算一小段的部分和，再把这些部分和拼起来——这和 reduction 用树形规约是同一个道理，区别只是 scan 要让**每个位置**都拿到"从头到自己"的和。

测试用 int 而不用 float：浮点加法换顺序结果会差一点，int 可以和 CPU 串行结果逐个精确比较。

## 算法 1：Hillis-Steele（步数少，加法多一些）

每一步，每个位置加上它左边距离为 offset 的那个数，offset 依次是 1、2、4…：

```text
初始：       3   1   7   0   4   1   6   3
offset=1：   3   4   8   7   4   5   7   9    每个数加上左边第 1 个
offset=2：   3   4  11  11  12  12  11  14    加上左边第 2 个
offset=4：   3   4  11  11  15  16  22  25    加上左边第 4 个 ✓
```

- **为什么对**：第 s 步结束后，位置 i 存的是"它自己和左边共 2^s 个数之和"（不够的就到开头为止）。每一步把覆盖范围翻倍，log₂n 步后覆盖了全部。
- **代价**：步数 log₂n（8 个数 3 步），但每步差不多 n 个线程都在做加法，总加法约 n·log n，比串行的 n 次多。
- **和 reduction 的关系**：warp reduction 每步也是"拿距离 offset 的数加过来"，但只关心一个位置的结果；scan 让每个位置都保留结果。

**动画 · Hillis-Steele 逐步演示**：看每一步每个位置从哪里拿数；切到"原地写"看为什么必须先读、同步、再写。

动画：8 个数做 Hillis-Steele scan。每一步 offset 翻倍，每个位置加上左边距离 offset 的数，3 步后得到前缀和。另一种模式演示原地写的数据竞争：如果线程按编号从小到大依次原地累加，会读到这一步已经被改过的值，结果出错。

block 版的标准写法（思路示意，不是仓库里的实现）：

```text
__shared__ int buf[BLOCK];
int t = threadIdx.x;
buf[t] = (t < n) ? in[t] : 0;                 // 越界填 0（加法的单位元）
__syncthreads();
for (int off = 1; off < BLOCK; off *= 2) {
    int v = (t >= off) ? buf[t - off] : 0;   // ① 先读：读的是上一步的结果
    __syncthreads();                          // ② 所有线程都读完
    buf[t] += v;                              // ③ 再写
    __syncthreads();                          // ④ 所有线程都写完，下一步才能读
}
if (t < n) out[t] = buf[t];
```

> 易错
>
> ：写成
>
> buf[t] += buf[t - off]
>
> 一行，读和写之间没有同步，线程 t 可能读到线程 t − off 这一步刚加过的值（上面动画的"原地写"）。两种改法：拆成"读 → 同步 → 写 → 同步"，或者开两块 buffer 轮流读写（double buffer，每步只要一次同步）。另外，越界线程要填 0 而不是不管，且所有线程都要走到
>
> __syncthreads()
>
> ，不能提前 return。

**warp 内**：32 个 lane 本来就同时执行，可以不用 shared memory 和同步，用 `__shfl_up_sync` 从编号小 off 的 lane 拿数：

```text
int x = val;
for (int off = 1; off < 32; off *= 2) {
    int y = __shfl_up_sync(0xffffffff, x, off);   // 拿 lane − off 的 x；lane < off 时拿到的是自己的值
    if (lane >= off) x += y;                      // 所以要判断，不能无条件加
}
```

和 softmax 的区别：softmax 规约要每个 lane 都拿到同一个总和，用 `__shfl_xor_sync`；scan 要每个 lane 拿到不同的前缀和，用 `__shfl_up_sync`。

## 算法 2：Blelloch（加法少，但分两个阶段）

- **up-sweep**：就是一次树形 reduction，沿途把各级的部分和留在数组里（位置 1、3、5、7 存相邻两个的和，位置 3、7 存四个的和，位置 7 存总和）。
- **down-sweep**：把根置 0，从根往下走：每个节点把自己的值交给左孩子，把"自己的值 + 左孩子原来的和"交给右孩子。走到底得到 exclusive scan。
- **代价**：总加法约 2n，和串行同一量级（work-efficient）；但步数是 2·log n，实现也更复杂。
- **GPU 上怎么选**：warp 内 32 个线程本来就同时在算，Hillis-Steele 多做的加法没有额外代价，步数少更快；Blelloch 在数据量大、线程不够用时省加法，教材里出现得多。（没有实测对比。）

## 为什么对：两种算法的证明

两个证明用同一个思路：找一个**每一步结束后都成立的性质（不变式）**，证明每一步都保持它，最后一步时它正好就是答案。记号：`S[a..b]` = x[a] + … + x[b]，下标小于 0 的部分截掉。

**Hillis-Steele**。不变式：offset = d 这一步开始前，`buf[i] = S[i−d+1 .. i]`，即"以 i 结尾、长度为 d 的一段"的和（不够 d 时从 0 开始）。

- 起点 d = 1：buf[i] = x[i]，成立。
- i ≥ d 时，这一步做 buf[i] + buf[i−d] = S[i−d+1..i] + S[i−2d+1..i−d]，两段首尾相接、不重叠，合起来是长度 2d 的一段。
- i < d 时 buf[i] 已经是 S[0..i]，前缀算完了，不能再加——所以只有 i ≥ offset 的线程做加法。
- d ≥ n 时所有位置都是 S[0..i]，即 inclusive scan，共 ⌈log₂n⌉ 步。

证明用的是 **buf[i−d] 这一步之前的值**。如果读到别的线程这一步刚改过的值，长度就不是 d，会重复计数。x = [1, 1, 1, 1] 原地写的一种顺序：offset = 1 时线程 1、2、3 依次读到新值，buf 已经是 [1, 2, 3, 4]；offset = 2 时线程 3 又算 buf[3] + buf[1] = 4 + 2 = 6，x[0]、x[1] 被加了两次。这就是"先读、同步、再写"的原因。

**Blelloch**（n 是 2 的幂；先得到 exclusive，要 inclusive 再加上 x[i]）。把每个长度 2^k 的块用它的最右端代表，L、R 是左右两半的最右端。

- up-sweep 每层做 `a[R] += a[L]`。不变式：做完这一层，每个块的最右端存整块的和。最后 a[n−1] 是总和。
- down-sweep 先把根清零，然后每个块做 `t = a[L]; a[L] = a[R]; a[R] += t`。不变式：处理某层之前，块的最右端存"这个块前面所有数的和"P，而 a[L] 仍是左半段的和。左半段前面的和就是 P，右半段前面的和是 P + 左半段的和，代码正好这样赋值。块长变成 1 时就是 exclusive scan。

```text
[3, 1, 7, 0, 4, 1, 6, 3]
up-sweep   块长 2：[3, 4, 7, 7, 4, 5, 6, 9]
           块长 4：[3, 4, 7,11, 4, 5, 6,14]
           块长 8：[3, 4, 7,11, 4, 5, 6,25]    a7 = 总和
根清零：           [3, 4, 7,11, 4, 5, 6, 0]
down-sweep 块长 8：[3, 4, 7, 0, 4, 5, 6,11]
           块长 4：[3, 0, 7, 4, 4,11, 6,16]
           块长 2：[0, 3, 4,11,11,15,16,22]    exclusive ✓
```

加法次数：up-sweep 和 down-sweep 各 n − 1 次，共约 2n；Hillis-Steele 是 n·log₂n（n = 1024 时约 1 万次，多 5～10 倍，但只有 10 步）。

> 两个证明的共同点
>
> ：只用到结合律，没用交换律（左右两段的顺序始终不变）。所以把加法换成任何满足结合律的运算，scan 都成立：max、min、乘法、矩阵乘法，online softmax 的 (m, d) 合并、FlashAttention 的分块合并也是这一类，所以它们能分块并行。浮点加法不严格满足结合律，换顺序结果可能差最后一位，这也是测试用 int 的原因。

## 大数组：分三级，或者 decoupled look-back

一个 block 最多 1024 个线程，处理不了整个数组，要把数组分段，每个 block 一段：

```text
① 每个 block 各自 scan 自己那一段，同时把这一段的总和（block sum）写到 work[blockIdx.x]
② 对 work[] 再做一次 exclusive scan → 得到每个 block 的"起始偏移"
   （block 太多、work[] 一个 block 装不下时，② 要递归地再分一层）
③ 每个 block 把自己那段的每个数都加上这个偏移

例：n = 8，每段 4 个
  段 0 [3 1 7 0] → [3 4 11 11]，和 11      段 1 [4 1 6 3] → [4 5 11 14]，和 14
  对 [11, 14] 做 exclusive scan → [0, 11]
  段 1 每个数加 11 → [15 16 22 25]，拼起来就是完整的前缀和
```

- **代价**：3 个 kernel，数据读 2 遍、写 2 遍（① 读输入、写局部结果，③ 再把局部结果读回来、加偏移后写）。这对应 softmax 里的"读三遍"：带宽算子多读一遍就慢一截。
- **decoupled look-back**（CUB 的做法）：只用一个 kernel。每个 block 算完自己这段的和就公布出去；然后往前看前面的 block：前一个已经公布了"含前面所有的累计前缀"就直接用，只公布了"自己这段的和"就先加上、继续往前看。不用等前面所有 block 全部完成，数据只读一遍、写一遍。这是这个算子里最难的部分（要处理 block 的调度顺序和内存可见性），列为可选。

测试长度特意选了 1024、1025（刚好超过一个 block）、4097、100003、5000011（block 和多到需要再分一层）。出错时打印第一个错的位置：比如第一个错在 i = 1024，基本就能确定是 block 之间的衔接（② 或 ③）出了问题。

## 实测：① block 和 ② multi

**① block**（一个 block，1024 个线程，shared memory 里 Hillis-Steele）。写 block 版时常见的 6 处错误：

- `__shared__ float [BLOCK] buf;` → `__shared__ int buf[BLOCK];`（类型是 int，方括号在变量名后）。
- 所有线程都读 `X[r]`（r 是 block 起点）→ 用全局位置 `g = r + i` 读，越界补 0。
- 循环写成 `n *= 2` → `offset *= 2`，上限用 BLOCK。
- 条件 `i > offset` → `i >= offset`（offset = 1 时 i = 1 也要加 buf[0]）。
- `__syncthreads()` 放在 if 里，i < offset 的线程走不到 → 所有线程都读（不该加的读 0）、同步、再加、再同步。
- `bur` 拼写；写回也要用 g 并判断边界。

还有两处"只有一个 block 时碰巧没问题"：边界判断用 block 内编号 i 而不是全局位置；循环上限用 n 而不是 BLOCK（offset 超过 BLOCK 后不会再有线程做加法，只是白跑循环和同步）。前者在 scan_local 里改成了全局位置，后者在 scan_local 里改成了 BLOCK（仓库里 scan_block 的上限仍是 n，因为它只处理 n ≤ 1024，结果不受影响）。

**② multi**（三步、三个 kernel，BLOCK = 1024）：

```text
inline bool launch_multi(const int* X, int* Y, int n, int* work, cudaStream_t s) {
    constexpr int BLOCK = 1024;
    int nb = (n + BLOCK - 1) / BLOCK;          // block 数 = sums 的个数
    int* sums = work;                          // 这一层的 sums 放在 work 开头
    scan_local<BLOCK><<<nb, BLOCK, 0, s>>>(X, Y, n, sums);   // ① 局部 scan + 写段和
    if (nb == 1) return true;                  // 只有一段，已经是答案
    launch_multi(sums, sums, nb, work + nb, s);              // ② 对 sums 原地 scan（递归）
    add_offset<BLOCK><<<nb, BLOCK, 0, s>>>(Y, n, sums);     // ③ 第 b 段加 sums[b − 1]
    return true;
}
```

- **为什么拆成 3 个 kernel**：③ 要等所有 block 的 ① 都做完。同一个 kernel 里 block 之间不能互相等：`__syncthreads()` 只管一个 block；64M 时有 6 万多个 block，Orin 一次只放得下几百个，先上去的 block 等后面的、后面的又等前面的让位置，会死锁。同一个 stream 里前一个 kernel 全部结束后一个才开始，kernel 之间就是全局同步点。
- **递归**：n = 2²⁶ 时第一层 65536 个段和，一个 block 处理不了，再调一次 launch_multi：第二层 64 个，一个 block 就够。测试长度 5000011 就是为了走到两层。
- **work**：bench 预先分配的 n + 4096 个 int 当草稿纸；第一层 sums 用 `work[0..nb)`，下一层接在 `work + nb`。不在 launch 里 cudaMalloc，因为它慢（几十 µs 到几 ms，还会让 GPU 等），计时会变成测 cudaMalloc；CUB 的临时空间、cuBLAS / TensorRT 的 workspace 也是调用者分配、库只用。内容不会自动清零，multi 先写后读不受影响，look-back 的标志位要在 launch 里先 `cudaMemsetAsync`。
- **原地 scan 和 `__restrict__`**：递归时 X 和 Y 都是 sums。每个位置由同一个线程先读进 shared、同步后才写回，所以原地没问题；但 `__restrict__` 承诺两个指针不重叠，这里正好违反，所以 scan_local 的 X、Y 不能加。
- 其他易错点：`threadIdx` 少 `.x`、`sums` 拼成 `sum`、X / Y 的 `__restrict__`、`launch_block` 还是 `return false`（函数末尾漏 return 时返回值是随机的，bench 可能跳过、也可能去检查没跑过的结果）。

| n | copy | multi | CUB |
|---|---|---|---|
| 1M | 165 | 30.0（18%） | 138（84%） |
| 16M | 193 | 31.7（16%） | 159（82%） |
| 64M | 188 | 22.0（12%） | 159（84%） |

Orin，GB/s，锁频 1300 MHz。所有正确性长度（1、31、32、33、1000、1024、1025、4097、100003、5000011）block、multi 都 PASS。不锁频时 GPU 可能只跑 306 MHz，计时前要先锁频。

**为什么只有 12～18%**：按读写份数，multi 是 ① 读 X 写 Y、③ 读 Y 写 Y，共 4n 次访问，copy 是 2n，预计约 copy 的 50%。实测远低于这个，说明瓶颈不在显存带宽而在 scan_local 本身。推测的三个原因（**没有用 ncu 验证**）：

1. 同步太多：1024 个线程做 10 轮，每轮 2 次 `__syncthreads()`，共 20 次，每次都要等 32 个 warp 到齐。
2. 每个 SM 只能放 1 个 block（32 个 warp，上限 48 个，放不下第二个），同步时没有别的 block 的 warp 可以切换上来，延迟藏不住——和 GEMM 里占用率低是同一类问题。
3. 每个线程只处理 1 个数，却要做约 10 次 shared 读写，Hillis-Steele 的 n·log n 次加法在这里体现出来。

64M 比 16M 更慢（12% 对 16%），可能和多一层递归有关，没有查。CUB 到 84% 是因为 look-back 只读一遍写一遍、每个线程处理很多个数（先在寄存器里串行累加）、warp 内用 shuffle 基本不用 `__syncthreads()`。

## ③ warp 版：设计和实测

目标是修好 scan_local 自己慢的问题。三步结构不变，显存仍是 4n 次访问，上限还是 copy 的约 50%；剩下一半留给 ④ look-back。参数：BLOCK = 256 个线程，每线程 ITEMS = 4 个数，每个 block 负责 1024 个数。block 内部 5 步（下面的例子假设一个 warp 只有 4 个 lane）：

```text
第 0 步  每个线程用 int4 读连续 4 个数
         lane 0 [3,1,7,0]   lane 1 [4,1,6,3]   lane 2 [2,5,1,1]   lane 3 [0,2,2,4]
第 1 步  线程内串行求前缀（寄存器里，不用同步）
         [3,4,11,11]        [4,5,11,14]        [2,7,8,9]          [0,2,4,8]
         每个线程的总和 v[3]：11, 14, 9, 8
第 2 步  warp 内对总和做 inclusive scan（__shfl_up_sync）
         incl = [11, 25, 34, 42]，excl = incl − v[3] = [0, 11, 25, 34]
第 3 步  lane 31 把 warp 总和写进 warp_sums[warp]，同步；warp 0 对 warp_sums 再 scan，同步
第 4 步  偏移 = excl + warp_sums[warp − 1]（warp > 0），加到 4 个数上，int4 写回
         lane 2：[2,7,8,9] + 25 = [27,32,33,34]
第 5 步  把整个 block 的总和写进 sums[blockIdx.x]
```

- **为什么每线程的 4 个数必须连续**：scan 依赖顺序（只用结合律、不用交换律），线程 t 的数要整段排在线程 t+1 前面，线程内的串行前缀才有意义，不能像 softmax 那样按 `lane + k·32` 交错。连续读也不破坏合并访问：每个 lane 用 int4 读 16 字节，一个 warp 正好连续 512 字节。
- **int4**：`*reinterpret_cast<const int4*>(X + base)` 生成一条 128 位读（`LDG.E.128`），只能读一个起点开始的连续 4 个 int，地址必须 16 字节对齐，不对齐不是变慢而是直接报 `misaligned address`。cudaMalloc 至少 256 字节对齐，段起点是 1024 的倍数没问题；递归时 sums 的起点 `work + nb` 不一定对齐，所以框架里写成 `next = work + (nb + 3) / 4 * 4`。n 不是 4 的倍数时，最后一个线程逐个读写、越界补 0。
- **incl 和 excl**：shuffle 版 Hillis-Steele 自然得到 inclusive；第 4 步要加的是"排在我前面的线程的总和"，即 excl = incl − 自己的总和。加 incl 会把自己的 4 个数算两次（lane 2 会得到 [36,41,42,43]）。lane 31 的 incl 就是整个 warp 的总和，第 3 步用它。线程 → warp → block → 多个 block，每一层都是"先算自己这部分的总和，再加上前面所有部分的总和"。
- **`__shfl_up_sync` 的判断**：lane < offset 时它原样返回自己的值，所以要 `if (lane >= offset) x += y`，否则自己加了两次。
- **对比 ②**：每线程 1 个数 → 4 个（int4）；block 内 shared 10 轮 → 寄存器串行 + shuffle；每 block 20 次同步 → 2 次；每 SM 1 个 block → 6 个（256 线程，受 48 个 warp 上限）；总加法 n·log n → 约 n。

`launch_warp` 是三步加递归，③ 复用 `add_offset<1024>`；`warp_scan_incl` 和 `scan_local_warp` 分 6 步完成（见下面的易错点）。函数限定符：`__global__` 是 kernel（CPU 用 `<<<>>>` 启动、返回 void）；`__device__` 是 GPU 上的普通函数，只能由 GPU 代码调用、可以有返回值；`__forceinline__` 强制展开，避免真正的函数调用（传参、保存寄存器、可能用到 local memory 上的栈）；头文件里的普通函数加 `inline` 是为了被多个 .cu 包含时不报重复定义。

**shuffle 版 Hillis-Steele 为什么对**：`__shfl_up_sync(0xffffffff, x, off)` 让每个 lane 拿"编号比自己小 off 的 lane"当前的 x。它是一条指令，32 个 lane 同时交出、同时拿到，所以拿到的一定是对方这一步加之前的值，shared 版必须的"先读、同步、再写"在这里天然成立，不需要 `__syncthreads()`。8 个 lane 的例子：

```text
初始 x：     3   1   7   0   4   1   6   3
off = 1：    3   4   8   7   4   5   7   9     lane ≥ 1 加上左边第 1 个
off = 2：    3   4  11  11  12  12  11  14     lane ≥ 2 加上左边第 2 个
off = 4：    3   4  11  11  15  16  22  25     lane ≥ 4 加上左边第 4 个
```

off 从 16 往 1 倒着走也对：lane i 最后的值是所有 x[i − d] 之和，d 是从 {16, 8, 4, 2, 1} 里挑若干个加起来，而 0～31 的每个数写成二进制只有一种方式，所以每一项正好加一次，和先后顺序无关；d > i 的项被 `if (lane >= off)` 挡掉。两种顺序只是中间状态不同，习惯上写从 1 往上。

**shuffle 只在调用者自己的 warp 里交换**：`warp_scan_incl` 是每个线程各自执行一遍，lane 是调用者在自己 warp 里的编号；lane 0 往前没有 lane，返回自己的值、被 if 挡掉，不会去拿上一个 warp 的 lane 31。所以三层衔接各用各的办法：warp 内 shuffle，warp 之间 shared + `__syncthreads()`，block 之间多个 kernel 或 look-back。

**第 3 步的两个细节**：warp 0 对 8 个 warp_sums 做 scan 时，32 个 lane 必须全部执行 shuffle（mask 是 0xffffffff），所以 lane ≥ 8 的读 0 陪着算、最后只有 lane 0～7 写回——和 softmax warp 版越界填 −∞ 是同一个思路。两个 `__syncthreads()` 都要写在 `if (warp == 0)` 外面：同步 ① 保证 8 个 warp 都写完 warp_sums，同步 ② 保证 warp 0 写回 scan 结果后别的 warp 才读 `warp_sums[warp − 1]`。

**incl、excl 不会改动 v**：`warp_scan_incl(int x)` 按值传参，传进去的是 v[3] 的副本，shuffle 交换的也是各线程自己的副本 x，v[0..3] 直到第 4 步才被改。第 1 步之后 v[3] 已经是本线程 4 个数的总和，所以 incl 是"包括我在内前面所有线程的总和"，excl = incl − v[3] 不含自己的任何一个数。lane 1 的完整过程（只看 warp 内）：

```text
                       v[0]  v[1]  v[2]  v[3]   incl   excl
第 0 步 读入             4     1     6     3
第 1 步 串行前缀         4     5    11    14
第 2 步 incl = scan(14)  4     5    11    14     25
        excl = 25 − 14                                   11
第 4 步 每个都加 excl    15    16    22    25
```

**warp_sums 和 sums**：warp_sums 在 shared memory，8 个元素，衔接一个 block 里的 8 个 warp；sums 在显存（work 的开头），nb 个元素，衔接所有 block，后面的 kernel ② ③ 要读，所以必须在显存。

**易错**：第 0 步循环里用了逗号（编译不过），而且那个循环把同一个 int4 读了 4 遍，也没处理尾部；第 4 步没处理尾部，会写到 Y 外面（比读越界更危险）；删掉 `launch_warp` 开头的 `return false`；加回 `static_assert(ITEMS == 4)`（代码写死了 v[0]～v[3]）。`-Xptxas -v`：23 个寄存器、0 spill、shared 32 字节。

| n | ② multi | ③ warp | CUB |
|---|---|---|---|
| 1M | 29.8（18%） | 63.0（37%） | 137（81%） |
| 16M | 31.6（16%） | 68.6（36%） | 158（82%） |
| 64M | 22.0（12%） | 51.1（27%） | 159（85%） |

Orin，锁频 1300 MHz，GB/s，括号是占 copy 的比例，同一次运行。所有正确性长度 PASS。

1. **改了什么**：scan_local 从"每线程 1 个数、shared 里 10 轮、20 次同步"换成"每线程 4 个连续的数（int4）、寄存器串行前缀、warp shuffle、2 次同步"。
2. **为什么快**：② 的瓶颈在 scan_local 自己（同步多、每 SM 只能放 1 个 1024 线程的 block、n·log n 次 shared 读写），③ 把这几项都去掉了。

## ④ decoupled look-back 的思路（暂不写）

**要解决的问题**：三级方案里 ③ 必须等所有 block 的 ① 做完，block 之间不能在一个 kernel 里互相等，只好拆成 3 个 kernel，Y 写完还要再读一遍、改一遍。如果一个 block 在写出结果之前就能知道"前面所有 block 的总和"，就只需要读一遍、写一遍。

**想法 1：接力**。block b 等 block b−1 公布"到它为止的前缀和"，加上自己的再公布。这是一条串行链：64M 时 6 万多个 block 依次接力，每一棒都要经过一次显存，加起来比三级方案还慢。

**想法 2：解耦**。关键是一个 block 自己这段的总和不需要等任何人就能算出来。所以每个 block 公布两种信息：

| 状态 | 含义 | 什么时候能公布 |
|---|---|---|
| X | 还没有信息 | 初始 |
| A（aggregate） | 只有我这段的总和 | 段内 reduce 完，很快 |
| P（prefix） | 第 0 段到我这段（含）的全部前缀和 | 知道前面所有段的总和之后 |

```text
block b：
1. 算出自己的总和 agg，马上公布 (A, agg)
2. 从 b−1 往前看：X → 原地等；A → 加到 excl 上、继续往前；P → 加到 excl 上、停
3. 公布 (P, excl + agg)
4. 段内每个数加 excl，写出最终结果

例：4 个 block 的段和 10、20、30、40；某时刻 block 0 = (P,10)，block 1 = (A,20)，block 2 = (A,30)
block 3 往前看：30（A）→ 20（A）→ 10（P，停），excl = 60，公布 (P, 100)
```

block 3 不用等 block 1、2 做完它们的往前看，只要它们算出 A 就行，所以等待链不再贯穿所有 block。

**4 个实现上的坑**：

1. **block 启动顺序不保证**：block 3 在等 block 2，而 block 2 还没被调度上来、SM 又被正在等的 block 占满，就会死锁。办法是不用 blockIdx.x 当段号，每个 block 启动后用 `atomicAdd(&counter, 1)` 领号，号是按实际启动顺序领的，要等的前面的段一定已经在跑或已结束。
2. **状态和值必须一起被看到**：先写值再写状态，别的 SM 可能看到状态已是 A、值还是旧的。把状态和值打包成一个 64 位数一次写入。
3. **等待时必须真的去读显存**：普通的 `while (status == X)` 可能被编译器只读一次放进寄存器，或被 L1 缓存住，永远看不到更新。要用 `volatile` 指针或原子操作读。
4. **每次 launch 前清零**：状态数组和计数器都要是 0，所以 launch 里先 `cudaMemsetAsync(work, 0, …)`。

**和 double buffering 不是一回事**：double buffering 在一个 block 内部，让搬下一块和算这一块重叠；look-back 是 block 之间的通信协议，省掉的是一整个 kernel 和一遍读写。更贴切的类比是加法器：接力像逐位进位，look-back 像跳跃进位。一句话：把"自己的部分"和"依赖别人的部分"拆开，自己的部分先公布，依赖别人的部分往前查到第一个已确定的结果就停。CUB 还让一个 warp 同时往前看 32 个 block、再用 shuffle 加起来。

决定先不写 ④：思路已经讲清，难点在内存可见性和调度细节，调试耗时，而之后的卷积和 attention 用不上它。scan 在 ③ 收尾。

## 推理里用在哪

- **top-p 采样**：概率从大到小排序后求累计和，找到第一个超过 p 的位置，只在它之前的词里采样。
- **MoE 分发**：先统计每个专家分到几个 token，再做一次 exclusive scan，就得到每个专家在连续缓冲区里的起始位置，每个 token 知道自己该写到哪里。
- **stream compaction / radix sort**：每个元素标 0 / 1（留不留、这一位是 0 还是 1），对标记做 exclusive scan，结果就是它该写到的下标。
