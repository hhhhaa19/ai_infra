# 核心算子：卷积与 GEMM，从手算到分块

**主线**：GEMM 从 naive 一步步优化到 cuBLAS 的 85%。每一版只看三件事：**改了什么、为什么快（或慢）、测出多少**，配一个数据流动画。核心思路只有一句：**让数据搬一次、用多次，并且别让硬件干等。**

## 结果总览

Orin，锁频 1300 MHz，FP32，单位 GFLOPS；全部通过正确性检查。

|---|---|---|---|---|
| ① naive | 一个线程算一个 C，直接读全局 | 408 | 12% | — |
| ② shared 分块 | block 合作把 A、B 小块搬进 shared | 614 | 18% | 1.5× |
| ③ 寄存器分块 | 一个线程算 8×8，外积 | 1744 | 51% | 2.8× |
| ④ 交错分工 | 线程隔 16 列取一列，消除 bank conflict | 2091 | 61% | +20% |

| cuBLAS | `cublasSgemm` | 3415 | 100% | — |

- **上限**：Orin 峰值 16 SM × 128 核 × 2 × 1.3 GHz ≈ 5325 GFLOPS；带宽 204.8 GB/s，拐点 ≈ 26 FLOP/字节。大 GEMM 远高于 26 → 理论上是算力瓶颈；2366 约是峰值的 44%，2895 约 54%，cuBLAS 自己也只到 64%。
- ⑦ 和 ⑥ 是同一次运行里对比的（那次 ⑥ 测到 2382，和表里的 2366 是两次运行的差别）；1024³ / 2048³ 下 ⑦ 是 2756 / 2840，占 cuBLAS 87% / 83%。
- **测法**：C 先填 NaN 查漏写；小形状和 CPU double 比、大形状和 cuBLAS 比，rel_l2 < 1e-5；`jetson_clocks` 锁频，预热 5 次、CUDA event 计 20 次取中位数；GFLOPS = 2·M·N·K / 时间。

## 卷积：一个线程一个输出 → shared 分块

和 GEMM 是同一条路，先在卷积上看一遍。一个输出 = 窗口和卷积核对应相乘再相加（C × 3 × 3 次乘加）：

```text
y[o, i, j] = b[o] + Σ_c Σ_u Σ_v  w[o, c, u, v] × x[c, i·s + u − p, j·s + v − p]
权重形状 = 输出通道 × 输入通道 × k × k，例：layer1 是 64 × 64 × 3 × 3

ACT layer1：输入 64×120×160，64 个 64×3×3 核，p=1, s=1
每个输出 64×3×3 = 576 次乘加，总共 64×120×160×576 ≈ 7.08 亿次乘加
```

**朴素版**：一个线程算一个输出。慢在一个输入像素被周围 9 个输出各读一次；同一输出通道 256 个线程用同一组 576 个权重，却各读一遍。

```text
__global__ void conv2d_naive(const float* x, const float* w, float* y,
                             int C, int H, int W, int O) {
    int o = blockIdx.z;                                  // 输出通道
    int i = blockIdx.y * blockDim.y + threadIdx.y;       // 输出行
    int j = blockIdx.x * blockDim.x + threadIdx.x;       // 输出列
    if (i >= H || j >= W) return;
    float sum = 0.0f;
    for (int c = 0; c < C; ++c)
        for (int u = 0; u < 3; ++u)
            for (int v = 0; v < 3; ++v) {
                int hi = i + u - 1, wi = j + v - 1;      // padding = 1
                if (hi >= 0 && hi < H && wi >= 0 && wi < W)
                    sum += w[((o * C + c) * 3 + u) * 3 + v] * x[(c * H + hi) * W + wi];
            }
    y[(o * H + i) * W + j] = sum;
}
dim3 block(16, 16);                               // 16 × 16 = 256 个线程
dim3 grid((W + 15) / 16, (H + 15) / 16, O);       // 盖住整张输出图，z 放输出通道
// layer1：grid = 10 × 8 × 64 = 5120 个 block（120/16 = 7.5 向上取整为 8）
```

**shared 分块**：一个 block 负责 16×16 输出，先合作把 18×18 输入块（多出的一圈叫 halo）和 9 个权重搬进 shared，同步，再从 shared 算。每个输入从读 9 次降到约 1 次。

```text
#define TILE 16
__global__ void conv2d_tiled(const float* x, const float* w, float* y, int C, int H, int W, int O) {
    __shared__ float xs[TILE + 2][TILE + 2];   // 18 × 18 输入块
    __shared__ float ws[9];                     // 一个通道的 3 × 3 权重
    int o = blockIdx.z, tx = threadIdx.x, ty = threadIdx.y;
    int i = blockIdx.y * TILE + ty, j = blockIdx.x * TILE + tx;    // 输出位置
    int i0 = blockIdx.y * TILE - 1, j0 = blockIdx.x * TILE - 1;    // 输入块左上角（含 halo）
    float sum = 0.0f;
    for (int c = 0; c < C; ++c) {
        for (int r = ty; r < TILE + 2; r += TILE)            // ① 256 个线程一起搬 324 个数
            for (int s = tx; s < TILE + 2; s += TILE) {
                int hi = i0 + r, wi = j0 + s;
                xs[r][s] = (hi >= 0 && hi < H && wi >= 0 && wi < W) ? x[(c * H + hi) * W + wi] : 0.0f;
            }
        int t = ty * TILE + tx;
        if (t < 9) ws[t] = w[(o * C + c) * 9 + t];          // ② 前 9 个线程搬权重
        __syncthreads();                                     // 没搬完不许算
        if (i < H && j < W)
            for (int u = 0; u < 3; ++u)
                for (int v = 0; v < 3; ++v)
                    sum += ws[u * 3 + v] * xs[ty + u][tx + v];   // ③ 从 shared memory 算
        __syncthreads();                                     // 没算完不许覆盖 xs
    }
    if (i < H && j < W) y[(o * H + i) * W + j] = sum;
}
```

- halo = 核大小 / 2，输入块边长 = 输出块边长 + 核大小 − 1（3×3 → 18×18，5×5 → 20×20）。
- 库里的做法：im2col + GEMM（展开成矩阵，A 是原输入的 9 倍大）、implicit GEMM（不展开，搬数据时现场算下标，cuDNN / TensorRT 主流）、Winograd（3×3 乘法少 2.25 倍）。所以卷积最终也落到 GEMM。

## ① naive：一个线程算一个 C（408）

```text
__global__ void gemm_naive(const float* A, const float* B, float* C, int M, int N, int K) {
    int i = blockIdx.y * blockDim.y + threadIdx.y;   // C 的行
    int j = blockIdx.x * blockDim.x + threadIdx.x;   // C 的列
    if (i >= M || j >= N) return;
    float sum = 0.0f;
    for (int k = 0; k < K; ++k) sum += A[i * K + k] * B[k * N + j];
    C[i * N + j] = sum;
}
dim3 block(16, 16);
dim3 grid((N + 15) / 16, (M + 15) / 16);   // x 盖 N 列，y 盖 M 行，向上取整
gemm_naive<<<grid, block, 0, s>>>(A, B, C, M, N, K);
return true;                               // 测试台看到 false 会当作"没实现"跳过
```

- **数据流**：每个线程沿 k 读 A 的一行、B 的一列，全部直接读全局内存。
- **为什么慢**：A 的每一行被读 N 次、B 的每一列被读 M 次。每次循环读 8 字节做 2 次运算，计算强度 0.25 FLOP/字节，远低于拐点 26。
- 访问方式本身不差：一个 warp 读 A 是同一地址（广播），读 B 是连续地址（合并）。问题只在同样的数被不同 warp、不同 block 反复读。

## ② shared memory 分块（614，1.5×）

```text
template <int TILE>
__global__ void gemm_tiled(const float* A, const float* B, float* C, int M, int N, int K) {
    __shared__ float As[TILE][TILE], Bs[TILE][TILE];
    int ty = threadIdx.y, tx = threadIdx.x;
    int i = blockIdx.y * TILE + ty, j = blockIdx.x * TILE + tx;     // 全局坐标：带上 block 偏移
    float sum = 0.0f;                                               // 在所有段之外，一直累加在寄存器里
    for (int t = 0; t < (K + TILE - 1) / TILE; ++t) {              // 段数，不是 K
        int ak = t * TILE + tx, bk = t * TILE + ty;
        As[ty][tx] = (i < M && ak < K) ? A[i * K + ak] : 0.0f;      // 越界补 0
        Bs[ty][tx] = (bk < K && j < N) ? B[bk * N + j] : 0.0f;
        __syncthreads();                                            // 没搬完不许算
        for (int k = 0; k < TILE; ++k) sum += As[ty][k] * Bs[k][tx];
        __syncthreads();                                            // 没算完不许搬下一段
    }
    if (i < M && j < N) C[i * N + j] = sum;                       // 最后只写一次
}
```

- **改了什么**：一个 block 负责 C 的 TILE × TILE 块，沿 K 切成每段 TILE 宽。每段：一起搬 A、B 小块进 shared → `__syncthreads()` → 各自从 shared 做 TILE 次乘加 → `__syncthreads()`。
- **为什么快**：每个从全局搬进来的数被 TILE 个线程用，全局读取降到 1/TILE（TILE = 16 → 1/16）。
- **为什么只快 1.5 倍**：naive 的很多读取本来就命中 L1 / L2；而且新瓶颈变成 shared 本身：每次乘加仍要读 2 个 shared 数，读和算 1 : 1。
- **两个同步**：没搬完不许算，没算完不许搬下一段。越界线程不能提前 return，要参加搬运（填 0）和同步。
- **TILE 加大的上限**：一个线程只算一个 C，TILE = 32 已经 1024 个线程，到 block 上限 → 只能让一个线程算多个 C。

**动画 · shared 分块的数据流**：一步一步看"搬进 shared → 从 shared 算"，下面的计数对比全局读取量。

## ③ 寄存器分块：一个线程算 8×8（1744，2.8×）

**核心想法**：一个线程多算几个 C，读进寄存器的数就能重复用。

```text
sum0 += As[i][s] * Bs[s][j]
sum1 += As[i][s] * Bs[s][j+1]        ← As[i][s] 在两行里是同一个数

a = As[i][s]                          ← 读 1 次，存进寄存器
sum0 += a * Bs[s][j]                  ← 读 1 次
sum1 += a * Bs[s][j+1]                ← 读 1 次
算 2 个元素：原来读 4 次，现在 3 次，乘加还是 2 次
```

放大到 8×8，配置是：

```text
一个 block 256 个线程，负责 C 的 128 × 128（BM = BN = 128）
一个线程 8 × 8 = 64 个元素（TM = TN = 8），16 × 16 个线程 × 8 × 8 = 128 × 128
沿 K 每段 BK = 8；shared：As 128×8 + Bs 8×128 = 2048 个 float = 8 KB

for k0 in 0, BK, 2BK…：
  ① 256 个线程合作搬 As[BM][BK]、Bs[BK][BN]（各 1024 个，每人各搬 4 个，越界补 0）→ __syncthreads()
  ② for kk in 0..BK-1：a[0..7] ← As 的一小列，b[0..7] ← Bs 的一小行，c[8][8] += a ⊗ b（外积）
  → __syncthreads()
③ 写回 64 个结果（越界跳过）。启动：dim3 block(256); dim3 grid((N+127)/128, (M+127)/128)
```

- **外积**：每个 kk 从 As 读一小列 8 个数进 `a[8]`，从 Bs 读一小行 8 个数进 `b[8]`，做 `c[m][n] += a[m]·b[n]`。读 16 次、算 64 次，读 : 算从 2 : 1 变成 1 : 4，这就是 2.8 倍的来源。
- **c[8][8] 必须在寄存器里**：TM、TN 要是模板参数、小循环完全展开，下标才是编译期常量，否则会溢出到 local memory（显存）。`-Xptxas -v`：119 个寄存器、0 溢出。
- **搬和算分开**：搬的时候 256 个线程按一维 tid 平分 As、Bs 的 1024 个数；算的时候按二维 (ty, tx) 决定负责哪个 8×8。
- **代价**：寄存器用得多，每个 SM 放的 warp 变少（后面 ncu 看到占用率 33%）。

**动画 · 一个线程的外积**：每个 kk 先读 16 个数进寄存器，再在寄存器里更新 64 个 c。

## ④ 交错分工：消除 bank conflict（2091，+20%）

- **bank**：shared 分 32 个 bank，第 n 个 float 在 bank n % 32，每个 bank 每周期送 1 个 float。一个 warp 里多个线程落在同一 bank 的不同地址 → 排队，几个就几轮。读同一地址是广播，不算冲突。
- **③ 的问题**：每个线程负责**连续 8 列**。要"竖着看"——同一时刻 16 个线程读的是第 0、8、16、24… 列，只落在 4 个 bank → 读 Bs 4 路冲突；读 As 两排 ty 相差 64 个 float → 2 路冲突。

```text
              tj=0  tj=1 ...  tj=7
tx=0  读的列:    0     1  ...    7     ← 横着看：一个线程，连续
tx=1  读的列:    8     9  ...   15
tx=2  读的列:   16    17  ...   23
...
                ↑ 竖着看：同一时刻读 0, 8, 16, 24, 32 ...，bank 只有 0、8、16、24
```

## ⑤ float4 + As 转置：反而变慢（1790，−15%）

- **想法**：既要无冲突，又要像 ③ 那样用 128 位读取。float4 只要求 4 个连续、16 字节对齐，所以每个线程读"两段、每段 4 个连续"：

```text
tx 负责的列 = [tx*4 .. tx*4+3] 和 [64 + tx*4 .. 64 + tx*4+3]
通用：第 q 段第 e 个 = q*(BN/TN)*4 + tx*4 + e      (q = 0..TN/4-1, e = 0..3)
```

```text
float4 v = *reinterpret_cast<const float4*>(&Bs[kk][q*(BN/TN)*4 + j*4]);
b[q*4+0] = v.x;  b[q*4+1] = v.y;  b[q*4+2] = v.z;  b[q*4+3] = v.w;
```

- 硬件按 8 个线程一组处理 float4（8 × 16 字节 = 128 字节），一组正好覆盖 32 个 bank，无冲突。

## 为什么变慢：ncu 和 SASS

- **占用率 33%**：119 个寄存器 × 256 线程，每个 SM 只放得下 2 个 block = 16 个 warp（上限 48），可轮换的 warp 少，延迟藏不住。
- **warp 在等**：每发一条指令平均间隔从 6.21 周期（④）变成 7.75（⑤）。指令少了，但每个 warp 等得更久。L1 吞吐 43～48%、L2 17%：不是带宽不够，是延迟藏不住。

| stall 原因（⑤） | 周期 | 含义 |
|---|---|---|
| long_scoreboard | **1.81** | 等全局内存 |
| short_scoreboard | **1.50** | 等 shared memory |
| math_pipe_throttle | 0.14 | 计算单元忙不过来：很小，离算力上限还远 |

1. **转置写 As 有 8 路冲突**：一个 warp 写 8 行 × 4 列，As 每行 128 个 float，每行起点都在 bank 0 → 只用 4 个 bank。
2. **kk 循环没展开**：SASS 里只有 64 条 FFMA、4 条 `LDS.128`（一次 kk 的量），每次 kk 都是"读 → 等 → 算"串行。

> 瓶颈会转移
>
> ：float4 确实减少了指令，但那时指令数已经不是瓶颈。先用 ncu 的 stall 找最大的一项，再改。

## ⑥ padding + 展开 kk（2366，cuBLAS 的 70%）

**padding**：`As[BK][BM+4]`，每行起点错开 4 个 bank。

```text
写 As 时 bank = (local_j × 132 + local_i) % 32 = (local_j × 4 + local_i) % 32
local_j = 0..7，local_i = 0..3 → 正好 0..31，32 个不同的 bank
```

- **+4 不是 +1**：+1 会让行起点不是 4 的倍数，float4 不对齐。代价只有 32 个 float。
- Bs 不需要：只有写 As 时一个 warp 跨了 8 行。

**动画 · 写 As 的 bank 分布**：切换不加 / +1 / +4。

动画：一个 warp 的 32 个线程把全局 A 转置写进 As[8][128] 时落在哪些 bank；切换不加 padding、加 1、加 4 三种行宽对比冲突。

<a id="anim-pd-root"></a>

> （这里是网站上的交互动画，Markdown 版略去。）

**展开 kk**：`#pragma unroll` 放在 kk 循环上（次数 BK = 8 是编译期常量），不是外层 t 循环。

```text
#pragma unroll
for (int kk = 0; kk < BK; ++kk) {
    ...   // 读 a、b 各 2 个 float4，做 8×8 外积
}
```

- 展开后 SASS 是 512 条 FFMA、32 条 `LDS.128`（8 次 kk），寄存器 119 → 127，无溢出。
- 编译器把下一次 kk 的 LDS 提前到这一次的乘加旁边，读和算重叠；硬件 scoreboard 保证用到数据前会等它到。

**动画 · 展开前后的时间线（示意）**

示意动画：kk 循环不展开时每次 kk 都是读 shared、等数据、做 64 次乘加严格串行；展开后下一次 kk 的读取提前发出，等待被计算盖住。

## ⑦ double buffering：边算这一块，边读下一块（2895，cuBLAS 的 85%）

- **瓶颈**：⑥ 之后最大的停顿是 long_scoreboard（1.81），也就是等全局内存。出在搬数据那一行：`As[..] = A[..]` 先 LDG 读全局，紧接着 STS 写 shared，读完立刻就用，只能干等。搬数据时 block 里所有 warp 都在搬，没有计算可以填进来。
- **关键事实**：GPU 读全局内存不阻塞，LDG 发出后接着执行下一条，**用到那个寄存器时**才等。所以把"读下一块"提前到"算这一块"之前，读的延迟就被计算盖住了。
- **为什么要两份 shared**：算这一块时别的线程还在读 As，不能覆盖。As、Bs 各开两份，一份在算，一份接收下一块，每轮交换。

```text
准备：第 0 块 → As[0]、Bs[0]；__syncthreads();
cur = 0
for t:
    ① if (还有下一块)  ra[4]、rb[4] ← 全局读下一块      // 只发 LDG，不等结果
    ② 用 As[cur]、Bs[cur] 做 8 个 kk 的计算             // 512 条 FFMA，盖住 ① 的延迟
    ③ cur ^= 1;  if (还有下一块)  As[cur]、Bs[cur] ← ra、rb
    ④ __syncthreads();                                  // 每轮 1 次（原来 2 次）
```

**动画 · 有没有 double buffering 的时间线（示意）**：

示意动画：GEMM 沿 K 的 4 轮循环。不用双缓冲时每轮先读全局、等数据、写 shared、同步、再计算；用双缓冲时下一块的读取和这一块的计算同时进行，两份 shared 轮流使用。

|  | 在哪 | 存什么 |
|---|---|---|
| `ra[4]`、`rb[4]` | 寄存器（每线程私有） | 下一块里自己负责搬的 4 + 4 个数（1024 个 ÷ 256 线程） |
| `As[2]`、`Bs[2]` | shared memory | 两份轮流：一份在算，一份接收下一块 |
| `a[8]`、`b[8]` | 寄存器 | 这一块某个 kk 的数据；和 ra、rb 生命周期重叠，不能共用 |

- **③ 必须在计算之后**：放在计算前，STS 要等 LDG 的数据，又退回干等。
- **每轮只要同步一次**：被写的那份 buffer 上一轮算完后已经同步过，不会有人还在读。
- **藏的是"全局 → shared"这一段**，搬运量一点没少。普通指令不能全局直接拷进 shared，必须经过寄存器；Ampere 起的 `cp.async` 可以直拷（没做）。

## 怎么读 ncu：时间账单、占用率、stack frame 和 spill

**核心只有一个概念**：一个 SM 里有 4 个调度器，每个调度器管几个 warp，每个周期从"准备好了"的 warp 里挑一个发一条指令。于是任何一个周期，每个 warp 都正好处在一种状态：**selected**（正在发指令，唯一在干活的状态）、**not_selected**（准备好了，但这拍选了别人）、或某种 **stalled**（在等某样东西，等什么就记成什么）。Warp State Statistics 统计的就是 warp 的时间花在了哪种状态上。

**单位**：`…_per_issue_active.ratio` = 平均每发射一条指令，warp 在这个状态上花了几个周期。各项加起来就是 Warp Cycles Per Issued Instruction，可以当成一张**时间账单**：

```text
selected 1.00 + not_selected 0.65 + wait 0.40 + short 0.39 + barrier 0.12
+ math 0.04 + long 0.02 + mio 0.01 + 没抓的小项约 0.3 ≈ 2.93
```

哪一项最大，就先解决哪一项。

**调度器有多闲**：每个调度器管 W 个 warp，当每个 warp 平均每 W 个周期发一条指令时，调度器刚好每个周期都有活干。所以 **调度器忙碌程度 ≈ W ÷ cycles/指令**。换算链：block 数/SM × 每 block 的 warp 数 = warp 数/SM，再 ÷ 4 = W。注意 W 数的是 warp 不是 block：1 个 block = 256 线程 = 8 个 warp，按编号轮流分给 4 个调度器，每个 2 个。

| 版本 | 每 SM warp 数 | 每调度器 W | cycles/指令 | 调度器忙碌 |
|---|---|---|---|---|
| ④ 交错版 f0b5cd5 | 16 | 4 | 6.21 | 64% |
| ⑤ float4 版 | 16 | 4 | 7.75 | 52% |
| ⑦ 双缓冲版 | 8 | 2 | 2.93 | 68% |

这个顺序和实测速度的顺序一致。它是粗略估计（一条 `LDS.128` 和一条 `LDS` 干的活不一样），用来判断方向够了。也说明**占用率和停顿要一起看**：warp 多可以藏延迟，单个 warp 等得少也可以。

**常见停顿原因对照**：

| 停顿 | 在等什么 | 我们代码里对应 | 常见解决办法 |
|---|---|---|---|
| not_selected | 不等，只是没轮到 | ⑦ 里 0.65 | 不是问题，说明 warp 够用 |
| long_scoreboard | 全局内存（也包括 local memory） | 搬 A、B：LDG → STS | 合并访存、预取（double buffering）、多放 warp；也要查有没有数组掉进 local memory |
| short_scoreboard | shared memory，以及 sin / exp 这类特殊运算 | 读 As、Bs：LDS → FFMA | 消除 bank conflict、寄存器级预取 |
| wait | 固定延迟的依赖 | FFMA 接 FFMA | 让相邻指令互不依赖、多放 warp |
| barrier | `__syncthreads()`，等最慢的线程 | 每轮的同步 | 减少同步次数、让工作量均匀 |
| math_pipe_throttle | 计算单元满了 | 一直很低 | 高了说明接近算力上限，是"好的瓶颈" |
| mio_throttle | shared memory 指令太多，队列排满 | 0.01 | 向量化（`LDS.128`）减少指令数 |
| lg_throttle | 全局内存指令太多，队列排满 | 没测 | 全局读写用 float4 |
| no_instruction | 指令缓存没命中 | — | 代码展开得太大时会出现 |

**拿到 ncu 输出后的顺序**：

1. **SpeedOfLight**：计算、内存各用了百分之多少。计算高 → 算力瓶颈；内存高 → 带宽瓶颈；**两个都不高 → 延迟瓶颈**（我们的 GEMM 一直是这种），才往下看。
2. **Occupancy**：每个 SM 有几个 warp，被什么限制住。
3. **Warp State Statistics**：时间账单里哪一项最大。
4. **定位到代码**：最大那项对应哪段代码，需要时用 SASS 或 bank conflict 指标确认。
5. **改一处，重测，只看针对的那一项有没有降。**

RMSNorm 当时为什么没走到第 2、3 步：它在第 1 步就有答案（带宽瓶颈，看有效带宽和每次请求的扇区数）。带宽到顶之后 long_scoreboard 占大头是正常的，这时只能少搬数据（比如融合），调 warp 没用。不过 RMSNorm 也用过一次停顿分析：查"n 除不尽为什么变慢"时，是靠 barrier 停顿涨了 7 倍和每 warp 活跃线程数 31.6 → 27.7 找到原因的。

**占用率：四个限制取最小**。一个 SM 同时有几种资源，哪种先用完就卡在哪。ncu 的 Occupancy 段把四项都列出来（Orin 每 SM 的数字；A100 是每 SM 64 个 warp，算占用率前先查清是哪种卡）：

| 限制 | 硬件上限（Orin 每 SM） | 能放几个 block | ⑦ 的值 |
|---|---|---|---|
| Block Limit Warps（warp 槽位：硬件要为每个 warp 记住 PC 和状态） | 48 个 warp = 1536 线程，每调度器最多 12 个 | 48 ÷ 每 block 的 warp 数 | 48 ÷ 8 = 6 |
| Block Limit Registers | 65536 个 | 65536 ÷（每线程寄存器 × 每 block 线程数） | 1 |
| Block Limit Shared Mem | 驱动分配的配额 | 配额 ÷ 每 block 用量 | 1 |
| Block Limit SM（block 槽位） | 16 个 block | 固定 | 16 |

- 实际能放的 block 数 = 四个里最小的 = 1 → 8 个 warp → 8 ÷ 48 = 16.67%（实测 16.66%）。
- **"128 这条线"**：要放 2 个 block，每个 block 最多 32768 个寄存器，每线程不超过 128 个。149 × 256 = 38144 > 32768，所以只能放 1 个。（另一种说法：寄存器按 warp 分配、每线程用量向上取整到 8 的倍数，149 算成 152；这一点没查文档。）
- 反例：每线程只用 32 个寄存器、几乎不用 shared 时，寄存器够放 8 个 block，但 warp 槽位只够 6 个，占用率 100%，卡在 warp 槽位上。
- **Shared Mem 这一行也是 1，和预期不一样**：每 block 只用 16.6 KB。推测：L1 和 shared memory 共用一块存储，驱动自动选了较小的 shared 配额，可以用 `cudaFuncSetAttribute(…, cudaFuncAttributePreferredSharedMemoryCarveout, …)` 调大。**待验证**。所以想回到每 SM 2 个 block，寄存器和 shared memory 两个限制要同时解决。

**local memory、stack frame、spill**。线程的私有变量（`c[8][8]`、`a[8]`、`ra[4]`）最好都在寄存器里。寄存器有两个限制：数量有限（Ampere 每线程最多 255 个，用得越多能同时放的 warp 越少）；不能按运行时下标取（指令里必须直接写"用 R5"）。放不进寄存器的私有变量只能放 **local memory**：名字叫 local 是因为每个线程私有，但它物理上在 DRAM 里（经过 L1 / L2），用 `STL` / `LDL` 读写，延迟和全局内存差不多，等待也记在 long_scoreboard 上。

- **stack frame**：编译器给每个线程在 local memory 里划出的空间大小。`48 bytes stack frame` = 每线程 48 字节 = 12 个 float。最常见的原因是下标不固定的数组。
- **spill**：寄存器不够用，编译器把一部分变量临时存到 local memory（spill store，STL），要用时再读回来（spill load，LDL）。常见原因：变量真的太多（`c[16][16]` 就要 256 个）；或者用 `__launch_bounds__(256, 2)` 强制压寄存器。

| `-Xptxas=-v` 看到的 | 意思 | 典型原因 |
|---|---|---|
| stack frame、spill stores、spill loads 都是 0 | 全部在寄存器里 | ⑦ 双缓冲版 |
| stack frame > 0，spill = 0 | 有数组在 local memory，但不是因为寄存器不够 | 数组下标不是常量（如 ra、rb 用运行时下标） |
| spill > 0 | 寄存器不够，被挤出去（stack frame 也跟着 > 0） | 变量太多，或用 `__launch_bounds__` 压了寄存器 |

```text
nvcc -O3 -arch=sm_87 -Xptxas=-v ...                          # 编译时看那一行
cuobjdump -sass build-orin/gemm_bench | grep -cE "LDL|STL"   # 0 就说明完全没碰 local memory
```

少量 spill 有时可以接受（只发生在循环外，或者 L1 能命中），出现时要实测，不能光看数字下结论。所以 long_scoreboard 高时，除了全局读取，还要查是不是有数组掉进了 local memory。

## RMSNorm 和 GEMM 对照

|  | RMSNorm | GEMM |
|---|---|---|
| 做什么 | 每行求平方和 → 开方 → 每个数乘系数 | C = A × B |
| 每个数被用几次 | 1 次 | 很多次（一个 A 元素参与一整行 C） |
| 计算强度 | 约 0.5 FLOP/字节 | 几百 FLOP/字节 |
| 和 Orin 拐点（约 26）比 | 远低于 → 带宽瓶颈 | 远高于 → 理论上是算力瓶颈 |
| 实际卡在哪 | 带宽 | **延迟**：计算和带宽都没用满，warp 在干等 |
| 主要看的指标 | 有效带宽（GB/s）、每次请求的扇区数 | 停顿原因、占用率、bank conflict、SASS 指令 |
| 优化的本质 | 少搬、搬得整齐、同时多发几个请求 | 多复用、别排队、边算边搬 |
| 结果 | own_reg：147.7 → 109.5 μs（n=4096，rows=512） | 408 → 2895 GFLOPS，cuBLAS 的 85% |

**同一套分析流程，两个算子都走过**：

| 步骤 | RMSNorm | GEMM |
|---|---|---|
| ① 先保证测得对 | CPU 参考、NaN 预填、逐元素校验、锁频、3 个独立进程确认 | double 参考、NaN 预填、不整齐形状、锁频、同一次运行内对比 |
| ② 算理论上限 | 有效带宽 vs 204.8 GB/s | GFLOPS vs cuBLAS 和峰值 5325 |
| ③ 判断瓶颈类型 | SpeedOfLight：内存 | SpeedOfLight：两边都不高 → 延迟 |
| ④ 找具体原因 | 扇区数 4 → 4.44（不对齐）；barrier ×7（零头分叉） | bank conflict 839 万；long_scoreboard 1.81；kk 没展开 |
| ⑤ 看机器码 | CUB 39 条 LDG，我们只有 3 条 → 没展开 | 自动 `LDS.128`；只有 64 条 FFMA → kk 没展开 |
| ⑥ 只改一处验证 | 补齐行宽后恢复；own_t 和 CUB 一样快 | 改交错后冲突 → 1218；双缓冲后 long_scoreboard → 0.02 |

**很多手段是同一个思想**：

| 思想 | RMSNorm | GEMM |
|---|---|---|
| 编译期常量 → 循环能展开 | own_t：blockDim → 模板参数 BLOCK，展开 16 份，追平 CUB | BM / BN / BK / TM / TN 全是模板参数；kk 加 `#pragma unroll`；双缓冲里 NT、LA 用 constexpr |
| 数据放寄存器 | own_reg：x 读一次存进寄存器，不再读第二遍 | `c[8][8]`、a、b、ra、rb 全在寄存器 |
| 下标必须固定 | 固定每线程元素数，`cuobjdump` 确认 LOCAL:0 | ra 用运行时下标会掉进 local memory，改成固定次数的 r 循环 |
| 让很多请求同时在路上 | 展开后一次发 32 个读请求 | 双缓冲：下一块的 LDG 和这一块的 FFMA 同时进行 |
| 竖着看一个 warp | 32 个线程的地址是否连续 → 合并访存、扇区数 | 32 个线程落在哪个 bank → bank conflict |
| 对齐 | 行宽不是 32 的倍数 → 每次请求 4.4 个扇区；补齐解决 | padding 用 +4 不用 +1，保证 float4 的 16 字节对齐 |
| 向量化 | 接 PyTorch 时加了 float4 版（rmsNormVec4） | float4 读 shared → `LDS.128` |
| 同步和分叉 | 零头让最后一个 warp 分叉，其他 warp 在 barrier 等 | 双缓冲把每轮 2 次同步减到 1 次，barrier 0.54 → 0.12 |

- **最大的共同点**：最后都落到"不让硬件干等"。RMSNorm 是让更多读请求同时在路上，GEMM 是让计算盖住读取。
- **最大的不同点**：GEMM 有复用，所以要用 shared memory 和寄存器分层存数据，才有 bank conflict、分块、双缓冲这些问题；RMSNorm 每个数只用一次，shared memory 只用来做规约。
- 先判断是哪类瓶颈，再选看哪些指标；编译期常量是性能的前提；两次都是 SASS 揭示了真相；"理论上更好"不等于更快（RMSNorm 有被推翻的猜测，GEMM 有变慢的 float4）。

## 卷积 bench：v1 直接卷积

**先把卷积本身讲清**。卷积核是一个小窗口，在图上滑动，每停一个位置就把窗口里对应位置的数相乘再求和，得到一个输出数。一层一层加上去：

1. **一个通道、一个卷积核**：4×4 的输入、3×3 的卷积核、不补边，横竖各能放 2 个位置，输出 2×2。左列 +1、右列 −1 的卷积核在找竖直边缘；权重是训练学出来的。
2. **多个输入通道**：输入有 C 张图（RGB 时 C = 3），卷积核也有 C 层，每层盖在对应的图上各自乘加，C 个结果再相加，得到 **1 个**数。所以不管输入几层，一个卷积核只输出一张图。
3. **多个卷积核**：准备 K 个卷积核，每个都在同一份输入上完整滑一遍，得到 K 张输出图。K = 输出通道数 = 这一层要找几种图案；这一层的 K 就是下一层的 C（只有第一层的输入是真实图片）。
4. **权重共享**：层与层之间卷积核不共享；同一层里一个卷积核滑遍全图，每个位置用同一组权重，所以卷积参数比全连接少得多。

```text
输入 in[N, C, H, W]   卷积核 w[K, C, R, S]   输出 out[N, K, P, Q]
P = (H + 2·pad − R) / stride + 1          例：SigLIP 512×512、16×16、stride 16 → 32，共 1024 个 patch

out[n,k,p,q] = Σ_c Σ_r Σ_s  in[n, c, p·stride − pad + r, q·stride − pad + s] · w[k,c,r,s]
                              └ 窗口左上角 ┘ └ 窗口里第 r 行
```

下标分两类：n、k、p、q 决定"算哪一个输出格子"，c、r、s 是这个格子要加起来的项。所以 n 不需要循环——不同照片从不相加，n 只出现在读 X 的下标里，作用是选哪张照片；k 同理，只出现在 Wt 的下标里。pad 区域的 0 并不存在显存里，算出的 h 或 w 越界时直接跳过（等价于乘 0），否则会读到上一层的数据或非法地址。

**v1：一个线程一个输出**。外面三层 k、p、q 交给线程，里面三层 c、r、s 留在线程里循环：

```text
size_t idx = blockIdx.x * (size_t)blockDim.x + threadIdx.x;
if (idx >= N·K·P·Q) return;                  // 最后一个 block 多出来的线程
q = idx % Q;  p = (idx / Q) % P;  k = (idx / (P·Q)) % K;  n = idx / (K·P·Q);   // 像时钟进位
for c, r, s:
    h = p·stride − pad + r;  w = q·stride − pad + s;
    if (h < 0 || h >= H || w < 0 || w >= W) continue;
    sum += X[((n·C + c)·H + h)·W + w] * Wt[((k·C + c)·R + r)·S + s];
Y[idx] = sum;                                // Y 的摊平顺序就是 n、k、p、q
```

一维下标要一层套一层：把 Wt 想成一本书，k 是章、c 是节、r 是行、s 是字，第 k 章从 `k·C·R·S` 开始，提公因式就是 `((k·C + c)·R + r)·S + s`。**易错**：写成 `k*C + c*R + r*S + s`，代入 C = 2、R = S = 3、读第 1 层第一个数：正确位置是 9，这个写法得到 3（读成了第 0 层第 1 行）。`h = r + p` 只在 stride 1、pad 0 时对；idx 和 h / w 两个越界检查都不能少。kernel 里要调用的辅助函数（如 `P()` / `Q()`）要标 `__host__ __device__`。

| 形状（N, C, H×W, K, R×S, stride, pad） | v1 direct | cuDNN | 差距 |
|---|---|---|---|
| resnet3x3（1, 64, 56×56, 64, 3×3, 1, 1） | 0.199 | 1.875 | 9.4× |
| resnet3x3_s2（1, 128, 28×28, 256, 3×3, 2, 1） | 0.178 | 0.426 | 2.4× |
| resnet1x1（1, 256, 56×56, 64, 1×1, 1, 0） | 0.069 | 0.614 | 8.9× |
| siglip_patch（3, 3, 512×512, 768, 16×16, 16, 0） | 0.077 | 2.857 | **37×** |

Orin，锁频 1300 MHz，TFLOPS，NCHW，FP32。cuDNN 8.6 只用 FP32 乘加、不用 Tensor Core。另有 4 组不整齐的小形状（含奇数尺寸、pad、stride 2、1×1）只查正确性，8 组全部 PASS。Orin FP32 峰值约 5.3 TFLOPS，v1 只用到 1～4%。

1. **读 Wt 没问题**：一个 warp 的 32 个线程 k 相同、只有 q 不同，读的是同一个地址，硬件读一次再广播。
2. **读 X 看 stride**：stride 1 时相邻线程的 w 相邻，地址连续能合并；siglip 的 stride 16 让相邻线程相隔 64 字节，32 个线程碰 32 段内存，所以最慢。
3. **根本问题是没有复用**：每次乘加都从显存读 2 个数。resnet3x3 里一个 X 元素被 9 个窗口位置 × 64 个卷积核用 576 次，每个权重被 3136 个输出位置用到，每次都重新读。以上是按代码推的，**没有用 ncu 验证**。

**下一步 v2 implicit GEMM**：把 (c, r, s) 压成一个下标，长度 CRS，每个输出就是两个长度 CRS 的向量点积，所有输出合起来是一次 GEMM：A = 权重 reshape 成 K × CRS，B = "补丁矩阵" CRS × NPQ（每列是一个输出位置要用的那块输入，越界处为 0），C = K × NPQ。显式 im2col 要把 B 真写进显存，3×3 stride 1 时 B 约是输入的 9 倍；implicit 只改 GEMM 里"搬 B 的 tile"那一行，加载时按卷积规则现算地址，其余（shared 分块、寄存器分块、双缓冲）照搬模块里的 GEMM。之后的难点：每个元素都要做几次 `/` 和 `%`（预先算好或沿 k 增量更新）；NHWC 布局让 c 连续、可以 float4；padding 分支。形状差别：1×1 卷积本身就是 GEMM；siglip 的 patch embed 窗口互不重叠，im2col 只是 reshape；resnet3x3 对应 M = 64、N = 3136、K = 576。

## 卷积 v2：显式 im2col + 自己的 GEMM

**要解决什么**：v1 每做一次乘加都从显存读 2 个数、读进来的不复用，resnet3x3 只有 0.199 TFLOPS。GEMM 里同样的问题已经用分块解决过，所以思路是**把卷积改写成矩阵乘，再直接调用自己写好的 GEMM**。

**最小例子**：X 是 3×3，一个 2×2 卷积核，输出 2×2。v1 算 Y[0,0] 是窗口 `1 2 / 4 5` 和 Wt `1 0 / 0 1` 对应相乘再加：1 + 5 = 6。这其实是两个长度 4 的向量点积：窗口摊平成 [1,2,4,5]，Wt 摊平成 [1,0,0,1]。把 4 个窗口都摊平、竖着排成 4 列，就是矩阵 B：

```text
            窗口(0,0) (0,1) (1,0) (1,1)
B =            1      2      4      5
               2      3      5      6
               4      5      7      8
               5      6      8      9

Wt (2×4)           · B (4×4)  =  Y (2×4)
[1 0 0 1]                         [ 6   8  12  14]   ← 输出第 0 层
[1 1 1 1]                         [12  16  24  28]   ← 输出第 1 层（再加一个卷积核就是 Wt 多一行）
```

这就是 im2col（image to column）。乘出来的结果直接就是 Y：B 的列号 = p·Q + q，正好是 `Y[k][p][q]` 在一行里的位置；Y 的第 k 行就是第 k 个输出层。对应 GEMM 的三个维度：M = K（卷积核个数），N = P·Q（输出位置数），GEMM 的"K 维" = C·R·S（每个窗口有几个数）。resnet3x3 就是 M = 64、N = 3136、K = 576。

**为什么不用转置**：GEMM 要求 `C[M×N] = A[M×K] · B[K×N]`，都是行主序。A = Wt，`Wt[k][c][r][s]` 本来就是一行一个卷积核；B 由我们自己按 [CRS × PQ] 行主序写，`B[row][col]` 在 `row·PQ + col`，一个窗口的数在内存里相隔 PQ，写出来就是列；C = 第 n 张图的 Y，`Y[k][p][q]` 本来就是 [K × PQ]。（上面 4×4 的 B 恰好对称，转不转看起来一样，只是巧合。）另一种摆法是每个窗口存成一行得到 Bᵀ [PQ × CRS]，算 `Yᵀ = Bᵀ · Wtᵀ`，Y 是 [PQ × K]，也就是 NHWC（channels-last）——要 NCHW 的话最后反而要再转置一次。

**拆下标：像"秒换算成时分秒"**。B 的行号 `row = (c·R + r)·S + s`，列号 `col = p·Q + q`（N = 1 时）：

```text
int s = row % S;          // 最低位：对自己的进制取余
int r = (row / S) % R;    // 中间位：先除掉下面的位，再对自己的进制取余
int c = row / (R * S);    // 最高位
int q = col % Q;  int p = col / Q;
int h = p*stride - pad + r;  int w = q*stride - pad + s;      // 和 v1 完全相同
B[row*PQ + col] = (h < 0 || h >= H || w < 0 || w >= W) ? 0.0f : Xn[(c*H + h)*W + w];
```

h、w 的公式和 v1 一样，因为 im2col 只改变"按什么顺序数要哪些数"，没改变"每个数在输入图的哪里"：v1 的 (n,p,q) 来自线程号、(c,r,s) 来自循环变量；这里 (c,r,s) 来自行号、(n,p,q) 来自列号。和 v1 不同的是越界的 0 **必须真的写进 B**，因为 GEMM 会把整列都乘一遍。**易错**：`r = (row % C) / R`、`s = row % C % R / S`（r、s 和 C 无关，用 tiny 形状 row = 13 代入，应为 c = r = s = 1，得到 r = s = 0）；`p = col / P`（应为 / Q；方形输出测不出来，`odd_pad` 的 P = 7、Q = 9 能查出来）；`r = (row / S) % S`（R = S 时测不出，3×5 卷积核会错）、读 X 写成 `(c*C + h)*H + w`、漏越界补 0、第 n 张图起点写成 `X + n*CRS`（一张图是 C·H·W 个数）、`launch_tiled` 的 A 填成 X、C 少乘 PQ、N 和 K 对调、漏 stream。正确的调用：

```text
for n in 0..N-1:
    im2col_kernel(X + n·C·H·W → B)                         // B 只开一块，每张图复用
    launch_reg(Wt, B, Y + size_t(n)·K·PQ, /*M*/K, /*N*/PQ, /*K*/CRS, stream);
```

B 的显存在第一次（不计时的那轮）`cudaMalloc`，不算进 TFLOPS。`size_t(C*R*S*P*Q)` 是先用 int 乘完再转，大形状会溢出，要写成 `size_t(C)*R*S*P*Q`。

|---|---|---|---|---|
| resnet3x3 | 1.157 (0.200) | 0.595 (0.388) | 0.420 (0.551) | 0.127 (1.823) |
| resnet3x3_s2 | 0.649 (0.178) | 0.236 (0.491) | 0.245 (0.471) | 0.271 (0.427) |
| resnet1x1 | 1.478 (0.070) | 0.263 (0.391) | 0.201 (0.512) | 0.172 (0.597) |
| siglip_patch | 46.96 (0.077) | 5.932 (0.611) | 1.630 (2.224) | 1.275 (2.841) |

Orin，锁频 1300 MHz（不锁频时 GPU 可能只跑 306 MHz，数字不可用），单位 ms，括号是 TFLOPS；cuDNN 8.6 只用 FP32 FMA。8 组形状（含 `odd_pad`、`odd_stride2`）全部 PASS。

| 形状 | X 大小 | B = CRS × NPQ | 膨胀 | reg 版 block 数（128×128） |
|---|---|---|---|---|
| resnet3x3（3×3，s1，pad 1） | 0.8 MB | 576 × 3136（7.2 MB） | 9× | 1 × 25 = 25 |
| resnet3x3_s2（3×3，s2） | 100,352 个 | 1152 × 196 | 2.25× | 2 × 2 = 4 |
| resnet1x1 | — | B 就是 X | 1× | 25 |
| siglip_patch（16×16，s16） | 2,359,296 个 | 768 × 3072 | 1×（只是重排） | 每张图 6 × 8 = 48 |

1. **"大 tile 更快"有前提：block 要够把 SM 填满**。s2 上 reg 版只有 4 个 block，Orin 16 个 SM 有 12 个闲着，tiled 版（16×16 小块）有 208 个 block，所以 tiled 更快——这是跑之前就按 block 数预测出来的。这一组两版都比 cuDNN 快（cuDNN 在纯 FP32 FMA 模式下对这个形状选的算法不好）。
2. **siglip 提升最大**：46.96 → 1.63 ms，约 29 倍，到 cuDNN 的 78%。GEMM 大（M = 768），窗口不重叠所以 im2col 几乎没有额外开销；v1 的 X 读取不合并问题在 GEMM 里也没有了。
3. **resnet3x3 还差 cuDNN 3.3 倍**（分析，**没有用 ncu 验证**）：M = 64，reg 版每个 128 行的块一半在算补的 0；B 是 X 的 9 倍，要先写出 7.2 MB 再读回。没有单独计时 im2col 这一步占多少。

**下一步 implicit GEMM**：不再把 B 写进显存，GEMM 搬 B 的 tile 进 shared memory 时按上面同一套拆下标 + h、w 公式直接去 X 里读，越界补 0。之后再考虑增量算下标、NHWC + float4。

## 卷积 v3：implicit GEMM

**要解决什么**：v2 分两个 kernel。第 1 个 `im2col_kernel` 读 X、抄成 B、把 B 写进显存；第 2 个 GEMM 从显存把 B 读回来、搬进 shared memory 再乘加。B 是用完就扔的中间产物，而且是 X 的 9 倍（resnet3x3：X 0.8 MB，B 7.2 MB），这一写一读全是额外的显存流量。问题是：能不能不要 B？

**只改一行**：`B[row][col]` 的值本来就是从 X 的某一格抄过去的，那 GEMM 需要它时自己算出该读 X 的哪一格就行了。拿 `gemm_tiled` 当骨架，只改搬 B 的那一行：

```text
改之前：Bs[i][j] = B[brow][col];                 // 读 im2col 写好的 B
改之后：int c = brow / (R*S), r = (brow / S) % R, s = brow % S;   // 行号 → (c, r, s)
        int p = col / Q,  q = col % Q;                              // 列号 → (p, q)
        int h = p*stride - pad + r,  w = q*stride - pad + s;        // 和 v1、v2 完全相同
        Bs[i][j] = (brow < GK && col < GN && h,w 不越界) ? Xn[(c*H + h)*W + w] : 0.0f;
```

搬 A（Wt 本来就是 [K × CRS]）、乘加循环、写回 Y 一个字都不改：GEMM 不关心 Bs 里的数从哪来。im2col_kernel 整个删掉，B 只存在于公式里，"implicit"（隐式）就是这个意思。越界有两种都要补 0：矩阵本身越界（`brow ≥ GK` 或 `col ≥ GN`）和卷积补的 pad（h、w 越界）。

| resnet3x3 | 显式 im2col（v2） | implicit（v3） |
|---|---|---|
| 写 B | 7.2 MB 写进显存 | 没有 |
| GEMM 读 B | 从显存读 7.2 MB | 直接读 X（0.8 MB），重复读的部分大多命中 L1 / L2（Orin L2 4 MB） |
| kernel 数 | 2 | 1 |
| 代价 | — | 每次搬 B 都要做整数除法和取余，GPU 上较慢（之后用"增量算下标"优化） |

**一个线程、一个 block、一轮各管什么**。还是一个线程算一个输出 `Y[n][k][p][q]`（row = k，col = p·Q + q），但一个 block 不是一张图：把 Yn 看成 [K × PQ] 矩阵，一个 block 负责其中 TILE × TILE 的方块（TILE = 16 时是 16 个卷积核 × 16 个输出位置）。resnet3x3 一张图需要 64/16 × 3136/16 = 4 × 196 = 784 个 block，它们同时交给 16 个 SM 去领，没有先后顺序；N 张图由 `launch_igemm` 里的循环每张图启动一次（以后可以放进 `blockIdx.z`）。这个方块放回 56×56 的输出图上，是按行展开后连续的 16 个像素，可能折到下一行（如 col 48～63 = 第 0 行最后 8 个 + 第 1 行前 8 个），拆 (p, q) 的公式会自动处理，所以 `odd_pad`（Q = 9）也能对。

block 内部的 `for (t = 0; t < (GK + TILE − 1) / TILE; ++t)` 沿 CRS 方向走：第 t 轮搬 Wt 的第 16t～16t+15 列和 B 的第 16t～16t+15 行，每个线程把这 16 个乘积加进 sum；输出方块的位置在整个循环里不变，走完后每个线程只写一次 Y。轮数是 ⌈GK / TILE⌉：resnet3x3 GK = 576，36 轮；tiny GK = 2·3·3 = 18 要 2 轮，第 2 轮只有第 16、17 行是真数据，其余 14 行必须补 0（写成 `GK / TILE` 就只剩 1 轮、漏算最后 2 行）。一个 tile 的 16 行可以跨两层：resnet3x3 每层 9 行，第 0 轮是 c = 0 的全部 9 行加 c = 1 的前 7 行，因为每个线程只用自己的 brow 拆 (c, r, s)，这没有影响。

**为什么比 v1 快**：v1 每个线程自己从显存读窗口和 Wt，每次乘加读 2 个数，读进来只给自己用；v3 每一轮 256 个线程合作搬 256（As）+ 256（Bs）= 512 个数，做 256 × 16 = 4096 次乘加，每读 1 个数做 8 次乘加，v1 是 0.5 次。Bs 里每个数被 16 行线程（16 个卷积核）各用一次，As 里每个数被 16 列线程（16 个输出位置）各用一次——和 GEMM 从 naive 到 tiled 是同一个道理。

**TILE 同时管三件事**：① 一个 block 负责的输出大小（16 × 16）；② 线程数（一个线程一个输出，所以也是 256）；③ 每轮沿 GK 走多长。它是按硬件挑的（TILE² ≤ 1024、2·TILE² 个 float 放得进 shared memory，一般试 16 和 32），和卷积的 K 无关，K 不是 TILE 的倍数时多出来的线程不写 Y（`odd_pad` K = 5，一个 block 16 行线程只有 5 行有活）。三件事绑在一起就不灵活：想让 block 负责更大的输出，线程数也得跟着变。`gemm_reg` 把它们拆开了（输出 128 × 128、线程 16 × 16、每线程 8 × 8、每轮 BK = 8），所以 tiled 版跑通后，下一步是把同一套改法套到 reg 版上。

**实测：从 tiled 到增量下标**。implicit 先套在 tiled 版上（v3a），再套到 reg 版上（v3b，128 × 128 tile、double buffering），最后把下标计算挪出循环（v3c）：

| 版本（ms） | resnet3x3 | resnet3x3_s2 | resnet1x1 | siglip_patch |
|---|---|---|---|---|
| v1 直接卷积 | 1.159 | 0.650 | 1.527 | 46.96 |
| v2a 显式 im2col + tiled | 0.598 | 0.236 | 0.264 | 5.909 |
| v2b 显式 im2col + reg | 0.422 | 0.246 | 0.201 | 1.630 |
| v3a implicit + tiled | 0.508 | 0.286 | 0.253 | 7.973 |
| v3b implicit + reg | 0.530 | 0.531 | 0.245 | 3.235 |
| v3c implicit + reg + 增量下标（查表） | 0.289 | 0.292 | 0.139 | 1.881 |
| cuDNN | 0.126 | 0.270 | 0.180 | 1.277 |

Orin，锁频 1300 MHz，FP32 NCHW，cuDNN 8.6 只用 FP32 FMA。8 组形状全部 PASS。绿色是自己写的版本里最快的。

1. **v3b 反而比显式慢（resnet3x3 0.422 → 0.530）**：搬 B 的每个元素都要做几次整数除法和取余。ncu（resnet3x3）里整数指令从 0.26 亿条涨到 1.61 亿条（6.1 倍，占全部指令 32%），FFMA 条数不变，寄存器 149 → 153，占用率仍是 16.7%。省下的显存流量被算地址的开销吃掉了。
2. **v3c 增量下标**：X 里的地址可以拆成两半，`地址 = base(列) + delta(行)`。列那一半（p、q 决定的窗口左上角）对一个线程在整个 t 循环里不变，提到循环外算一次；行那一半（c、r、s 决定的窗口内偏移）只和 brow 有关，所有 block 都一样，预先算成一张表放进 `__constant__`，循环里查表。这和 cuDNN 的 `IMPLICIT_PRECOMP_GEMM` 是同一个思路。resnet3x3 0.530 → 0.289 ms，第一次比显式 im2col 快；1×1 卷积 0.139 ms，比 cuDNN 的 0.180 还快。
3. **implicit 不一定赢**：siglip_patch 的窗口互不重叠，显式 im2col 没有膨胀（只是重排），而 stride 16 让 implicit 读 X 时相邻线程相隔 64 字节、读不合并，所以显式 reg 版（1.630）比 v3c（1.881）快。implicit 省的是"膨胀出来的那部分显存写和读"，读请求的次数并没有减少（多出来的读打在 L1 / L2 上）。
4. **tile 大小要看形状**：s2 用 128 × 128 只有 4 个 block，16 个 SM 大部分闲着，所以小 tile 的 v2a 最快；resnet 的 K = 64 小于 BM = 128，一半的 FFMA 在乘补的 0（ncu 里 FFMA 条数正好是有用量的 2 倍）。

还没做（只讲过）：按形状选 tile（如 64 × 64）；改成 NHWC，让 c 连续、沿 s 读能合并；把 X 的原始 tile 先搬进 shared memory 再展开。

## 面试要求

推理优化、CUDA 算子岗位里 GEMM 几乎必问。下面合并了卷积部分和 GEMM 的要求；完整优化过程见本模块上面的 ①～⑥。

### 必须会

- 卷积输出尺寸公式 `(H + 2P − K) / S + 1`；多通道怎么算；乘加次数怎么算。
- 朴素卷积 kernel：按输出分配线程，列放在 x 方向（合并访存）；padding 的实现。
- shared memory 分块卷积：输入块要比输出块大一圈 halo（核大小 / 2）。
- naive GEMM（当场手写，15～20 分钟内写对）：下标、`dim3` 的 x / y 对应列 / 行、grid 向上取整、越界判断、`<<<grid, block>>>` 启动；能说出为什么 j 要跟 threadIdx.x（合并访存）。
- shared memory 分块 GEMM（当场手写）：row / col 的算法、段数 `(K+TILE-1)/TILE`、越界补 0、两个 `__syncthreads()` 各自防什么、为什么不能提前 return、sum 放在循环外最后写一次。常见追问："第二个 `__syncthreads()` 去掉会怎样？""K 不是 TILE 的倍数怎么办？"
- 算清三个数：计算量 2MNK、给出用时能算 GFLOPS；峰值 = 核心数 × 2 × 频率（Orin ≈ 5.3 TFLOPS，A100 FP32 ≈ 19.5 TFLOPS）；计算强度和 roofline，拐点 = 峰值算力 / 带宽，为什么大矩阵 GEMM 是计算密集、RMSNorm 是访存密集。

### 应该会

- 卷积的几种实现：直接卷积、im2col + GEMM、implicit GEMM、Winograd、FFT，各自省了什么、代价是什么；TensorRT 为什么要实测挑实现。
- 寄存器分块：外积的视角、BM / BN / BK / TM / TN 各是什么、线程数 = (BM/TM)×(BN/TN)、为什么必须是编译期常量、读和算的比例从 1:1 变成 1:4；能写出 kk 循环里读 a、b 和外积那几行。
- bank conflict：32 个 bank、`bank = 地址 % 32`、同 bank 不同地址才冲突（同地址是广播）、"竖着看一个 warp"；能当场分析一个下标有几路冲突（例如"每隔 2 个读"是 2 路），给出至少两种修法：改线程分工（交错）、padding（并解释为什么是 +4 不是 +1）、swizzle（知道名字和思路）。
- 合并访存 vs bank conflict：一个是显存 → L1（32 字节 sector），一个是 shared → 寄存器（32 个 bank）。
- float4：只要求 4 个连续 + 16 字节对齐；省的是指令数，不会让 shared memory 读得更宽；为什么读 a 需要把 As 转置；全局读用 float4 时 K、N 不是 4 的倍数怎么办。
- 占用率：寄存器、shared memory、线程数怎么限制每个 SM 的 block 数；为什么占用率低时延迟藏不住；"占用率不是越高越好"（寄存器分块就是用占用率换复用）。
- 用数据讲完整的优化故事：交错分工把 bank conflict 从 839 万降到 1218 次，快了 20%；接着做 float4 反而慢了 15%，ncu 显示 warp 主要在等全局内存和 shared memory、计算单元基本没满，SASS 显示 kk 循环没被展开、转置后写 As 有 8 路冲突；加 padding 和 `#pragma unroll` 后到 2366 GFLOPS，cuBLAS 的 70%；这时最大的停顿是 long_scoreboard 1.81，做 double buffering 后降到 0.02，2895 GFLOPS，cuBLAS 的 85%，而占用率反而从 33% 掉到 16.7%。
- 读 ncu 的顺序：SpeedOfLight 判断瓶颈类型 → Occupancy（四个限制取最小，能当场算"每线程 149 个寄存器、每 block 256 线程，每 SM 放几个 block"）→ Warp State 的时间账单 → 定位代码 → 只改一处重测。long / short scoreboard、barrier、not_selected、math_pipe_throttle 各表示什么。
- stack frame 和 spill 的区别；为什么数组下标必须是编译期常量才能进寄存器；怎么查（`-Xptxas=-v`、数 SASS 里的 LDL / STL）。
- 算子和模型的关系：ACT 里哪些层是卷积、哪些是 GEMM；batch = 1 时为什么 GEMM 会变成访存密集。

### 加分

- double buffering / 预取（自己做过，见 ⑦）：能写出一轮循环的四步顺序，说清为什么要两份 shared、为什么写 shared 必须放在计算之后、为什么每轮只同步一次；`cp.async`、TMA 知道是什么；寄存器级预取（a、b 也开两份）。
- warp 分块、split-K（K 很大而 M、N 很小时，把 K 切开给多个 block 再归约）。
- Tensor Core：WMMA / MMA 指令、FP16 / BF16 / TF32 / INT8 输入、为什么快一个数量级；TF32 会悄悄降低 FP32 精度（所以 FP32 engine 加了 `--noTF32`）。
- cuBLAS / CUTLASS / cuDNN 的关系；cuBLAS 是列优先，行优先 C = AB 要把 A、B 对调传进去。
- 小矩阵、batch = 1 的 GEMM（ACT、LLM decode）：为什么占不满 GPU、为什么这时是访存密集、GEMV。
- depthwise 卷积为什么难优化（计算强度低）。
