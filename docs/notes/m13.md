# LLM 推理全流程：prefill、decode、lm_head 与 KV cache

**解决什么问题**：把学过的算子（RMSNorm、GEMM）放回它们所在的地方——一句话从输入到生成回答，中间到底发生了什么，每一步是哪种瓶颈。用 TinyLlama-1.1B（22 层、hidden 2048、32 个头、4 个 KV 头、每头 64 维、MLP 5632、词表 32000）和例子"今天 天气 很"走一遍。本模块全部是讲解和粗算，**没有实验数据**；模型和系统的细节（哪个模型用什么结构、论文里的数字）是讲解内容，没有逐条核对出处。

## 先认清三类数据

|  | 内容 | 大小 | 会不会变 |
|---|---|---|---|
| **权重** | embedding 表、每层的 W_q / W_k / W_v / W_o、MLP 三个矩阵、RMSNorm 系数、lm_head | 约 11 亿个数（"1.1B"的来源），FP16 约 2.2 GB | 推理时完全不变，每个词、每一轮用同一套 |
| **激活值** | 每层算出来的 x、Q、attention 结果等 | 和 token 数成正比 | 每轮都不同，用完就丢 |
| **KV cache** | 每个 token 在每一层的 K、V | 约 22 KB / token | 越生成越长，只追加不修改 |

整个推理就是**激活值一层层地乘权重**，K、V 顺手存进 cache。权重是每一步里"乘的那个矩阵"；Q、K、V 是 `x × W_q`、`x × W_k`、`x × W_v` 算出来的，输入 x 不同（不同的词、不同的层）它们就不同。

| 每层的权重 | 形状 | 作用 |
|---|---|---|
| RMSNorm 的 weight（2 个） | 2048 | 归一化后每一维乘的缩放系数 |
| W_q | 2048 × 2048 | 把 x 变成 Q："我要找什么信息" |
| W_k、W_v | 2048 × 256 | 变成 K、V："我有什么信息"。GQA 只有 4 个 KV 头 × 64 = 256 |
| W_o | 2048 × 2048 | 把 attention 的结果投影回来 |
| W_gate、W_up | 2048 × 5632 | MLP 先升维 |
| W_down | 5632 × 2048 | MLP 再降回来 |

整个模型另有 embedding 表（32000 × 2048）、最后的 RMSNorm（2048）、lm_head（32000 × 2048）。

## 七步流程

```text
文字 → ① 分词 → ② embedding → ③ prefill：22 层一次处理整段 prompt（顺便建好 KV cache）
     → ④ 输出层：得到每个词的分数 → ⑤ 采样出一个词
     → ⑥ decode 循环：每次只喂刚生成的 1 个词，过 22 层，再采样一个……直到结束
     → ⑦ 把 token 转回文字
```

1. **分词**（CPU）：文字切成 token 编号，"今天天气很" → [t1, t2, t3]，N = 3。
2. **embedding 查表**：每个编号去 embedding 表里取对应的一行，得到 x：3 × 2048。
3. **prefill**：3 个 token 一起过 22 层，每层就是一个 decoder layer（见下一节）。结束时得到最终的 x（3 × 2048，每行是该位置的 hidden state）和 22 层的 KV cache（每层 3 个 token 的 K、V）。
4. **输出层**：只取最后一行，`h = RMSNorm(最后一行)`，`logits = h × lm_headᵀ`，得到 32000 个分数。
5. **采样**：`概率 = softmax(logits / temperature)`，可选 top-p，抽一个词，比如"好"。到这里用户等的时间叫**首字延迟（TTFT）**，主要花在 prefill 上。
6. **decode 循环**："好" → embedding → x：1 × 2048，同样过 22 层，但只算这 1 行 → lm_head → 采样 → 得到"。"，再喂进去……每生成一个词的时间叫 **TPOT**，决定每秒出几个字。
7. **停止并输出**：遇到结束符或达到最大长度，把编号拼回文字。

## prefill 时一层里做什么

```text
① 归一化        a = RMSNorm(x)                        3 × 2048
② 算 Q、K、V    Q = a × W_q   → 3 × 2048 = 32 个头 × 64 维
                K = a × W_k   → 3 × 256  =  4 个头 × 64 维（GQA）
                V = a × W_v   → 3 × 256
③ 加位置信息    Q、K 做 RoPE（按每个 token 的位置旋转）
④ 存 cache      K、V 写进这一层的 KV cache（现在有 3 个 token）
⑤ attention     每个头：分数 = Q × Kᵀ / √64          3 × 3
                causal mask：每个词只能看自己和前面的（上三角置为 −∞）
                softmax 得到权重，再 × V              3 × 64
                32 个头拼起来，× W_o                  3 × 2048
⑥ 残差          x = x + 上面的结果
⑦ 归一化        a = RMSNorm(x)
⑧ MLP           g = a × W_gate、u = a × W_up          3 × 5632
                m = SiLU(g) ⊙ u（逐元素相乘）
                结果 = m × W_down                     3 × 2048
⑨ 残差          x = x + 结果
```

输出的 x 还是 3 × 2048，交给下一层，重复 22 次。每层 7 个大矩阵乘（Q、K、V、O、gate、up、down）、2 次 RMSNorm（最后输出层还有 1 次）。我们自己写的那一层 `DecoderLayer`（[模块 8](m8.md)）就是这个骨架，少了 RoPE 和 KV cache，所以现在只能做 prefill 那种计算。

## decoder layer 和 decode 阶段不是一回事

|  | Decoder layer（解码器层） | Decode 阶段（解码阶段） |
|---|---|---|
| 是什么 | 模型的**结构**：一个组件 | 推理的**时间阶段**：一个过程 |
| 对应 | `DecoderLayer` 那个类 | 生成时"一次出一个 token"的那段循环 |
| 和谁对比 | encoder layer | prefill 阶段 |

名字的来历：最早的 Transformer（2017，做翻译）分两半，encoder 读原文、每个词能看全句；decoder 生成译文、带 causal mask、每个词只能看自己和前面。Llama、GPT 只保留 decoder 那一半（decoder-only），每层就叫 decoder layer，代码里 `is_causal=True` 是它的标志。

**同样的 22 个 decoder layer，在 prefill 和 decode 两个阶段都要走**，只是输入不一样。prefill 和 decode 是两个阶段，不是两层：模型有 22 层、回复 100 个 token，就是 prefill 走 22 层一次，decode 走 22 层 100 次。

## prefill 出来的是什么，为什么只用最后一行

22 层走完得到一个 3 × 2048 的矩阵，每个 token 一行，叫 hidden state——"模型读到这个位置时的总结"。关键在于**第 i 行是被训练成预测第 i+1 个词的**：

- "今天"那一行：用来猜下一个词，答案是"天气"。
- "天气"那一行：总结了"今天天气"，答案是"很"。
- **"很"那一行**：总结了"今天天气很"，用来猜下一个词，这正是我们要的。

前两行的"下一个词"就在 prompt 里，训练时有用，推理时用不上。所以只取最后一行，一个 2048 维的向量 h。

## lm_head：给每个词打分

lm_head 是一个 32000 × 2048 的权重矩阵：32000 行对应词表里的 32000 个 token，每一行是这个词的 2048 维向量。所以**lm_head 本身就是"词库"**，不是拿它去和另一个词库比。`logits = lm_head × h` 一次算出 h 和全部 32000 个词向量的点积（一次 GEMV），点积越大说明这个词和当前语境越搭。这些行向量是训练学出来的。

```text
玩具例子：5 个词、3 维（省略了点积之前的 RMSNorm）
h = [0.9, 0.1, 0.5]                     （"今天天气很"那一行）

词向量（lm_head 的每一行）       点积 = 分数（logit）
"好"   [1.0, 0.0, 0.8]    →  0.9 + 0 + 0.40 = 1.30
"冷"   [0.8, 0.1, 0.6]    →  0.72 + 0.01 + 0.30 = 1.03
"热"   [0.7, 0.0, 0.5]    →  0.63 + 0 + 0.25 = 0.88
"猫"   [0.0, 1.0, 0.0]    →  0 + 0.1 + 0 = 0.10
"跑"   [0.1, 0.2, -0.5]   →  0.09 + 0.02 − 0.25 = −0.14
```

**为什么是点积，不是余弦相似度**：点积 = |h| × |w| × cos θ，比余弦相似度多两个长度，它们都有用。词向量的长度 |w|：常见的词向量往往更长，天然得分更高，相当于自带"这个词本来就常出现"的先验。h 的长度 |h|：越长，分数之间的差距被拉得越大，softmax 之后概率越集中，表示模型越确定。最后的 RMSNorm 会先把 h 归一化，但它带可学习的缩放系数，长度并不固定。

**lm_head 和 embedding 表**：形状一样，都是"每个词一个向量"。embedding 表输入时用（编号 → 向量，查第几行），lm_head 输出时用（向量 → 每个词的分数）。是不是同一份值取决于模型，看 `config.json` 里的 `tie_word_embeddings`：GPT-2 共用（weight tying）；Llama 2、TinyLlama 是两份独立的 32000 × 2048（各约 6500 万个参数）；Llama 3.2 1B / 3B 这类小模型共用（没核对）。共用省参数（1B 级别的模型里一份占 5～10%），不共用是因为输入和输出的作用不完全一样。

**lm_head + 采样每生成一个词都要做一次**，不是只用来出第一个词：

```text
prefill：  整段 prompt → 22 层 → 取最后一行 → lm_head → 采样 → 第 1 个新词
decode 1： 第 1 个新词  → 22 层 → lm_head → 采样 → 第 2 个新词
decode 2： 第 2 个新词  → 22 层 → lm_head → 采样 → 第 3 个新词
```

## softmax 和采样

分数可正可负，加起来也不等于 1。softmax 先取 e 的指数（都变成正数），再除以总和：

```text
e^1.30 = 3.67   e^1.03 = 2.80   e^0.88 = 2.41   e^0.10 = 1.11   e^−0.14 = 0.87     总和 = 10.86
概率：好 34%   冷 26%   热 22%   猫 10%   跑 8%
```

- **greedy**：直接选最大的。每次结果一样，但容易重复、死板。
- **temperature**：先把分数除以 T 再 softmax。T < 1 差距被放大，更保守；T > 1 差距被缩小，"猫""跑"也有机会，更有创意也更容易胡说。
- **top-p**：按概率从大到小累加到 p 为止，只在这几个词里抽。p = 0.8 时好 + 冷 + 热 = 82%，"猫""跑"直接排除。

softmax 在流程里出现两处：attention 里面，以及最后采样。

## decode：每次 1 个 token，靠 KV cache 看到整句话

"好"查 embedding 得到 1 × 2048 的 x，作为唯一的输入过 22 层。每层的区别：

- Q、K、V 都只有 1 行。
- 新的 K、V **追加**进 cache，cache 里变成 4 个 token。
- attention：这 1 个 Q 去和 cache 里全部 4 个 K 算分数（1 × 4），softmax 后乘 4 个 V。不需要 mask，因为 cache 里都是前面的词。所以它虽然只是一个 token，却能"看到"整句话。
- W_o、MLP、残差、RMSNorm 都只算这 1 行。

**为什么要 KV cache**：没有它，每生成一个词都要把前面所有 token 的 K、V 重新算一遍，越往后越慢。**为什么只缓存 K、V**：Q 是"我要找什么"，只用来和之前的 K 比较，这一轮算完就没用了；K、V 是"我有什么"，后面每个新词都要拿自己的 Q 来比，所以要一直留着。

**cache 只增加，不修改**：因为有 causal mask，前面的词看不到后面的词，后面新来的词不会改变前面词的 K、V——这也是能缓存的前提。

```text
prefill 后：  [今天, 天气, 很]              3 个
decode 1：    [今天, 天气, 很, 好]          4 个   ← 追加"好"
decode 2：    [今天, 天气, 很, 好, 。]      5 个   ← 追加"。"
```

后果：越生成越慢一点（attention 要读的 K、V 越来越多）；显存一直涨，到上下文窗口为止。

## 两个阶段是两种瓶颈

|  | prefill | decode |
|---|---|---|
| 输入 | 整段 prompt，N 个 token | 1 个 token |
| 矩阵乘的形状 | [N × 2048] × [2048 × …]，GEMM | [1 × 2048] × [2048 × …]，GEMV |
| attention | N × N，带 causal mask | 1 ×（已生成的长度） |
| KV cache | 新建，写入 N 个 | 读全部，追加 1 个 |
| 每读一次权重能用几次 | N 次 | 1 次 |
| 瓶颈 | **算力**（像手写的 GEMM） | **带宽**（像 RMSNorm）：每个词都要把全部权重读一遍 |
| 影响的指标 | 首字延迟 TTFT | 每秒 token 数（TPOT） |

**decode 在 Orin 上的粗算**（理论上限，没有实测，实际会更低）：TinyLlama FP16 权重约 2.2 GB，每生成 1 个 token 要把全部权重读一遍；Orin 带宽 204.8 GB/s，每个 token 至少 2.2 ÷ 204.8 ≈ 11 ms，最多约 90 token/秒。换成 INT4 后权重约 0.6 GB，上限提高到 3 倍多。**端侧 LLM 量化省的主要不是计算，是要搬的数据。**云端的另一个办法是 batching：权重读一次，给很多请求同时算（continuous batching）。

**KV cache 多大**：每个 token 存 K 和 V，22 层，每层 4 个 KV 头，每头 64 维，FP16 每个数 2 字节：

```text
TinyLlama：  2 × 22 × 4 × 64 × 2 字节 ≈ 22 KB / token      2048 个 token ≈ 45 MB
Llama-2-7B： 2 × 32 × 32 × 128 × 2 字节 = 512 KB / token   一个 4K 上下文的请求 ≈ 2 GB
```

一张 80 GB 的卡放完 14 GB 的权重，也只能同时服务三十来个 4K 的 Llama-2-7B 请求，所以 KV cache 直接决定能同时服务多少用户。

| 算子 | 每层出现 | 瓶颈类型 / 对应的笔记 |
|---|---|---|
| RMSNorm | 2 次（最后还有 1 次） | 带宽，[RMSNorm 专题](rmsnorm.md) |
| GEMM / GEMV | 7 次，最后还有 lm_head | prefill 算力、decode 带宽，[模块 11](m11.md) |
| softmax | attention 里 1 次，采样 1 次 | 带宽，每行两次规约，[模块 14](m14.md) |
| attention | 1 次 | 还没学（FlashAttention） |
| RoPE | 1 次 | 还没学 |
| SiLU、逐元素乘、残差加 | 几次 | 带宽，可以和前后算子融合（[模块 8](m8.md)） |
| KV cache 管理 | 每层读写 | 下一节是概念，还没动手 |

## 生产中怎么管 KV cache 的大小

分成几类：少存、存得紧凑、复用、放不下怎么办。

**一、从模型结构上让每个 token 存得更少**（模型设计时定好的）：

| 方法 | 做法 | 例子 |
|---|---|---|
| GQA / MQA | 多个 Q 头共用一组 K、V 头 | TinyLlama：32 个 Q 头共用 4 个 KV 头，cache 少 8 倍；Llama 3 8B 是 8 个 KV 头，每 token 约 128 KB |
| MLA | 把 K、V 压缩成更小的隐向量再存 | DeepSeek V2 / V3 |
| 滑动窗口 | 只看最近若干个 token，更早的丢掉 | Mistral；Gemma 一部分层用局部窗口 |

**二、KV cache 量化**：K、V 从 FP16 存成 FP8 / INT8，大小减半。精度略有损失，要实测。

**三、PagedAttention（vLLM 的核心）**。以前的做法是每个请求一来就按最大长度预先分配一整块连续显存，大部分请求用不到最大长度，浪费很多，显存还会碎成小块（vLLM 论文说旧系统有 60～80% 的 KV cache 显存被浪费）。PagedAttention 借鉴操作系统的分页：

- 把 KV cache 切成固定大小的块（比如每块 16 个 token）。
- 每个请求有一张**块表**，记录它的第 0 块、第 1 块……放在显存的哪个位置，物理上可以不连续。
- 生成到需要新块时才分配，浪费最多是最后一块没填满的部分。
- attention kernel 按块表去取 K、V。
- 额外好处是共享：多个请求的 prompt 开头一样时共用同一批块，用引用计数管理，要改时再复制（copy-on-write）。

**四、prefix caching**：很多请求开头相同（系统提示词、同一份文档、多轮对话的历史）。把已经算过的前缀的 KV cache 留着，下一个请求前缀一样就直接用，连 prefill 都省了。vLLM 叫 automatic prefix caching，SGLang 用前缀树管理，叫 RadixAttention。

**五、放不下了怎么办**：

| 方法 | 做法 |
|---|---|
| 调度限流 | 限制同时服务的请求数、最大上下文长度、显存使用比例（vLLM 的 `gpu_memory_utilization`），新请求排队 |
| 抢占 | 显存不够时先暂停某些请求：把 cache 换出到 CPU 内存，或者直接丢掉、之后重新 prefill 算回来 |
| 分层存储 | GPU 显存 → CPU 内存 → SSD，冷的往下放（LMCache、Mooncake 这类系统） |
| prefill / decode 分离 | 两个阶段放在不同机器上，算好的 KV cache 通过网络传过去，各自优化 |
| 按重要性丢 token | 只保留重要的 token（StreamingLLM、H2O 这类方法，大多还在研究阶段） |

**端侧简单得多**（比如 Orin 上用 llama.cpp）：启动时按设定的上下文长度（`n_ctx`）一次性分配好整块 cache；满了就停止，或者丢掉一部分旧内容腾地方（context shift）。主要手段是 KV cache 量化和选用 GQA 模型，因为端侧通常只服务一个用户，不需要分页和调度那一套。

## cache 的"冷热"怎么看

按**最近会不会被用到**来分，和 CPU 缓存、操作系统换页的思路一样。关键点：**正在生成的请求，它的 cache 全部是热的**——decode 每一步新词的 Q 都要和这个请求全部的 K、V 做 attention，整块都要读，没有哪部分可以挪走。冷热主要是在**请求之间**区分的。

| 状态 | 冷 / 热 | 例子 |
|---|---|---|
| 正在 decode 的请求 | 热 | 每一步都要读 |
| 被很多请求共享的前缀 | 热 | 同一个 system prompt，几乎每个新请求都命中 |
| 被抢占、暂停的请求 | 温 | 过一会儿还要继续 |
| 多轮对话，等用户回复 | 冷 | 用户可能 30 秒后才回，也可能再也不回 |
| 已结束的请求留下的前缀 cache | 冷 | 留着是为了万一有人再用到同样的前缀 |

**系统怎么判断**：最近什么时候被用过（LRU，显存不够时先踢最久没用过的；vLLM 的 prefix caching 是请求结束后块不马上清空、标记为可回收，需要新块时从最久没被命中的开始回收）；被用了多少次；引用计数（计数 > 0 的块绝对不能动）；请求的状态（调度器知道哪些在跑、哪些在排队、哪些在等用户）。

**挪走还是丢掉，算一笔账**：换出到 CPU 内存或 SSD，代价是以后搬回来的传输时间；直接丢掉，代价是以后重新 prefill 的计算时间。前缀很长（几万 token 的文档）时重算很贵，存下来更划算；前缀很短或传输很慢时直接重算可能更快。例子：用户聊了 8000 个 token 后在想下一句，这段时间 cache 是冷的，可以挪到 CPU 内存；用户发来新消息时搬回 GPU，只对新消息做 prefill；10 分钟都没回就可能直接删掉。所以冷热本质上是一个**预测问题**：猜这块 cache 下次什么时候会被用到，再在显存、CPU 内存、SSD 和重算之间选最便宜的。

## 面试要求

LLM 推理岗位的基础题。这里只到"讲清流程和瓶颈"，vLLM 的实现细节和手写 KV cache 还没学。

### 必须会

- 不看资料讲完整流程：分词 → embedding → prefill → lm_head → 采样 → decode 循环 → 停止；每一步的张量形状。
- prefill 和 decode 的区别：输入、矩阵乘形状（GEMM / GEMV）、KV cache 的读写、瓶颈（算力 / 带宽）、对应的指标（TTFT / TPOT）。
- KV cache：为什么需要、为什么只缓存 K 和 V、为什么可以缓存（causal mask）、每 token 多大怎么算。
- 一层 decoder layer 里的 9 步和每步的形状；GQA 是什么。
- 权重、激活值、KV cache 三类数据各自的大小和变化规律。

### 应该会

- 为什么 decode 是带宽瓶颈：给定权重大小和内存带宽，估算 token/s 的上限；为什么量化和 batching 能提速。
- lm_head：形状、点积打分、和 embedding 表的关系（weight tying）；temperature、top-p 的作用。
- PagedAttention：解决什么浪费、块和块表、按需分配、共享和 copy-on-write。
- prefix caching；decoder layer 和 decode 阶段的区别。

### 加分

- KV cache 量化、MLA、滑动窗口；抢占时换出和重算怎么取舍；冷热判断（LRU、引用计数）。
- prefill / decode 分离部署；端侧（llama.cpp 的 `n_ctx`、context shift）和云端的差别。
- MoE 模型在 FFN 位置的差别（每个 token 只去部分专家，多卡时是 all-to-all；dense 模型的张量并行是 all-reduce），见[Lina 论文笔记](lina.md)。

三档的含义见复习笔记顶部说明。
