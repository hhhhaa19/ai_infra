# ONNX → TensorRT plugin：把自己的算子接进 TensorRT

**这一模块讲什么**：端侧部署走 ONNX → TensorRT，部署环境里通常没有 PyTorch。不做处理时，eager 写法的 RMSNorm 导出后是 7 个标准节点，由 TensorRT 自己融合，我们的 kernel 完全用不上。要让 TensorRT 调用我们的 kernel，需要四步：让 kernel 不依赖 PyTorch → 在 ONNX 里留一个自定义节点 → 写 plugin → 加载 `.so` 后建 engine。下面按这个顺序讲，先从"手上有哪些图"开始。

## 第一步：先分清有哪几种"图"

这条线上"图"这个词出现了很多次，意思各不相同：

| 图 | 谁生成 | 里面是什么 | 存在哪 | 和硬件有关吗 |
|---|---|---|---|---|
| （eager 没有前向图，是动态图） | — | Python 一行行执行，每行马上发 kernel；只有训练时 dispatcher 顺手记下 autograd 图（`grad_fn`） | 张量上 | — |
| FX 图（Python 层） | Dynamo（抓图工具，不是图本身；推形状靠 Meta） | nn.Linear、*、SDPA… | 进程内存 | 无关 |
| FX 图（aten 层） | AOTAutograd | 约 200 个核心 aten 算子；训练时还有反向图 | 进程内存 | 无关 |
| Inductor 生成的代码 | Inductor | 按顺序调 kernel 的 Python 文件 + Triton | 磁盘缓存 | 绑定 GPU |
| ONNX 图 | `torch.onnx.export`（TorchScript 追踪或 Dynamo 追踪） | ONNX 标准算子 + 权重 + 自定义节点 | .onnx 文件 | 无关（CPU / GPU 上导出都一样） |
| TRT network | TensorRT 的 ONNX Parser | TensorRT 自己的层，基本一个节点一层 | 建 engine 过程中 | 无关 |
| engine | TensorRT builder | 融合好、为这块 GPU 挑好 kernel 的执行计划 | .engine 文件 | 绑定 GPU（sm_87）和 TensorRT 版本 |
| CUDA Graph | CUDA 驱动 | 一串具体的 kernel 调用：参数、地址、grid | 驱动里 | 绑定这个进程的地址 |

这些图和 dispatcher 也有关系。dispatcher 是每个算子的实现表：eager 执行查 CUDA 格，eager 训练查 Autograd 格，Dynamo 抓图查 Meta 格。AOTAutograd 查的 Autograd 格和 eager 是同一套求导规则（`derivatives.yaml`），它就是把 eager 运行时会做的事提前录成图。`ai_infra::rms_norm` 只填了 CUDA 和 Meta 两格，Autograd 是空的，所以能推理、不能训练。

既然 CUDA Graph 已经记录了 kernel 调用，为什么不能直接交给 TensorRT？因为 ONNX 记的是"要算什么"，CUDA Graph 记的是"已经选好的 kernel 怎么调"。TensorRT 的价值是自己决定怎么融合、挑哪个 kernel，所以必须拿到前者。CUDA Graph 里还有这个进程的显存地址，也没有标准的文件格式给别的程序加载。CUDA 本身没有"模型"概念，要不用 PyTorch，可以直接用 TensorRT API 搭网络（TensorRT-LLM 的做法），或者整个模型手写 CUDA（llama.cpp、llm.c）。

## 第二步：TensorRT 在这条线上相当于 Inductor

TensorRT builder 的角色和 Inductor 很像，都接收一张图，做融合，再决定用什么 kernel：

|  | torch.compile | TensorRT |
|---|---|---|
| 输入的图 | FX 图（aten 层） | ONNX 图 → TRT network |
| 图优化、融合 | lowering + scheduler | builder 图优化（常量折叠、层融合；Myelin 会把大片层包成 ForeignNode） |
| 每一步用哪个 kernel | 融合部分**现场生成** Triton，矩阵乘交给 cuBLAS | 主要从**预先写好的 kernel 库里挑**（Myelin 也会生成一部分逐元素 / 规约 kernel） |
| 怎么挑 | 默认经验规则，max-autotune 才实测 | 每层实测候选实现（tactic），所以建 engine 要锁频；选错的会被永久写进 .engine。timing cache 可以复用计时结果 |
| 我们的算子 | 黑盒，Meta 推形状 | 黑盒 plugin，`getOutputDimensions` 推形状 |
| 产物 | 代码 + cubin | .engine |

两边对待自定义算子的方式几乎对称：都不往里融合，只在它前后融合。区别是 TensorRT 在 PyTorch 外面，多一步导出 ONNX，外壳也要用 TensorRT 的 C++ 接口重写。

## 第三步：让 kernel 不依赖 PyTorch

plugin 要用选档逻辑，但它原来写在 `rmsnorm_ext.cu` 里，文件第一行就是 `#include <torch/extension.h>`。include 它就得带上 libtorch；复制一份又容易两边改漏。所以把选档和启动代码剪切到 `launch.cuh`，让两个外壳都 include 它。

```text
                 kernels.cu（所有 kernel）+ launch.cuh（chooseBlock / withBlock / launchRMSNorm，只依赖 CUDA）
                     ▲                                        ▲
     torch/ext.cu（PyTorch 的壳）                  tensorrt/plugin.cu（TensorRT 的壳）
     torch.ops.ai_infra.rms_norm                   RmsNorm plugin
     Python load() → ninja → nvcc                  CMake → make → nvcc
     rmsnorm_cuda.so（链接 libtorch）              librmsnorm_trt_plugin.so（链接 libnvinfer + cudart）
     被 Python 加载                                 被 trtexec / Python ctypes 加载

共用的是源码，不是 .so：同一份 kernel 编译两次，打进两个 .so。
```

怎么分辨哪些是 PyTorch 的东西？看前缀：`torch::`、`at::`（ATen）、`c10::`、`TORCH_` 开头的宏。`cudaStream_t`、`cudaGetDevice`、`<<<>>>` 是 CUDA 自己的，来自 CUDA Runtime / libcudart，nvcc 会自动包含和链接。

改动只有两类。第一，SM 数改用 `cudaDeviceGetAttribute(…, cudaDevAttrMultiProcessorCount, …)`，用 `static` 加立即调用的 lambda，只查一次。第二，`TORCH_CHECK` 改成返回错误字符串，成功返回 nullptr。这样"有没有错"由头文件判断，"怎么报错"由各自的外壳决定：PyTorch 用 `TORCH_CHECK`，TensorRT 返回错误码。

验证方法很直接：`echo '#include "launch.cuh"' > t.cu && nvcc -arch=sm_87 -c t.cu`，不给任何 PyTorch 路径，能编过就说明干净。

顺便还用 `withBlock` 去掉了重复代码。模板参数要编译期确定，而 BLOCK 运行时才知道，switch 把运行时的数翻译成编译期常量，语法细节见模块 3 第 6 节。`launchReg` 和 `launchFusedReg` 没有合并，因为要把"哪个 kernel"也做成模板参数，太绕。另外 `build_ext.py` 的 `_DEPS` 要加上新头文件，否则改了头文件扩展不会重编，这个坑以前踩过。

## 第四步：跟着一个 RmsNorm 节点走完全程

现在看整体流程。节点先在导出时产生，plugin 单独编译；建 engine 时两者碰头，加载 engine 时再恢复一次。

```text
阶段 A  导出（PyTorch 世界）  python src/llama/export_onnx.py ours
  A1 register_custom_op_symbolic("ai_infra::rms_norm", rms_norm_symbolic, 17)
       @parse_args("v", "v", "f", "i")                 # v = 图里的张量，f = 常量 float，i = 常量 int
       def rms_norm_symbolic(g, x, weight, eps, impl):
           out = g.op("ai_infra::RmsNorm", x, weight, eps_f=eps)   # eps 作属性（_f 后缀 = float），impl 不导出
           out.setType(x.type()); return out
  A2 DecoderLayer(impl="ours") → __init__ 里 rms_norm_op() → 加载 rmsnorm_cuda.so → 算子已注册
       base（eager，norm 权重 normal_() 随机化）→ load_state_dict 拷进来，各写法权重完全一样
  A3 每种形状：PyTorch 先算出 ref → torch.onnx.export（追踪时真的跑我们的 CUDA kernel，
       custom_opsets={"ai_infra": 1}）→ 存 io_{形状}.pt（x 和 ref）→ onnx.checker + 写 graph_ours.txt
  产出：layer_ours_*.onnx（图 + 权重，没有我们的代码）。之后都不需要 PyTorch。

阶段 B  编译 plugin（只做一次，和 A 互不依赖）  cmake --build build-orin --target rmsnorm_trt_plugin
  plugin.cu include launch.cuh，launch.cuh include kernels.cu → librmsnorm_trt_plugin.so

阶段 C  建 engine  trtexec --onnx=… --saveEngine=… --plugins=librmsnorm_trt_plugin.so --noTF32 …
  C1 加载 .so → REGISTER_TENSORRT_PLUGIN 的全局变量自动构造 → 造出唯一的 creator → 登记 "RmsNorm"/"1"
  C2 Parser 逐个读节点；遇到 RmsNorm 不认识：
       No importer registered for op: RmsNorm. Attempting to import as plugin.
       Searching for plugin: RmsNorm, plugin_version: 1 …  Successfully created plugin: RmsNorm
     → creator.createPlugin(属性 eps) → new RmsNormPlugin(eps)；第二个 RmsNorm 再调一次
  C3 builder 问：getNbOutputs → 1；getOutputDimensions → 同 x；getOutputDataType → 同 x；
     supportsFormatCombination(pos = 0,1,2) → 只要 kFLOAT + kLINEAR
  C4 融合 + 实测挑 kernel（plugin 是黑盒，Myelin 只能在它前后分段融合）；期间可能 clone
  C5 序列化：getSerializationSize → 4，serialize → 写 eps 的 4 个字节
  产出：ours_*_fp32.engine（只能在 sm_87 + TensorRT 8.5 上用）

阶段 D  加载并推理  TRT_PLUGINS=build-orin/librmsnorm_trt_plugin.so python src/llama/trt_check.py …
  D1 ctypes.CDLL 加载 .so（必须在反序列化之前），creator 登记
  D2 deserialize_cuda_engine → 读到 plugin 层 → creator.deserializePlugin(那 4 个字节)
  D3 create_execution_context；D4 set_tensor_address 绑定地址
  D5 execute_async_v3 → 跑到这个节点调 enqueue：
       rows = 前面所有维度相乘，n = 最后一维 → launchRMSNorm(rows, n, inputs[0], inputs[1], outputs[0], eps_, stream)
```

导出时完全用不到 plugin。两边**唯一的联系是两个约定**：节点名（symbolic 写 "RmsNorm"，creator 的 `getPluginName()` 也返回 "RmsNorm"）和属性名（`eps_f=eps` 对应 `createPlugin` 里找的 "eps"）。写错一边（比如 "RMSNorm"），导出照样成功，建 engine 时才报找不到 plugin。

导出时用什么设备？老导出器拿示例输入把模型真的跑一遍，模型和输入在哪就在哪跑；"记录操作"本身是 CPU 上的 Python。我们的算子没有 CPU 实现，所以 ours 要在 GPU 上导出。导出不需要锁频，建 engine 需要。

## 第五步：plugin 类的每个函数什么时候被调用

读 plugin 代码时，别从上往下看语法，要按"TensorRT 什么时候来调用"分组。建 engine 时问形状和类型，推理时调 `enqueue`，保存 engine 时写 `eps`。

| 函数 | 谁调用 / 什么时候 | 我们写了什么 | PyTorch 那边对应 |
|---|---|---|---|
| RmsNormPlugin(float eps) | creator.createPlugin，建 engine 时 | 存 eps | — |
| RmsNormPlugin(void const*, size_t) | creator.deserializePlugin，加载 engine 时 | memcpy 4 字节回 eps_ | — |
| getOutputDimensions | builder 规划图 | `return inputs[0];`（返回的是形状**表达式** DimsExprs，动态形状下 batch 可能未定） | Meta 实现 |
| supportsFormatCombination | builder 按 pos 逐个问；inOut 先输入后输出（x、weight、y） | 三个位置都只要 kFLOAT + kLINEAR | forward 里的类型 / 连续检查（PyTorch 是收到再查，TensorRT 是事先问清、由它保证，必要时在前后插转换） |
| configurePlugin / getWorkspaceSize | builder | 空 / 返回 0（只用寄存器和 shared） | — |
| enqueue | 每次推理 × 每个节点 | 算 rows、n，调 launchRMSNorm；出错 fprintf 并返回 1 | CUDA 实现 forward |
| getSerializationSize / serialize | 写 engine 文件 | 4 / memcpy eps | 无（PyTorch 不存文件） |
| clone | TensorRT 需要副本时（比如每个 context 一份） | new 一个带同样 eps 的 | — |
| initialize / terminate / destroy | 准备运行 / 释放 / 用完 | 0 / 空 / `delete this` | — |

所有函数都是 `noexcept`，因为 TensorRT 要求出错只能靠返回值，不能抛异常。参数只写类型不写名字，表示用不到。`DynamicExt` 表示支持动态形状。

这里最容易混的是 eps 和 weight。weight 是 2048 个 float 的张量，在 ONNX 里是节点的**输入**，TensorRT 自己把它当常量存进 engine。eps 只是一个数，是节点的**属性**，要 plugin 自己保存。部署时只有 `.engine`，没有 ONNX，所以 plugin 需要的参数必须自己写进去。以后加参数，就在 `serialize` 里往后写，构造函数按同样顺序读。

ONNX 里显示 `eps=9.999999747378752e-06`，是因为 float32 存不下精确的 1e-5。它的二进制是 0x3727C5AC，engine 里按小端序存为 AC C5 27 37。

做 FP16 时，`supportsFormatCombination` 要区分 pos：`pos == 0` 时允许 kFLOAT 或 kHALF，其余位置 `return inOut[pos].type == inOut[0].type`，因为问到 pos 时前面的类型已经定了。也可以让 weight 保持 FP32，单独判断。

## 第六步：creator，生产 plugin 的工厂

为什么要 creator？Parser 遇到 RmsNorm 时手里还没有 plugin 对象，必须事先有个东西待在注册表里，等着被找到。这就是工厂模式：creator 整个程序一个，由它生产 plugin。

```text
RmsNormPluginCreator() {
    fields_.emplace_back("eps", nullptr, PluginFieldType::kFLOAT32, 1);   // 属性说明书：有个叫 eps 的 float，没有数值
    fc_.nbFields = static_cast<int32_t>(fields_.size());                   // C 风格接口：个数 + 指针
    fc_.fields = fields_.data();
}
IPluginV2* createPlugin(char const*, PluginFieldCollection const* fc) noexcept override {
    float eps = 1e-6f;                                                      // 节点上没写 eps 时的默认值
    for (int i = 0; i < fc->nbFields; ++i)
        if (std::strcmp(fc->fields[i].name, "eps") == 0 && fc->fields[i].type == PluginFieldType::kFLOAT32)
            eps = *static_cast<float const*>(fc->fields[i].data);         // 这次 data 指向真实数值
    auto* p = new RmsNormPlugin(eps); p->setPluginNamespace(ns_.c_str()); return p;
}
REGISTER_TENSORRT_PLUGIN(RmsNormPluginCreator);
// 展开：static nvinfer1::PluginRegistrar<RmsNormPluginCreator> pluginRegistrarRmsNormPluginCreator {};
```

|  | creator（工厂） | plugin（产品） |
|---|---|---|
| 有几个 | 整个程序 1 个（宏造的，代码里没有 new 它） | 每个 RmsNorm 节点 1 个，clone 后可能更多（5 个节点 → createPlugin 调 5 次，至少 5 个对象） |
| 什么时候出现 | .so 加载时（全局变量自动构造） | 建 engine 或加载 engine 时 |
| 带着什么 | 名字、版本、属性说明书 | 这个节点自己的 eps |
| 干什么 | 生产 plugin（两种方式对应两个构造函数） | 推形状、执行 kernel |

什么时候创建 plugin？你不用自己判断，调用时机全由 TensorRT 掌握。这和 PyTorch 里我们从没自己调用过 forward 一样：按接口把格子填好，框架在合适的时候来调用。ONNX 里有几个 RmsNorm 节点，`createPlugin` 就调几次，比如 5 个节点是 1 个 creator、调 5 次，不是 5 个 creator。

`fields_`、`fc_` 必须是成员变量，因为 `getFieldNames()` 返回的是指向它们的指针。写成局部变量，函数一返回就销毁，指针就悬空了。**把指针交给别人之前，先想清楚它指向的东西能活多久。**同样，对象在我们的 `.so` 里 new，就在我们的 `.so` 里 delete（`destroy()` 里的 `delete this`），因为两边可能用不同的内存分配器。

## 第七步：编译成 .so，只有 nvcc 真正在编译

写好 plugin 后要把它编译出来。这里 Python、CMake、ninja 看着很乱，其实它们都只是组织命令的工具：

```text
plugin.cu ─ GPU 部分 ─▶ PTX ─ptxas─▶ SASS（sm_87）
          └ CPU 部分（enqueue、launchRMSNorm…）─▶ g++ ─▶ CPU 机器码
          → 打包成 .o → 链接 → 可执行文件（能直接跑）或 .so（要被别的程序加载）

一条命令就能编 plugin：
nvcc -shared -Xcompiler -fPIC -arch=sm_87 src/rmsnorm/tensorrt/plugin.cu -lnvinfer -o librmsnorm_trt_plugin.so
  -shared 编成 .so；-fPIC .so 会被加载到任意地址，代码不能写死地址；-lnvinfer 链接 TensorRT

CMake：CMakeLists.txt（需求）→ cmake -S . -B build-orin（生成 Makefile）→ cmake --build（调 nvcc）
  add_library(rmsnorm_trt_plugin SHARED src/rmsnorm/tensorrt/plugin.cu)，只链接 CUDA::cudart 和 TensorRT
PyTorch load()：生成 build.ninja（要和已装 torch 完全一致的编译参数）→ ninja 调 nvcc → 加载 .so → TORCH_LIBRARY 注册
```

`.so` 有两种用法：编译时链接，程序一启动就加载（比如我们的 `.so` 链接 libnvinfer.so）；或者运行时 dlopen（trtexec 的 `--plugins=`、Python 的 `ctypes.CDLL`、PyTorch 的 `load()`）。`.so` 里同时有 CPU 机器码和 GPU 的 SASS，可能还附带 PTX。plugin 必须是 `.so`，因为 `trtexec` 已经编译好了，只能在运行时打开它；`.a` 是给链接器用的，不能这样加载。

再看 GPU 代码的三层：CUDA C++ 是人写的；PTX 是"虚拟 GPU 汇编"，寄存器不限、跨代兼容，新驱动可以 JIT；SASS 是真正的机器码，每代架构不同，寄存器在这一步分配，存在 cubin 里。float4 那次看的 `LDG.E.128` 是 SASS，PTX 里对应 `ld.global.v4.f32`。Triton 不经过 CUDA C++，直接生成 PTX 再交给 ptxas。engine 不能跨 GPU，就是因为里面有为这块 GPU 挑好的 SASS kernel。

想自己看的话：`nvcc -arch=sm_87 -ptx src/rmsnorm/kernels.cu -o k.ptx`；`nvcc -arch=sm_87 -cubin … && cuobjdump -sass k.cubin | grep LDG`。

## 第八步：engine 和 context

建好的 engine 可以反复加载。engine 是只读的方案，context 是一次运行的状态：

|  | engine | context |
|---|---|---|
| 存什么 | 只读：网络结构、权重、选好的 kernel | 运行时状态：中间结果显存、这次的输入输出地址、动态形状下这次的具体形状 |
| 有几个 | 1 个，建一次（15～20 秒）多次加载（零点几秒） | 可以多个，每个一份中间显存；同一个 context 不能同时在两个 stream 上跑 |

复用 engine 有几个前提：同一种 GPU、同一个 TensorRT 版本、加载前先加载 plugin `.so`、输入形状在建 engine 时允许的范围内。我们是固定形状，三种形状三个 engine；动态形状要导出时标动态维，再配 optimization profile，运行时 `set_input_shape`。多个 context 共用一份权重，可以并发处理多个请求；每个 context 通常会 clone 一份 plugin。

再和 ONNX 对比一下。简单说，**ONNX 描述"要算什么"，engine 决定"在这块硬件上具体怎么算"**。engine 本身不运行，它是编译好的结果，加载并创建 context 后才执行。融合也只是优化之一，TensorRT 还会选实现（tactic）、确定精度和内存布局，有些层（比如形状计算）放在 CPU 上执行。

|  | ONNX | engine |
|---|---|---|
| 内容 | 计算图、权重、算子属性 | 优化后的图、选好的实现、权重和内存规划 |
| 算子 | 标准算子和自定义节点，通常不做硬件相关融合 | 能融合的已融合，比如 Myelin 子图 |
| 可移植性 | 不绑定硬件，能给不同框架用 | 绑定 TensorRT 版本和 GPU 型号 |
| 精度和优化 | 还没做 TensorRT 的优化决定 | FP32 / FP16 等在建 engine 时已定 |
| 能否直接执行 | 要先建成 engine | 加载后创建 context 即可 |

RmsNorm 是个例外：engine 里**没有我们的 CUDA 代码**，只记下 plugin 的类型名、版本和 `serialize` 写的 4 字节 eps，kernel 还在 `.so` 里。所以运行时必须加载同一个 `.so`，反序列化时才能靠 creator 的 `deserializePlugin` 把 plugin 重建出来，没加载就会失败。

## 第九步：用什么工具建 engine 和验证

这次实际用的是 `trtexec` 和 `trt_check.py`，没有用你自己的 C++。三者的区别是：

|  | trtexec（TensorRT 自带） | trt_check.py（Python 检查脚本） | 你自己的 C++（src/tensorrt_intro） |
|---|---|---|---|
| 位置 | /usr/src/tensorrt/bin/trtexec（不在 PATH） | src/llama/trt_check.py | build_engine.cpp / infer_async.cpp |
| 建 engine | 能 | 不能，只加载 | build_engine 能 |
| 输入 | 随机数 | 导出时存的同一个 x | input.bin |
| 检查对不对 | 不检查（eps 读错也照样报好看的时间） | 和 PyTorch 的 ref 逐元素比 | 写出 .bin 再用 compare_outputs.py |
| 计时 | GPU Compute Time 等；`--dumpProfile` 逐层 | 和 bench_layer.py 同样的 CUDA event 方法，所以能和 PyTorch 直接比 | std::chrono，含 H2D / D2H |

`trtexec` 回答"跑多快"，用随机输入，不检查结果对不对；`trt_check.py` 回答"算得对不对"，并用和 PyTorch 相同的方法计时。Python 的 tensorrt 包和 C++ 接口底层是同一个 libnvinfer，函数一一对应（`deserialize_cuda_engine` ↔ `deserializeCudaEngine`、`execute_async_v3` ↔ `enqueueV3`）。trt_check.py 借 PyTorch 分配显存、比误差、录 CUDA Graph，只是为了测试方便，真正部署通常用 C++。

trtexec 要公平对比，需要加 `--noTF32`（TensorRT 默认允许 TF32，PyTorch 默认关）、`--noDataTransfers`、`--useSpinWait`；另跑一次 `--useCudaGraph`；用 `--profilingVerbosity=detailed --exportLayerInfo` 看融合结果。

把这次每一步实际用的东西列出来，就能看清 PyTorch 只在哪里出现：只有第 3、5 步用到 PyTorch，engine 建好后推理本身完全不需要它。

| 步骤 | 用什么 | 文件 | 语言 |
|---|---|---|---|
| 1. 写算子 | 自己的 kernel 和 plugin | kernels.cu、launch.cuh、plugin.cu | C++/CUDA |
| 2. 编译 plugin | CMake | librmsnorm_trt_plugin.so | C++/CUDA |
| 3. 导出 ONNX | PyTorch | export_onnx.py | Python |
| 4. 建 engine、测时间 | NVIDIA 的 trtexec | scripts/build_trt_engines.sh | 现成的 C++ 程序 |
| 5. 查正确性、同方法计时 | TensorRT Python 接口，PyTorch 准备数据和计时 | trt_check.py | Python |

第 4、5 步的时间分别怎么来的？这次都没有用 ncu 或 CPU 时钟。ncu 看单个 kernel 内部的读写字节、带宽、缓存命中，默认冷缓存、基础频率，还会 replay，不适合测实际耗时；`enqueue` 提交后马上返回，只测 CPU 这一段看不到 GPU 实际运行的时间。

| 时间 | 怎么测 | 测的是什么 |
|---|---|---|
| trtexec 的 b1、b8、prefill | 自带计时，`GPU Compute Time` 中位数 | 推理段；加了 `--noDataTransfers`，不含 CPU 和 GPU 之间的拷贝 |
| trtexec 的 CUDA Graph 版 | 同上，加 `--useCudaGraph` | CUDA Graph 下的推理段 |
| trt_check.py | CUDA event，方法同 bench_layer.py | GPU stream 上两个事件之间的时间；N 次平均为一个样本，30 个样本取中位数，再交替 3 轮取中位数 |
| 逐层时间 | `--dumpProfile --separateProfileRun` | TensorRT 自己的逐层统计，单独跑一次，不影响普通计时 |

两种方法能对上：同一个 eager engine，trtexec 和 trt_check.py 在 b1 是 1.309 / 1.311 ms，b8 是 8.882 / 9.030 ms，prefill 是 14.790 / 14.789 ms。

改用自己的 C++ 程序还要做三件事（还没做）：① 链接 plugin 或用 `dlopen` 加载；② `createNetworkV2(0U)` 在 TensorRT 8.5 是隐式 batch，ONNX parser 不支持，要传显式 batch 标志（原代码是在 Quest 的 TensorRT 10 上写的）；③ 用 `clearFlag(kTF32)` / `setFlag(kFP16)` 设置精度。另外 `infer_async.cpp` 为 ResNet 写死了形状和路径，要改成从 `getTensorShape()` 读。

|---|---|---|

trt_check.py 的计时方法和 bench_layer.py 相同，所以数字能和 PyTorch 的结果放在一起比。`infer_async.cpp` 对应这里加载和推理的部分，调的是同一套接口。

## 补充：三个产物、两种翻译写法、对接细节

先分清这条线上的三个产物。第七步编译的只有 plugin，也就是 RMSNorm 这一个算子的代码，和模型结构、权重都没有关系；模型里的矩阵乘和 attention 用的是 TensorRT 自带的 kernel 库。

| 产物 | 里面有什么 | 怎么来 |
|---|---|---|
| `.onnx` | 整个模型的计算图和权重 | PyTorch 导出 |
| `librmsnorm_trt_plugin.so` | RMSNorm 的 kernel 和 plugin 外壳 | `nvcc` 编译 `plugin.cu` |
| `.engine` | 整个模型优化后的执行方案，含权重 | TensorRT 根据 ONNX 构建 |

所以有两种"编译"：`nvcc` 编译的是**代码**，TensorRT 建 engine 处理的是**模型**。部署时要同时带上 `.engine` 和 `.so`，还要有运行环境（TensorRT 和 CUDA 运行库、GPU 驱动，Orin 上由 JetPack 提供），但不需要 PyTorch。平台绑定程度也不同：ONNX 不绑定硬件；engine 绑定 TensorRT 版本和 GPU 型号；plugin 的 `.so` 绑定 CPU 架构和 CUDA 环境（Orin 是 ARM + sm_87，Quest 是 x86 + sm_80，要分别编译、分别建 engine）。所以常见做法是把 ONNX 留作交换格式，到目标机器上再建 engine。

再看"plugin 对象是不是算子"。更准确地说，plugin 对象是图里一个算子节点在 TensorRT 里的外壳：

| 概念 | 是什么 | 数量 |
|---|---|---|
| ONNX 节点 | 图里的一个 `RmsNorm` | decoder layer 有 2 个（norm1、norm2） |
| plugin 对象 | 这个节点在 TensorRT 里的 C++ 对象，存 eps，负责推形状、启动 kernel | 每个节点至少 1 个，clone 后可能更多 |
| creator | 生产 plugin 的工厂 | 整个程序 1 个 |
| kernel | GPU 上真正运行的代码 | 按形状选版本启动 |

TensorRT 这条线目前没有用融合算子：`RmsNorm` 只做 norm，第二个残差 Add 变成了独立的 `/Add_1`，第一个被包进 attention 那段 Myelin。要用融合版需要三件事：导出时把 Add + RmsNorm 合成一个新节点、写调用 `launchFusedAddRMSNorm` 的新 plugin、重建 engine。当时判断收益很小（预计，没实测）。

接着是导出时的翻译规则。导出器遇到 `ai_infra::rms_norm`，要有人告诉它写成哪个 ONNX 节点。老导出器用 symbolic，新导出器（`dynamo=True`）用转换表，**只换写法，不改结果**：

```text
【现在：symbolic（Orin，torch 2.1）】
register_custom_op_symbolic("ai_infra::rms_norm", rms_norm_symbolic, 17)
out = g.op("ai_infra::RmsNorm", x, weight, eps_f=eps)    # _f 表示 float 属性

【新导出器：转换表（示意，没有运行过）】
ai_infra = onnxscript.values.Opset("ai_infra", 1)
def rms_norm_onnx(x, weight, eps, impl=0):
    return ai_infra.RmsNorm(x, weight, eps=eps)
torch.onnx.export(layer, (x,), path, dynamo=True,
    custom_translation_table={torch.ops.ai_infra.rms_norm: rms_norm_onnx})

两种写法最后都是：节点 ai_infra::RmsNorm，输入 x、weight，属性 eps；impl 只用于测试，不写进 ONNX
```

要走新导出器，还得在新版 PyTorch 上导出（比如 Quest），并确认 TensorRT 8.5 能解析结果。现在的路线已验证，除非要在 Orin 之外导出，否则没必要换。

导出和 plugin 之间不直接调用，只靠 ONNX 里两个字符串对上：plugin 用 `getPluginName()` 返回 "RmsNorm"、`getPluginVersion()` 返回 "1"，加载 .so 时登记；Parser 遇到不认识的 `RmsNorm` 就按名字查注册表，调 `createPlugin`；creator 再按属性名 "eps" 读出数值。写错时什么时候发现：

| 错误 | 什么时候发现 |
|---|---|
| 节点名写成 `RMSNorm` | 导出成功，建 engine 时报找不到 plugin |
| 没加载 `.so` | 建 engine 或加载 engine 时失败 |
| 属性名写成 `epsilon` | 可能不报错：creator 找不到 "eps"，悄悄用默认值 1e-6，结果只差一点 |

最后一种最危险，这也是 `trt_check.py` 一定要和 PyTorch 输出比误差的原因。

PyTorch 和 TensorRT 两个外壳的核心是一样的：拿到地址和形状，然后调用同一个 `launchRMSNorm`。

| 步骤 | PyTorch `forward` | TensorRT `enqueue` |
|---|---|---|
| 注册 / 找实现 | `TORCH_LIBRARY` + schema，dispatcher 找实现 | ONNX 节点 + creator 按名字注册，注册表找 creator |
| 推形状 | Meta 实现 `empty_like(x)` | `getOutputDimensions` 返回 `inputs[0]`、`getOutputDataType` 返回 `inputTypes[0]` |
| 拿输入地址 | `x.data_ptr<float>()` | `inputs[0]` |
| 拿输出地址 | `empty_like` 后取指针 | `outputs[0]` |
| 拿 stream | `getCurrentCUDAStream()` | 参数 `stream` |
| rows、n | 从张量形状算 | `n` = 最后一维，`rows` = 前面维度相乘（[8,1,2048] → rows 8） |
| 报错 | `TORCH_CHECK` | `fprintf` + 返回 1 |

## 补充：FP16 为什么分两步、TensorRT 选错 kernel 怎么办

我们的 kernel 只支持 FP32，`supportsFormatCombination` 也只接受 `kFLOAT`。如果拿 ours ONNX 直接开 `--fp16`，TensorRT 要么在 plugin 前后插 FP16 ↔ FP32 转换，要么建不出来，哪种要实测；就算跑通也不是真正的 FP16 算子。所以分两步：

| 阶段 | ONNX | 要不要改 kernel | 目的 |
|---|---|---|---|
| 第一步 | eager（RMSNorm 是 7 个标准节点，TensorRT 用自己的 FP16 实现） | 不用 | 看 FP16 基线，验证 b8 慢是不是矩阵乘 kernel 选得不好 |
| 第二步 | ours | 要改：`kernels.cu` 读写 half、累加用 float；`launch.cuh` 选 FP16 版；`plugin.cu` 支持 kHALF | 让我们的算子真正支持 FP16 |

累加不用 half，是因为 FP16 范围和精度有限，2048 个元素求和容易出问题。先不碰 kernel，是为了一次只变一个变量。

b8 的教训是：我们能控制自己的算子，但矩阵乘这类大头由 TensorRT 选，而且核心闭源。不能改编译器时，至少要能证明问题在哪（`--exportLayerInfo`、`--dumpProfile`、nsys）。可以按这个顺序处理：① 先验证原因，用 FP16 或开 TF32 重建，看 kernel 和时间变不变；② 调整模型结构，比如改 ONNX 图、切分节点，影响 Myelin 怎么分组；③ 换 TensorRT 版本或平台比较；④ 某个矩阵乘特别值得时自己写 plugin；⑤ 换运行时对照，比如 ONNX Runtime。另外，之前 b8 变快恰好是 plugin 切开了 Myelin，不是主动设计，不能当成稳定方法。

## FP16 基线实测：开 FP16 后改了什么、快了多少、误差怎么看

**要回答的问题**：FP32 + 禁 TF32 时，eager engine 的 decode b8 要 8.92 ms，比 PyTorch eager 的 1.80 ms 还慢，推测是 Myelin 给 M=8 的矩阵乘挑了慢 kernel。按上一节"FP16 分两步"的第一步，只用现有的 eager ONNX、不改 kernel，看 FP16 快多少、矩阵乘 kernel 变没变。

**开 `--fp16` 改的是什么**：代码和 ONNX 文件都不改，改的只是 TensorRT 建 engine 时允许用的精度，所以变化全在 engine 里面。① 每层的候选实现里多了 FP16 版本，TensorRT 照样逐层实测，哪个快、能用就选哪个，不是强制所有层都变 FP16；② 选了 FP16 实现的层，权重会被转成 FP16 存进 engine，这次三个 engine 都是 99 MB；③ FP32 + `--noTF32` 时矩阵乘不能用 Tensor Core，开 FP16 后可以；④ 相邻层都是 FP16 时中间结果也是 FP16，读写减半，前后精度不同的地方 TensorRT 会插格式转换层，转换太多会抵消收益；⑤ ONNX 的输入 `x` 和输出 `out` 是 FP32，不额外设置时 engine 对外仍收发 FP32，只在内部转换，所以 `trt_check.py` 和以后的 C++ 程序不用改接口。要让接口也变成 FP16，得加 `--inputIOFormats=fp16:chw --outputIOFormats=fp16:chw`，这次没加。`--noTF32` 管的是仍保留 FP32 的那些层，保证它们和 FP32 基线条件一致。

```text
同一个 eager ONNX（FP32 权重和计算图）
        ↓ trtexec --fp16 --noTF32
每层在 FP16 / FP32 实现里实测挑选
        ↓
FP16 engine：FP32 输入 → 内部转 FP16 → FP16 矩阵乘（权重 FP16）→ FP16 / FP32 混合 → 转回 FP32 输出

实际命令（Orin，b8 为例；为了不覆盖 FP32 结果放进新目录）
trtexec --onnx=layer_eager_decode_b8.onnx --saveEngine=../layer_eager_fp16/eager_decode_b8_fp16.engine \
        --fp16 --noTF32 --noDataTransfers --useSpinWait --profilingVerbosity=detailed --exportLayerInfo=…_layers.json
trtexec --loadEngine=… --noDataTransfers --useSpinWait --dumpProfile --separateProfileRun --exportProfile=…_profile.json
```

| 形状 | FP32 | FP16 trt_check.py | FP16 + CUDA Graph | 加速 | 最大绝对误差 | 相对 L2 | 余弦 |
|---|---|---|---|---|---|---|---|
| decode b1 | 1.32 ms | 0.69 ms | 0.63 ms | 约 1.9× | 3.69e-3 | 9.52e-4 | 0.9999996 |
| decode b8 | 8.92 ms | 2.44 ms | 2.33 ms | 约 3.7× | 6.19e-3 | 8.99e-4 | 0.9999995 |
| prefill s512 | 14.84 ms | 2.31 ms | 2.32 ms | 约 6.4× | 3.86e-3 | 3.98e-4 | 1.0000000 |

条件：Orin 锁频，GPU 开始和结束都是 1300.5 MHz。FP16 时间来自 trt_check.py（CUDA event，方法同 bench_layer.py）；trtexec 的 GPU Compute Time 是 b8 2.42、b1 0.687、prefill 2.370 ms，两种方法对得上。FP32 一列和 FP16 不是同一次运行。FP32 engine 的误差对照：最大绝对 1e-6 量级，相对 L2 约 2e-7。

**矩阵乘 kernel 确实换了**：逐层 profile 里 FP32 b8 只有 1 个 ForeignNode，平均 9.24 ms；FP16 是 ForeignNode 2.42 ms，加上前后各一个 Reformatting CopyNode（0.017 / 0.006 ms），这就是 FP32 输入输出和内部 FP16 之间的转换。ForeignNode 里面看不到 kernel，所以又用 nsys 抓了 b8 FP16 engine（每次前向的平均时间）：

```text
FP32：ampere_sgemm_128x32_sliced1x4_nn            × 3，各约 2436 μs
FP16：trt_ampere_h16816gemm_128x64_ldg8_relu_nn_v1 × 2，各约 662 μs
               trt_ampere_h16816gemm_128x64_ldg8_nn_v1      × 1，约 640 μs
               ampere_fp16_s16816gemm_fp16_128x64_ldg8_f2f_nn × 2，各约 296 μs
               norm（Myelin 融合）__myl_bb0_3 / bb0_8_MulMeaAddSqrDivMulMul 约 6.0 / 5.5 μs
h16816 / s16816：Tensor Core 的 16×8×16 矩阵乘指令；h 是 FP16 累加，s 是 FP32 累加（按命名习惯理解，没查文档）
```

所以 FP16 下 b8 的大头从约 7.3 ms 降到约 2.2 ms，支持"FP32 下 Myelin 给 M=8 挑的 kernel 不好"的推测；但 FP32 下它为什么会挑 sliced1x4 sgemm，仍然没查清。另外 b8 FP16 的 2.44 ms 还是比 PyTorch eager FP32 的 1.80 ms 慢，两次不是同时测的，不能直接下结论。推测：b8 只有 8 行，128×64 这种大分块浪费了大部分计算单元，按读完权重的理论时间应该更短，**未验证**。

**误差怎么看**：几个指标比较的是同一件事，即 FP16 输出和 PyTorch FP32 标准答案差多少，只是角度不同。用三个数举例：

```text
ref = [ 2.000, 0.001, -1.000 ]   PyTorch FP32 标准答案
out = [ 2.002, 0.002, -0.999 ]   TensorRT FP16 输出
差  = [ 0.002, 0.001,  0.001 ]

最大绝对误差  max|out − ref| = 0.002                      只看最差的那个元素
最大相对误差  |out − ref| / |ref|：0.001、1.0、0.001        第 2 个被分母 0.001 放大成 1.0
相对 L2      ‖out − ref‖ / ‖ref‖ = 0.00245 / 2.236 ≈ 0.0011  整体差了约 0.1%
余弦相似度    两个长向量的方向是否一致；ref=[2,1]、out=[4,2] 时也是 1，不看大小
```

`trt_check.py` 的相对误差公式是 `|out − ref| / (|ref| + 1e-3)`，真实输出里总有接近 0 的元素，绝对误差 0.003 也会被除成很大的数，这就是 max_rel_err 到 0.61～0.87 的原因。它适合发现局部异常，不适合描述 FP16 的整体误差。这次的主要依据是相对 L2（4e-4～1e-3，整体约 0.04%～0.1%）加最大绝对误差（0.004～0.006，输出平均绝对值约 0.8、最大约 4～5）；余弦只作补充，因为输出整体放大 2 倍它也还是 1。

| 指标 | 回答什么 | 缺点 |
|---|---|---|
| 最大绝对误差 | 最坏的元素差多少 | 不知道相对原值大不大 |
| 最大相对误差 | 有没有局部异常 | 接近 0 的元素会被放大 |
| 相对 L2 误差 | 整体差多少 | 局部异常可能被平均掉 |
| 余弦相似度 | 方向是否一致 | 不看大小 |

**多少算大**：没有统一标准，分三层判断。第一层，和这种精度本身的舍入误差比：FP32 约 7 位有效数字，常见相对误差 1e-7～1e-6；FP16 有 10 位尾数，相邻两个数的间隔约 2⁻¹⁰ ≈ 9.8e-4，常见 1e-4～1e-3；INT8 只有 256 级，常到 1e-2，强依赖校准（这些是经验量级，不是硬标准）。所以这次 4e-4～1e-3 落在 FP16 的正常范围。第二层，和参考实现比：先测"PyTorch FP32 对 PyTorch FP16"的误差 A，再看"PyTorch FP32 对 TensorRT FP16"的误差 B，B 和 A 差不多才说明 TensorRT 没额外引入问题；这次没测 A，所以只能说"在 FP16 正常量级内"。第三层，看最终任务：分类看 Top-1 和准确率，LLM 看困惑度和评测，机器人策略看动作误差、成功率和动作是否平稳。工程上的起点（经验值，不是标准）：FP32 engine 相对 L2 < 1e-5；FP16 engine 相对 L2 不明显超过 PyTorch FP16 基线；INT8 先看任务指标再定能接受多少数值误差。

**还没证明的**：只测了单层，几十层叠起来误差会累积；数值接近不等于任务一样好；相对 L2 和余弦是在 Orin 上临时算的，没加进 `trt_check.py`；没有同一次运行的 PyTorch FP16 对照（要先给 `bench_layer.py` 加 dtype 参数，提了但没做）。

**为什么到这里就停**：这次要回答的三个问题（FP16 有没有收益、b8 慢是不是和矩阵乘 kernel 有关、FP16 误差正不正常）都有了答案。b8 仍慢于 PyTorch FP32 是这个测试用 decoder layer 的问题，不是项目目标；由此定下一条规则：每做一个实验先问"这个结果会改变下一步要做什么吗"，不会就记录下来，不继续追。下一步转 ACT 部署（模块 10）。

## 最后：Orin 结果（FP32 + noTF32，锁频，ms）

| 形状 | eager engine（Myelin 生成 norm） | ours engine（plugin） | PyTorch eager（bench_layer） |
|---|---|---|---|
| decode b1（括号为 CUDA Graph） | 1.32（1.25） | 1.33（1.21） | — |
| decode b8 | 8.92 | 3.98 | 1.80 |
| prefill s512 | 14.84 | 14.99 | — |

eager engine 里，Myelin 把整层包成 1 个 ForeignNode。"1 层"不等于 1 个 kernel，里面还会启动很多个。norm 是 `__myl_bb0_3_MulMeaAddSqrDivMulMul`，名字就是 7 个操作的缩写，相当于 Inductor 的 `triton_red_fused_add_mean_mul_pow_rsqrt`。

ours engine 里，Myelin 被 plugin 切成 17 段。第一个残差 Add 被包进 attention 那段 Myelin，第二个变成独立的 `/Add_1`。b8 快一倍多，并不是因为 norm 快，而是 MLP 三个矩阵乘离开 Myelin，交给了普通矩阵乘层（0.87 ms）；attention 段 b8 仍要 3.05 ms（推测同样是挑错 kernel）。**矩阵乘选对 kernel 比少几个 kernel 重要得多**，norm 只有几 μs。

b8 下 TensorRT 两个 engine 都比 PyTorch eager（cuBLAS）慢。问题在 Myelin 对"FP32、禁 TF32、M=8"的选择，和 RMSNorm 无关。开 FP16 后矩阵乘换成了 Tensor Core kernel，b8 降到 2.44 ms（见上面的 FP16 基线）；开 TF32 的情况没测。

## 面试要求

### 必须会

- 什么时候需要 plugin：TensorRT 不支持的算子，或它实现得明显不好的地方。
- plugin 的结构：plugin 类（建 engine 时 `getOutputDimensions` 等推形状、`supportsFormatCombination` 选格式；推理时 `enqueue` 调 kernel）+ creator（工厂，按 ONNX 节点属性或 engine 里序列化的数据创建 plugin）+ 注册。
- ONNX 自定义节点和 plugin 怎么对上：节点名 / 属性名。
- plugin 的代价：它是黑盒，会把 Myelin 的融合切开（RMSNorm plugin 时切成 17 段），可能反而变慢。

### 应该会

- 序列化 / 反序列化：plugin 参数怎么存进 engine（eps 的 4 字节）。
- 让 kernel 不依赖 PyTorch（`launch.cuh`），同一份 kernel 同时给 PyTorch 扩展和 TensorRT plugin 用。
- FP16 基线：开 FP16 后 TensorRT 换成了 Tensor Core kernel（`h16816gemm`），b8 8.92 → 2.44 ms；误差怎么看。
- 逐层 profile（`trtexec --dumpProfile`）怎么读。

### 加分

- IPluginV2DynamicExt vs 新版 IPluginV3；plugin 支持 FP16 / INT8 要做什么。
- TensorRT 选错 kernel 时的手段（tactic 选择、timing cache、改形状）。
